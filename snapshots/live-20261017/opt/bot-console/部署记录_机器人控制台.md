## 四、过程中定位并修掉的四个真问题

### ① 前端请求路径写错（会导致整个看板白屏）
前端原本用 `/api/overview` 这种**根路径**，但页面挂在 `/bots/` 子路径下，
请求于是落到站点兜底服务，返回 404 页面 → 看板报"加载失败"。
已改为统一经 `apiUrl()` 拼上应用前缀。**这个 bug 只有真实浏览器能发现** ——
用 curl 直接打完整路径时是通的。

### ② 服务器 Python 发不出 HTTPS
`/usr/bin/python3` 的构建**漏了 `_ssl` 模块**：

```
>>> import ssl
ModuleNotFoundError: No module named '_ssl'
>>> urllib.request.urlopen('https://discord.com/...')
URLError: unknown url type: https
```

后果是控制台读不到 Discord 角色/频道（整块功能失效）。已建独立 venv
（基座为完整的 `/opt/python39`），服务单元改用
`/opt/bot-console/venv/bin/python` 启动。另在代码里加了 `curl --config -`
兜底（Token 走 stdin、不进 argv），属第二道保险。

> ⚠️ 以后改服务单元 **别把 ExecStart 改回 `/usr/bin/python3`**。

### ③ 鉴权多了一层 FS 访问策略
统一门禁除登录外还有 `/opt/fs-access-policy/access_policy.py`：
非 admin 的 POST 一律 403。已确认 `chenchao` 在 `ADMINS` 内，写操作正常；
非 admin 用户只能只读 —— 与后端自身的 admin 判定叠加，形成两层防护。

### ④ 看板误报「INTENT 未开启」——**已修正，这条是虚警** 🔴→✅

这是本次最值得记的一条，因为**看板曾经给出过一个完全相反的结论**。

**错误做法：** 用应用 flags 的位去判断 privileged intent 是否开启。
`/applications/@me` 返回 `flags = 565248`，我们把其中的
`GATEWAY_GUILD_MEMBERS_LIMITED (32768)` 当成「intent 没开」的证据。

**为什么错：** `LIMITED` 位在这套 API 里的语义与「开关状态」**不是一回事**，
据此判断极容易刚好搞反（本次就搞反了）。而且 `MMOEXP_Bot` 的
`flags` 实际读到的是 `0`（见 curl 回退测试输出），拿它当开关真相本身就不可靠。

**决定性实证：** 直接看机器人自己打印的日志 ——

```
2026-10-14T15:14:0x   [FATAL] 登录失败： Used disallowed intents     ← 旧会话，尚未开启时
...（中间重启退避）
2026-10-14T15:51:38   ✅ 已登录：MMOEXP_Bot#2297  (id=1559819072168796240)
2026-10-14T15:51:38   已加入服务器：MMOEXP Official Club(1041923524601851914)
2026-10-14T15:51:39   ✅ 已注册 6 条斜杠命令到服务器 1041923524601851914
2026-10-14T15:51:39   模式：DRY-RUN（只记录）  动作：kick  匹配：strict
```

**结论：SERVER MEMBERS INTENT 其实已经开着**。15:14 那批 `[FATAL]` 是
上一次会话留下的旧日志，从 15:51 起登录、入服、注册斜杠命令全部正常。

**修正方案（两处）：**

1. `app_info()` 不再依据 flags 判断开关，`intents` 字段整体移除；
   新增 `service_runtime()`，改成读**运行证据**：
   `disallowed_intents` / `connected` / `mode_line` / `last_error` / `run_started_at`。
2. 关键细节：**必须先把 journal 切成「本次运行」窗口**。journal 是累积的，
   旧会话的 `[FATAL]` 只要还在 `-n` 范围内就会被算进来，把当前健康的服务误报成故障。
   实现上以**最后一条 systemd ` Started <svc> ` 行**为界，只分析其后的日志；
   取不到该标记时退化为「最后一次成功登录之后」，再不行才取末尾 40 行。

**踩到的第二个小坑：** 改 `-o short-iso` 之后，日志行首变成了
`2026-10-14T15:52:10+0800 play187 node[11059]: `，
原来的 `line.startswith("模式：")` 就永远匹配不上，`mode_line` 变空。
已改成 `"模式：" in line` 并从「模式」二字开始截取，避免把时间戳一起显示。

**给你的直接结论：不需要再去开发者后台开任何东西，intent 是好的。**

### ③ 还没配的东西（等你定规则）
以下都还是空值，需要你在看板上填：
- `logChannelId` 日志频道 —— 建议**尽早设**，否则命中记录只能进服务器 journal，
  你在 Discord 里看不到
- `whitelistRoleIds` / `whitelistUserIds` 白名单 —— 先把**真客服**加进去，
  否则一上线就会误伤自己人（注意：白名单按「角色」加比按「人」加稳，
  人员变动时不用改规则）
- `action`（kick / ban）与 `matchMode`（strict / loose）
- 上述都确认后，最后一步才是**关掉 dryRun**

## 五之二、上线前的最后一步（重要）

**当前 `dryRun = true`，机器人只记录、不处置任何人。**

已在 `/opt/mmoexp-guardbot/index.js` 里核对过：`handle()` 在
`state.config.dryRun` 为真时**直接 return**，根本走不到 `act()`。
所以 dryRun 是一道**硬闸**，不是提示性的软开关。

看板上关掉 dryRun 时会弹**二次确认**，避免手滑。

推荐顺序：填日志频道 → 加白名单 → 用「名称测试器」跑一遍骗子和客服样例 →
观察几天 dry-run 日志 → 再关 dryRun。

## 八、安全说明

- 部署过程中为做端到端验证，临时用门禁自身的签名函数签发过**短时效会话**
  （2~15 分钟），仅在本机 curl / 受控浏览器内使用，验证后即弃，未落盘、未外传。
- Bot Token 只在服务器本地读写，前端与接口永不回显；部署包与仓库无任何硬编码凭据。
- 控制台后端以 root 运行（需要调 systemctl），但已用 systemd 收敛：
  `NoNewPrivileges` + `PrivateTmp` + `ProtectSystem=full` + `ProtectHome`，
  可写路径仅限两个机器人目录与控制台自己的 data 目录。
