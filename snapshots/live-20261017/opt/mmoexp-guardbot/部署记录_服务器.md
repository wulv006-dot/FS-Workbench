## 排查记录：邀请报错「Integration requires code grant」

**报错**：点邀请链接后弹窗 `Integration requires code grant`

**根因（已用 API 验证）**：`GET /applications/@me` 返回

```
bot_require_code_grant = True      ← 就是它
bot_public             = True
approximate_guild_count = 0
```

即 **Bot → Authorization Flow → REQUIRES OAUTH2 CODE GRANT** 处于**开启**状态。
这个开关一开，Discord 就拒绝普通 `&scope=bot` 邀请链接，强制要求走完整 OAuth2 授权码流程（带 redirect_uri）。
普通机器人**从来不需要**这个功能，直接关掉即可。

**尝试过但无效**：`PATCH /applications/@me {"bot_require_code_grant": false}` 返回 200，但字段值不变
—— Discord 已不允许通过 API 修改该字段，只能在门户操作。

**修复**：https://discord.com/developers/applications/1559819072168796240/bot
→ **Authorization Flow** → 关闭 **REQUIRES OAUTH2 CODE GRANT** → 底部 **Save Changes**

## 关于「消息内容」：新功能读了私信，但**依然不需要** MESSAGE CONTENT INTENT

16:2x 加上了「状态自检」——私信机器人它会回报状态与配置。这算是"读消息内容"了，
但 **MESSAGE CONTENT 这个特权 intent 仍然保持关闭**，理由是 Discord 官方文档
（*Message Content Intent Alternatives*）明确列了三种**永远可用**的情况：

> Bots will always have access to:
> · **Messages received in DMs**
> · Messages where the bot is **@mentioned**
> · Messages the bot sends

对本功能还有个额外好处：**私信分支不检查内容**（任何一条私信都触发），
所以即使哪天 Discord 改变豁免策略，也只是"读不到文字"，
"事件照样到达、照样回报" —— 触发逻辑并不依赖内容。

只需要两个**非特权**的东西：

```js
intents: [ ..., GatewayIntentBits.DirectMessages ]   // 4096，非特权
partials: [ Partials.Channel ]                        // 私信频道默认不在缓存里
```

⚠️ **千万别顺手加 `GatewayIntentBits.MessageContent`** —— 开发者后台没开它，
代码里声明了会让网关直接以 `4014 Used disallowed intents` 断开，机器人起不来。

## 教训：判断特权 intent 要读**运行日志**，不要读 `flags`

- ❌ `flags & 32768`（`GATEWAY_GUILD_MEMBERS_LIMITED`）当「未开启」→ **假阳性**，本项目踩过。
- ✅ 读日志：有没有 `Used disallowed intents`、有没有 `✅ 已登录`。
- ⚠️ **第二层坑**：journal 是**累积**的，旧会话的 `[FATAL]` 只要还在读取范围内就会被算进来，
  把当前健康的服务误报成故障（15:14 的旧报错 vs 15:51 的正常登录就是这么被混淆的）。
  → 看板里的 `service_runtime()` 因此改为**只分析「本次运行」窗口**（以最后一条
  systemd ` Started ` 行为界）。
- ⚠️ **第三层坑**：`journalctl -o short-iso` 的行首是时间戳，
  用 `line.startswith("模式：")` 永远匹配不上，`mode_line` 会变空 → 要用 `"模式：" in line`。

### ① Admin 永不处理 → 做成硬保护（与白名单解耦）

老板原话：「admin我们肯定不处理呀，这是我们自己管理的身份组」。
之前只是把 `Admin` 角色放进白名单，属于**软豁免**（有人把它删掉就失效）。
现在改成**硬保护**，独立于白名单：

> 成员身上任何角色带 `Administrator` 权限 → 不看名字、不计命中、不处置。

三处生效：`handle()` 入口短路、`canActOn()` 返回阻塞、`guard-purge` 扫描循环跳过。

**上线前核过一次风险**（`_ops_preflight_scan.cjs`）：本服带 `Administrator` 权限的角色共 6 个 ——
`Admin`(7 人) / `MMOEXP_Official_Player`(5 人) / `MEE6` / `Bot` / `MMOEXP_BOT` / `Query_Invite_Member`。
后四个的**人类持有数都是 0**。这点必须核：如果 `Query_Invite_Member` 这种邀请追踪角色
会随加入自动分发，那"有管理员权限就保护"会把守卫整体架空。实测没有，规则安全。

### ② dryRun 关闭

`config.json` 的 `dryRun` 由 `true` → `false`（脚本 `_ops_set_dryrun.py`，幂等 + 自动备份）。
重启后启动日志：`模式：正式处置  动作：ban  匹配：strict`。
关闭**之前**先跑了全量体检，确认存量为 0 命中（见 ③）。

### ③ 状态自检收紧：只认白名单，其余完全静默

老板原话：「只有我们白名单的人私信机器人才能有反馈，其他人私信不能有相关信息反馈」。

- `operatorCheck()` 删掉两条放行路径：**服务器拥有者**、**拥有「管理服务器」权限者**。
