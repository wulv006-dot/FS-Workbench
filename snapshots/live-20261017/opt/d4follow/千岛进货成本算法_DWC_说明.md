# 千岛进货成本算法（DWC · 订单簿深度加权进价）v1

> 落地日期：2026-09-27 ｜ 适用：47.253.252.55 `/opt/d4follow` 自动改价系统 的「千岛」成本源
> ⚠ **本文档单独存档**：2026-11 新赛季重制后物品可能改成 1 / 5 / 10 个一组零售，届时需要回来重调参数（见第 8 节）。

---

## 0. 一句话

进货成本不再读千岛的「平台聚合价」，改为每轮拉取该商品的**真实在售清单（订单簿）**，
按我们的**补货批量 Q** 从最低价往上「吃深度」，算**加权均价 VWAP** 当进货单价。

---

## 1. 为什么要换：聚合价是滞后参考价（实测）

同一个 SPU（强力巢穴钥匙 · 国际服/赛季/普通）：

| 时间 | 平台聚合价 `rmbPrice` | 订单簿最低可买价 | 订单簿 1000 个的 VWAP |
|---|---|---|---|
| 05:37（库内快照） | 0.0662 | — | — |
| 09:32 | ~0.0428 | **0.0356**（库存 649+361，起售 300/361） | **0.0356** |
| 09:37（5 分钟后） | 0.0362 | **0.049** | **0.049** |

→ 那两档 0.0356 **在 5 分钟内被买光**，聚合价还停在旧价上。
换算成成本（刻度 10、汇率 6.65）：最高最低差 **86%**，直接影响毛利与「成本地板」闸门。
**结论：聚合价不能当成本。**

（`currency-spu-price-list` 仍然要用 —— 只用来拿 `spuId` / 商品名映射与全量列表。）

## 2. 两级取价分工

| 层级 | 接口 | 用途 | 刷新 |
|---|---|---|---|
| ① 平台聚合价 | `POST /c2c-web/v1/common/currency-spu-price-list` | 拿 `spuId`、商品名、全量列表（184 名/区服） | 快照超过 **6h** 才抓 |
| ② 订单簿（成本主口径） | `POST /c2c-web/v1/currency/spu-list-v2` | 真实在售清单 → DWC 成本 | **每轮（1h）**，缓存 1h |

订单簿 item 关键字段：`rmbPrice`（单价·元）、`stock`（库存）、`minBuyCount`（起售量）、
`stepBuyCount`（步进，实测恒 0）、`direction`（`SELL`/`BUY`）、`specValues[]`（区服）。

> 实测定价不是整齐的 10/100，而是任意整数（15/93/197/256/300/361/500/900/12000…），
> 且恒有 `minBuyCount ≤ stock`。所以**判档绝不能写死 `==100`**。

---

## 3. 算法

记：某一 SPU 在某区服的订单簿 = 全部 `direction=SELL`、`rmbPrice>0` 的条目，
记为 `B`，按 `rmbPrice` 升序。`moq_i` = 第 i 条起售量，`stk_i` = 第 i 条库存。

### 3.1 第一步：判档 → 定补货批量 Q

```
bulk   = Σ stk_i   (仅 moq_i >= 起售阈值)
total  = Σ stk_i   (全部)
bulk_share = bulk / total
Q = 批量档(1000)   if bulk_share >= 占比阈值(0.5)
    else 单件档(50)
```

*「整批卖」的信号 = 起售量大的那些卖家占了库存的大头。* 实测：
强力巢穴钥匙 `bulk_share ≈ 0.99` → Q=1000；宝石/小件 `bulk_share ≈ 0.00` → Q=50。

### 3.2 第二步：从低价往上吃深度，算 VWAP

```python
used, cost = 0, 0.0
for r in B:                       # 已按 rmbPrice 升序
    if used >= Q: break
    need = Q - used
    if r.stock <= 0 or r.moq > Q:  # 买不到 / 起售量比我们的批量还大
        skip; continue
    take = min(r.stock, need)
    if take < r.moq:               # 剩余需求不足一条的最小起售
        if r.moq > need * 跳过倍数(2.0):
            skip; continue         # 为一点点余量再吃一大坨 → 不值当
        take = min(r.stock, r.moq) # 整条买下（会小幅超出 Q）
    cost += r.rmbPrice * take
    used += take

单价 = cost / used
```

**用户给的例子**：库存 300@1 元 + 700@1.5 元 → (300×1 + 700×1.5) / 1000 = **1.35 元** ✅（已做单测）

### 3.3 边界规则（都不报错，只降级 + 打标）

| 情况 | 处理 | 备注字段 |
|---|---|---|
| 累计可吃深度 < Q | 用全部可得深度算，打标 | `深度不足` |
| 整簿深度 < Q（或 Q > 深度×超深倍数） | 批量口径前提不成立 → **退回单件档 Q=50 重算** | `整簿不足Q退回单件档` |
| 某档起售量 > Q | 跳过该档 | `跳过N档` |
| 订单簿为空 / 抓取失败 / 被限流 | **保持原成本不变**，绝不写 0 | — |
| 命中缓存 | 直接用缓存，不重抓 | — |

> `整簿不足Q退回单件档` 是实测补的一条：腐化根藤全簿只有 811 个却被判「批量档 Q=1000」，
> 结果吃光全簿、单价虚高 **+172%**（0.1726 → 0.4696）。退回单件档后是 0.2849，合理得多。

## 4. 参数（`config.json` → `千岛.订单簿`）

| 键 | 默认 | 含义 |
|---|---|---|
| `enabled` | true | 总开关（关掉即退回聚合价口径） |
| `缓存小时` | 1 | 订单簿复用时长；采集定时器也是 1h，所以≈每小时刷新 |
| `起售阈值` | 10 | 起售量 ≥ 此值算「整批卖」的卖家 |
| `批量档` | 1000 | 批量档的补货批量 Q |
| `单件档` | 50 | 单件档的补货批量 Q |
| `占比阈值` | 0.5 | 「整批卖」库存占比 ≥ 此值 → 判批量档 |
| `跳过倍数` | 2.0 | 凑余量要买 > need×此值 的整条 → 跳过 |
| `超深倍数` | 3.0 | Q > 全簿深度×此值 → 退回单件档 |
| `最大翻页` | 8 | 分页上限（limit=100/页） |
| `打开等待毫秒` | 12000 | 页面加载后等待 |
| `等待轮数` | 40 | 点击后等待轮数（×500ms） |
| `缓存文件` | data/qiandao_books.json | 订单簿缓存 |

### 抓取是怎么做到「一次页面加载 + 一次点击」拿 15 个订单簿的

订单簿必须在页面上「打开某个 SPU」才会发请求。5 SPU × 3 区服 = 15 组合。
做法：`page.route` 拦 `spu-list-v2`，拿到页面那条**已鉴权的真实请求**当模板，
在 route 回调里用 **`route.fetch(post_data=…)` 重放**，把 `spuId` / 区服筛选 / 分页都换掉，
最后 `route.fulfill(response=第一条)` 让页面照常显示。
被改写的只有 body —— 实测**签名不覆盖 body**（`x-request-sign` 只签 URL+时间）。
耗时：**10.8 秒**拿全 15 个订单簿。

## 7. 运维：限流 / 缓存 / 降级

- **限流**：千岛高频访问会返回 `405` + `{"message":"您的手速也太快了…"}`。
  命中即整轮放弃、沿用上一次快照，**绝不写 0**。页面侧检测关键字「手速太快」。
- **页面加载成本** ≈ 每小时：订单簿 1 次 + 聚合价每 6h 3 次。
- **缓存**：聚合价 `data/qiandao_latest.json`（3h）；订单簿 `data/qiandao_books.json`（1h）。
- **人工补数据**：`push_data.py`（本机，`POST /api/cost`）。它 import 的是同一份 `core_qd.py`，
  所以本机副本也要同步更新，否则本机会把**聚合价**推上去覆盖订单簿价。

## 8. ⚠ 2026-11 新赛季重制后的调整预案（用户已提前说明）

> 用户原话：*「2 个月后会有调整，因为新赛季重制，赛季初期，我们平台的这些物品又可能变为
> 单独一个售卖，或者 5 个、10 个售卖；到时候再找你改。」*

到时要重估的是：

1. **`起售阈值`**：赛季初如果全是「5 个一组 / 10 个一组」零售，`10` 这个阈值会把
   5 个一组的漏掉、10 个一组的又算成批量。可能要改成 `5` 或按商品单独配。
2. **`批量档` / `单件档`**：基准批量要按新赛季的实际补货量重定（现在 1000 / 50）。
3. **「整簿不足 Q 退回单件档」**：赛季初全簿普遍很薄，这条会频繁触发，
   要确认退回后的价格是否还符合预期。
4. **按商品单独覆盖 Q**：目前只有全局两档，没有单商品覆盖。
   如果赛季初各商品差异很大，需要加 `对照项[key].千岛.补货批量` 覆盖，
   并在 `build_qd_map` 里按对照项重算（现在 `qd_cost` 只存按全局档算好的一个价）。
5. **`超深倍数` / `跳过倍数`**：新赛季订单簿形态变了要重测。
