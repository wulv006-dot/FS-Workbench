# FC经营数据：字段如何取得、怎么算、能判断什么（2026-10-24）

这是按真实FS回包与活动工具源码整理的字段使用教学。字段值是教学时点的例子，后续必须重新绑定本任务证据。源未公开公式的字段明确标原值，不能替上游发明定义。业务授权、现行成本与双红线合同优先。

## 1. 每读一个字段，都走完这条思考链

**业务问题 → 来源及字段路径 → 状态/范围/单位/时点 → 原值还是推导 → 合法比较 → 允许的判断 → 其他解释 → 下一项最小补查/动作。**

例如“PC收入下降”只是定位：用支付明细platform组发现PC；再分订单与客单，随后查实际商品/型号/购买和赠送K、折扣、商业落地页与同批履约。缺交付K时客单不是单价；仍可把PC列为优先问题，但不能写量价齐跌、价格影响已排除或页面就是根因。

每个关键结论内部记录claim、evidence_id、JSON pointer、期间/范围、公式、竞争解释及会改变行动的下一证据。报告前台展示简短判断、关键图、影响与动作，不把下面手册整张复制给老板。

## 2. 主盘原生字段：先认识三个“客单”

调用示例：`fc.query_native_statistics({profile:"FC27",start:"2026-10-23",end:"2026-10-23"})`。若pending，按retryAfter接续原query；成功后用`fc.read_evidence`读相应`/data/authoritative_fields/...`或`/data/selected_derived/...`。别根据primary/supplement名字猜权威，核system、period、field_scope、unit、status、capturedAt；Admin优先且0有效。

`authoritative_fields`也不是“所有字段都已核成主站”。本例收入和订单明示主站，但多个客户/原生率字段为`field_scope=source_native_scope`、`website_basis=null`；须分别保留源生范围，不能把主盘两个字段的主站标签继承给整张表。两项同源生范围指标可以按声明公式并列观察；要外推主站客户画像或与主站收入合并归因，先核渠道范围/同单集合。未知范围限制外推，不抹掉原字段观察。

| 字段/路径尾部 | 它是什么、怎样得出 | 怎样用、能得到的判断 | 不能推出；下一步 |
|---|---|---|---|
| authoritative_fields.revenueUsd.value | Admin主站收入原值，USD；本例29396.08 | 与同站同定义完整日/同星期比较，判断总盘收入涨跌 | 不能擅称净利润或已经扣净所有退款费用；具体扣减看源定义 |
| orders.value | 同原生主站统计的订单数，本例434 | 与收入配对拆出订单和每单收入变化 | 不是人数、支付尝试或金币K；数量购买机制须商品明细 |
| selected_derived.selectedAovUsd | 程序用同一selected收入÷selected订单：29396.08÷434=67.732903… | 报告可写“每单收入/自算客单USD/单”；与同公式比较 | 不用它证明单位售价；不要与另一个原生客单混用 |
| averageOrderUsd.value | Order“单均价”原值，本例68.31；上游分母未公开 | 如有业务用途单列“Order原生单均价” | 不能用434倒推其收入或覆盖，不替代自算主盘客单 |
| averageCustomerUsd.value | Admin“customer_price”原生客单，本例69.82；未公开精确公式 | 保留原名称与定义边界，必要时向统计接口核分母 | 不擅自认作29396.08÷421或÷434；三个客单不强核平 |
| profitMarginPct.value | Order“利润率”原值，本例30.1%，毛/净及成本汇率公式未公开 | 按现行合同用于参考利润估算；变化用百分点或相对变化且标清 | 不是已核实采购毛利率、净利率或每单真实利润 |
| selected_derived.referenceProfitUsd | 现行估算公式：Admin收入×同期参考率÷100；本例8848.22008 | 报告标“参考利润（估算）”，可和同公式同期比较 | 不称实结，不用不同样本毛利率替它校正；实际利润走同单成本 |
| pureSalesUsd.value | Admin pure_amount“纯销售额”原值，本例28362.10 | 作为源定义下的销售口径，单列说明 | 不是利润，不能因名字“纯”就扣成本/广告或重复扣退款 |
| deductedAmountUsd.value | Admin deducted_amount扣除金额原值，USD | 查扣除项结构与总盘口径差异的线索 | 不能未经定义把收入减它当财务净收；先核类别与退款是否重叠 |
| newCustomers.value | Admin new_people“新客户人数”，people；本例144 | 展示原生新客人数、同定义变化 | 不是ES新客标记订单数；不因数字接近就互换，也不保证已核历史首次购买 |
| newCustomerRevenueUsd.value | Admin new_amount“新客户总额”，USD，本例8184.02 | 与同源newCustomers配对，8184.02÷144=56.833…，名为“每位原生新客收入” | 降低可能是购买K、商品、优惠或来源结构；不能直接说新客买少或获客变差 |
| payingCustomers.value | Admin paid_payments付款总人数原值，本例421 | 描述源定义下付款人数；434÷421约1.03单/人只作频次描述 | 不是复购率；客户去重/邮箱/历史定义需用户分析接口核对 |
| newCustomerSharePct.value | 此适配器明示公式为newCustomers÷orders×100，本例144÷434=33.18% | 只能按此人数/订单混合比标注原字段 | 不叫“新客占全部付款客户比例”；若算144÷421必须核两个人数集合一致 |
| repeatRatePct.value | Admin repeat_rete复购率原值92.16%，上游没公开分子分母 | 可标原生指标观察，变化写+1.60pp等 | 不能用434/421重算、宣称留存好或优惠有效；转同龄客户cohort |
| paymentSuccessRatePct.value | Admin payment_rate原值100%，尝试分母未核 | 原字段可展示，支付问题判断另找尝试/失败原因 | 不证明所有访客支付无阻塞、无弃单或通道正常 |
| fulfillmentRatePct.value | Admin shipped_rate原值76.96%，未公开精确分母 | 与相同原字段分列看；核定义、读取时点和订单年龄 | 不等于支付明细367/422，也不等于成本样本290/384 |
| refundAmountUsd / refundOrders | 两个独立原字段：退款金额1134.91、退款单数0 | 两值并列，核计入时间、状态、成功退款与撤单口径 | 金额非零而单数0不应改任一值，也不能说没有退款 |
| maxOrderAmountUsd / minOrderAmountUsd | 源生极值，本例566.77/0.86 | 极值变化提示需查大额订单分布、异常或产品结构 | 最大单没变不能排除大单笔数/金额减少；看分位或金额带 |
| goodsPaymentCny / receiptsCny | Order货款总额/收款总额原值，CNY；本例收款原值0 | 保留来源、币种和定义；真实费用审计再核合同 | 不用USD订单减CNY金额；0不是自动缺失，但定义不明不能据其判真实零收款 |

注意：本例10/16自算客单为29273.54÷435=67.29549…，10/23为67.732903…，变化为+0.64998255…%，直接保留1位小数为+0.6%。若先把变化舍成+0.65%再保留1位，会变成+0.7%，是二次舍入错误。应全精度计算后直接舍到最终展示精度，不经中间百分数二次舍入；对称分解同理。

## 3. 变化、分解、趋势与目标：算对以后才谈原因

| 计算/字段 | 怎样得到 | 支持的判断与限制 |
|---|---|---|
| 差额与变化率 | current−comparison；(current/comparison−1)×100% | 只描述相同定义的变化；比较0时比率未定义，写新增/不可比 |
| 百分点pp | 当前百分率−对照百分率，例如30.1−26.08=4.02pp | 对照10/16到10/23是跨周，不是“一天内”；相对增幅须另除对照 |
| 订单/客单收入分解 | ΔN×(A1+A0)/2、ΔA×(N1+N0)/2；相加闭合ΔR | 是算术恒等分摊，不是价格/需求因果份额，N不是K、A不是每K价 |
| 多日合计客单 | 同口径sum收入÷sum订单，不能平均每日客单 | 同星期、同长度、同节假日/版本影响分开解释；主盘周趋势用原生合计 |
| 平台贡献 | 同完整支付明细分组的Δ收入；合计回到该明细Δ收入 | 支持该明细内谁拉动/拖累；不自动成为主盘归因或客户迁移 |
| 累计完成率 | 同目标版本的累计值÷目标；时间进度=已完成自然日÷月天数 | 领先仅说明累计跑在日历前，不是锁定；收入/订单/利润分别计算 |
| 剩余缺口/所需日均 | target−actual；再除剩余完整天数，单位保持一致 | 收入跑速不能证明利润达标；利润用利润缺口与利润日均 |
| 月累计参考利润 | 本例720890.24×月累计参考率25.4%=183106.12 | 不是用单日30.1%算出的；不能把月累计进度归因当天率 |
| 情景/门槛 | 取明确假设或用户目标并标来源，再做条件计算 | 情景不是预测；CPA30/ROAS2/PC客单60等若无推导不因标“建议”就变成有效标准 |

`fc.calculate`需绑定原证据的`value_paths` JSON pointer（以`/data/...`开头），值必须与字段完全一致。ratio为分子/分母，difference为[对照,当前]；assumptions有值时结果只能称情景。先读字段定义，再选分母，不能为了算得出就拼两个来源。

## 4. 支付明细：维度是“切哪里”，指标是“量什么”

`fc.query_business({start,end,group_by:["platform"],filters:{},page:1})`返回当前不可变明细中的分组；可按需要最多三个维度交叉，例如platform×product。先核coverage、pagination与source_grain。`fc.query_queue`查当前未结池，不加支付日筛选；不能把它当昨日新增积压。

| 维度/字段 | 该怎么用 | 使用后能说什么；下一步 |
|---|---|---|
| day / hour | 按paid_at的支付日/小时，先核时区 | 定位哪天/时段变化；不是下单日或价格生效时刻，价格分析要接真实暴露时间 |
| platform | PS/Xbox/PC及unknown分别保留；核mapping | 平台分化、贡献互抵；不能从平台边际证明客户迁移或某个平台是全部主因 |
| product | 源产品分类，Coins/Items/待分类不强行合并 | 品类量额结构；未知分类不可补成Coins，整单金额不自动等于单品收入 |
| country | 用该源国家字段，未知保留 | 国家结构异常线索；不直接代表国籍、广告定向或语言；下钻商品/来源交叉 |
| device | 用源设备分类看结构 | 设备群体的订单/客单变化；不能把订单设备分布当网站访问或证明手机结账故障 |
| payment | 支付方式/通道按源字段分组 | 已付订单结构；没有尝试/失败分母不能算通道成功率或损失订单数 |
| site_group | 当前主站/卫星规则，分销门店身份未知另标 | 描述该分组；推广码渠道不是站点身份，不凭码把订单从主盘剔除 |
| status | 读取时当前状态 | 当前问题/完成/退款结构；不能冒充支付日末状态或完整事件历史 |
| age_band | 以本次captured_at减paid_at（必要时源定义created_at），分年龄带 | 老池风险与处理优先级；不是已等待实际发货时长；已部分交付价值未知 |
| orders / revenue_usd | 去重后的付费订单数/本集合USD合计；unpriced分列 | 同集合收入=订单×客单；不能强行与主盘同数 |
| average_order_usd | 本明细收入÷本明细订单，已展示舍入值 | 同明细比较；不能与原生selectedAov拼成一条趋势 |
| current_completed / current_unfinished / current_issues | 捕获时状态计数；问题通常是未完成子集，按源互斥关系核 | 描述当前状态；问题与未完成不相加；不据跨年龄批次直接宣布处理变慢 |
| current_funding | 源当前待付款/资金状态计数，按本模块定义 | 用于状态组成，不能替代所有支付尝试 |
| progress_field=not_provided | 未投影真实交付进度 | 不是0交付。先查已开放商品订单/履约样本/原订单阶段；缺则保留未知 |
| known_revenue_usd / unpriced_orders | 已知金额合计与无有效金额记录数 | 金额覆盖是否足够；缺金额不补0，分组收入排序可能受缺失影响 |

业务用法：发现PC收入下降→看PC订单和客单→用product_sales定位PC Coins具体产品/型号→用query_product_orders核档位/数量单位、赠送和状态→再与实际折扣和相关落地页比较。不要只写“让运营去查”，而不使用当前工具可给的最小汇总。若工具确实不投影交付K，记录已查接口与精确缺字段，不编单位价。

## 5. 商品/规格/数量：先搞清一行代表什么

`fc.query_capability(kind="product_sales",profile,start,end,...)`和`fc.query_product_orders(profile,product_id或model_id,start,end,platform,...)`参数以实际schema为准。先从商品销量识别产品/型号，不猜ID。一个通用Coins PID可能覆盖全部数量档，PID订单数不是金币数量，也不是人数。

| 字段类 | 得出方式与单位 | 可以判断/不能判断 |
|---|---|---|
| product_id / model_id / platform | 真实源身份与映射，不能跨命名空间换用 | 能锁同款/规格/平台；wiki展示产品不按未售卖报错 |
| quantity / unit / package | 读原商品行数量与单位；100K基包、赠送、整数K自定义分别核 | 数量可加须同一单位与真实包含关系；缺单位不能加，1件不必然100K |
| 整单USD / 商品行原币 | 订单金额与商品行金额分开 | 跨商品订单要避免重复计整单收入；不把GBP商品行与USD订单相减 |
| delivery K / bonus K | 实际交付与赠送各有回执才计算 | USD净收÷实交K才是到手单位价；原选购K不必然等于已交付K |
| pagination / duplicates / changed total | 各PID/型号逐页核总数与稳定身份 | 未走完是部分，不是后台缺数据；跨PID重复订单须去重 |

## 6. ES、优惠与推广归属：金额、资格、归因三层分开

| 字段/维度 | 如何取得与计算 | 能判断什么；不能推出什么 |
|---|---|---|
| 订单金额（美元） | ES原USD字段，按所选文件/状态/日期去重 | 本文件集合的订单金额结构，不覆盖Admin原生主盘或自动当财务净额 |
| 实付金额与币种 | 原币分别保留，GBP/EUR/USD不合并 | 同币种观察或有真实换算依据后比较；不与USD直接相减推优惠 |
| discount_amount_usd / actual_discount_usd | 实际折扣金额字段，用户已确认统一USD，含0/负值/缺失 | 让利金额与结构；不是名义折扣比例，也不能从已扣优惠收入再扣一次 |
| known_discount_orders | 有折扣字段的订单，可含0 | 不等于实际正优惠订单数；需另看positive_discount_orders与unknown |
| new_customer / 新老客是/否 | 原始订单标记，按原状态分组 | 新客标记订单结构，不是独立新客人数、首次购买证据或独享优惠资格 |
| order_status | 完成/支付/退款/验证未过等分列 | 实际兑现让利需合适状态与退款冲回；全状态让利不叫净已核销费用 |
| channel / coupon map | 按用户确认码映射分类，版本与生效范围另核 | 推广归属线索；不等于订单主来源、站点或因果增量，重合不能相加 |
| advertising_source_totals / PMax | 按订单实际游戏与来源识别，保留去重与覆盖 | FC实际成交可归FC项目；平台PMax总费用/价值跨游戏，不能整条套FC |
| retained_ratio | 同集合net_order_usd÷(net_order_usd+实际优惠USD) | 收入加权观察让利强度，不是活动核销率、优惠资格覆盖或未来概率 |
| 每单让利/折扣占比 | 同集合实际优惠÷同集合订单，或÷已声明金额基数 | 基数若是优惠后金额，就不能直接与政策30%优惠前基数比较 |
| file_set_complete | 声明的文件是否全部读完 | 不代表上游整日/主站/全部状态齐全，须同时看upstream_completeness |
| captured_at / aggregated_at | 来源采集与本次聚合时点分开 | 采集07:11不能单独证明支付只覆盖到07:12；须核实际支付时间范围/导出边界，未核不要写死时段 |
| missing_dimensions / timezone / upstream_completeness | 工具明确的维度/时区/范围边界 | ES缺platform或country不足时，换到完整Admin支付明细/商品接口；不宣布公司无数据 |

## 7. 成本、毛利、完成率：三个分母不能混

`fc.query_pricing_evidence({kind:"order_costs",profile:"FC27",start,end})`复用既有同单成本档案，只覆盖其声明的Gold/站点/状态范围。看summary与coverage，再按customerType/platform/project组解释。

| 字段 | 怎样得到 | 如何用于结论 |
|---|---|---|
| orders / coins_selected | 原筛选Coins订单数，含原声明的各状态 | 是选单分母，不是已完成成本样本，也不是客户人数 |
| completedOrders | 该档案捕获时完成的订单 | completed÷selected是完成占比；不能与另时点支付明细完成率直接比较 |
| coveredOrders / missingCostOrders / missingRevenueOrders | 按原订单身份匹配收入和实际成本，分别计缺项 | 290完成、290匹配、缺成本0说明完成样本全匹配；不说明未完成订单未来成本0 |
| saleCny / costCny | 同已匹配完成集合的真实收入/采购成本，CNY | 同集合profitCny=sale−cost；不能换上全日USD收入与旧汇率混算 |
| profitCny / margin | 本例43835.80；43835.80÷147195.15=29.7807% | 称该完成样本采购毛利；未扣广告/支付/退款费用等不称净利 |
| 每单收入/每单成本 | sale或cost÷同集合完成订单数 | 507.57/356.41是每单，不是每K；变动可能来自K档与平台结构 |
| 实际单位成本/单位实收 | 同集合金额÷同定义K，含赠送、舍入、退款及真实汇率口径 | 有K才能谈单位价格或采购价变化；套餐数量未保留则机制待验 |
| 金额覆盖 | 已匹配金额÷同一目标集合应匹配金额，另列订单覆盖 | 金额分母没给就未知；75.5%完成占比不能自动当75.5%金额覆盖 |

| 广告后贡献 | 同范围采购毛利−可归属广告费 | 广告费范围没闭合就未识别；广告不改变采购毛利本身，条件保本不是需求预测 |

|---|---|---|
| Ads cost / costMicros | 原平台费用，costMicros÷1,000,000转账户币种，归一回包cost按其currency | 投入变化；多账户币种未统一不可直接相加 |

## 10. 怎样把数据变成结论和行动

每项交付用四句话检查自己：

1. **我观察到什么**：字段、方向、范围与数据质量。例如“同路径Coins页sessions下降、跳出上升”。
2. **它对经营意味着什么**：可以列承接问题为优先线索，但金额影响未识别，不把相关升级因果。
3. **还可能是什么**：来源结构、设备、资讯导流、内容需求、埋点或短期波动；找能区分的最小字段，而非无差别列所有可能。
4. **现在找谁做什么**：先自行用已开放接口完成最小聚合；剩下的专业核对交对应负责人，写交付/复查/不同结果的后续。建议条件从已批目标、历史基线、SLA或明确试点设计得出；缺依据不造阈值。

标题、行动卡、图注也要逐字检查：没K就不写量价齐跌；没识别设计不写根因已确认；有年龄解释的可能性，就不在标题说年龄解释不了。正文承认不确定而标题下断言，仍是失败。展示层只保留必要基数、变化和判断，详细字段/前后原值放可展开证据，涨红跌绿配正负号和清楚比较基准。

## 字段理解练习的审校规则

- 不把同表所有字段继承成主站：逐字段读 field_scope/website_basis。原始 source_records 的 all-websites 与权威选值的 scope 是不同层；以各自声明为准，未知不推断。
- channel_type=DEMAND_GEN 只可称 Demand Gen；系列名含视频不证明投放素材都是视频。SEARCH、DEMAND_GEN、PMax 按真实类型分层。
- 采集时刻和记录条数接近全日不能证明导出边界矛盾，更不能断言“7小时不可能产生这些订单”；先核时间字段、唯一订单和分布。
- 不能从已舍入的同比/环比反推精确对照值；有原始字段则读取原始字段，无则标估算。
- 当前证据没有某字段与后台没有该字段不同；同包中部分分组没投影，须读路径/分页再查合法接口。
- 未公开累计参考率的生成算法，不能把它定义为每日简单平均或某种加权平均；只按已约定公式用累计原生率计算参考利润，不能倒因为率的来源。
- 建议期限以任务生成时点和负责人的合理交付窗安排；是建议，不能冒称已下达或已确认承诺。
