## 1. Admin 支付明细是独立模块，不是 Order 明细

- `facts/REFERENCE-FACTS.json` → `daily.detail_trend`，evidence_id `ev_543ea67fce5f655863c23a98`，来源是 **Admin FC 支付明细**；captured_at `2026-10-17T03:08:25.235253+00:00`，snapshot_id `fc-detail-d2705a27ad4c190d37ef`。
- 该序列 10/16 为 427 单/$29,432.75，是按支付时间、含当前状态的支付明细结构；Admin 原生主盘是 435 单/$29,273.54。两者同属 Admin 但模块与分母不同，不核平、不缩放。
- 周报的真实来源按行区分：`weekly.native_dimensions.primary.system = order.p2pah.cn`（品类、状态等），`supplement.system = admin.p2pah.cn`（国家、设备、支付、问题分类）。不要把周报真正来自 Order 的字段改标成 Admin，也不要反过来。
- 写作时用“Admin FC 支付明细”或“Admin 订单统计”，不要笼统写“支付明细”，更不要写成“Order 支付明细”。

## 2. 客单因素的舍入

- 顺序公式：客单因素 = Q1×(A1−A0)。10/16 日报为 435×3.02670323387529… = **1316.6159067357535**，四舍五入 **+$1,316.62**（不是 1,316.61）。
- 先用原精度核恒等：−9,254.705906735754 + 1,316.6159067357535 = −7,938.09，与收入差额一致；再展示。
- 两项展示值相加若出现 1 美分差，注明是舍入差，不修改原值或强行凑平。

## 3. 对称分解原本正确

- 认可范本 HTML 的图注与 `facts.comparison.symmetric_decomposition` 都采用两期均值：−$9,472.63 / +$1,534.54，名称与算法一致，**范本没有命名错误**。
- 失败稿的错误是：用顺序公式的数（−9,254.71 / +1,316.62）却写成“对称算术分解”。
- 新方法（METHOD）选择顺序公式，是方法选择，不是对范本算法的否定。两种都可成立，条件是名称与公式配套、并声明不是因果识别。

## 4. 履约年龄的语义

同一快照下不同支付日队列的完成率差异（10/16 85.7%、10/14 91.4% 等）本身就符合“越新的订单越可能尚未完成”，不能拿较新队列偏低来排除年龄解释，也不能据此认定某日额外延误。正确写法：完成率下降值得跟进；同日读取的队列年龄不同，现有聚合快照尚不能分清订单年龄与处理延误的各自影响；先核未完成与问题单的实际等待时长与状态，次日复查同一批。判断是否真的变慢，需要同一批订单各自 T+1/T+3/T+7 的历史快照。

## 5. 回执字段的取值规则（通用）

- 生成/读取时点一律由 `datetime.now(timezone.utc)` 等真实时钟取得，不手填、不估计、不倒推；若原字段是手写值，标为 unknown 并保留原值，另写 corrected_at。
- SHA、字节数、计算回执从实际文件或程序输出读取，不从记忆或草稿抄；展示值与原精度分开记录，展示舍入差如实说明。
- 声明“已检查/已通过”必须绑定实际被验的 SHA；外部验收的 SHA 与本地产物不同时分别记录，不合并、不冒充。
- 字段名要准确：`style_source_html_sha256` 指整份 HTML，`style_css_sha256` 只对 `<style>` 内容字节；安装清单区分初装版本与最终版本。
