# FC27 三类报告（日报 / 月中复盘 / 市场与定价研究）

用一份 JSON 驱动一张**自包含 HTML 成品页**，可同时输出同口径 Markdown。三类报告共用同一套版式、语言与交互（学习自用户提供的 Codex 示范：`FC27_经营日报_20261014.html`、`FC27_月中经营复盘_20261001-14.html`、`FC27_市场与定价策略研究_20261015.html`），只换内容骨架与数据。

## 何时用哪一类

| 类型 | 回答的问题 | 核心内容 |
|---|---|---|
| `daily` 经营日报 | 昨天发生了什么，接下来先做什么 | 同星期/前日对照、异常来源、当前问题池、次日动作与复查 |
| `midmonth` 月中经营复盘 | 目标是否有风险，资源怎么分配 | 阶段实绩与目标进度、周计划与月末情景、流量与运营策略、下半月排期 |
| `pricing` 市场与定价研究 | 竞争位置如何，什么条件下值得应对 | 分平台竞品与折算、有效成本与贡献、条件优惠、Items 同款、监测阈值 |

派发任务里出现「日报/月中复盘/定价研究」就选对应类型；同一期数据只允许进入对应类型的报告。

## 怎么跑

1. 复制上一期的输入 JSON（`assets/` 里的三份即上一期真实输入）：`daily-20261014.json`、`midmonth-20261001-14.json`、`pricing-20261015.json`。
2. 改数据与文本块。数字只填**原值**：日序列、平台/品类/支付差额、队列分档、目标值与情景参数。合计、占比、拆解、闭合都交给脚本算，不要手写汇总。
3. 生成：`python3 scripts/render_report.py assets/<本期>.json --out-dir /profile`。
4. **只看退出码 0**：脚本打印每个切面的闭合值，任一项不回到净变化、或模板残留占位符，就以 2 退出。不一致不交稿。
5. 交付：聊天给两分钟读完结论 + 文件路径；HTML 用 `MEDIA:` 与 `::preview{file="..."}` 发出。

## 三类报告的内容规则

1. **首段三句**：结果（含绝对额与百分比）→ 主要判断（缺口/机会落在哪个位置）→ 次日或下半月优先动作。不把证据清单塞进摘要。
2. **金额与订单分轴**，图与表必须成对：图给方向，折叠表给原值。比率不能与金额同轴。
3. **涨红跌绿表示数值方向，不是好坏评价**；正负号也要写清楚。
4. **每节一个结论式标题**（“销售下滑，主要少在金币”），不写“销售分析”。
5. **事实 / 替代解释 / 缺口**三段式：未证就写未证；相关不能写成已确认原因。
6. **行动**：对象、建议负责人（标“建议”）、首查日、复盘日、看什么、停止条件；全部标“未执行”。
7. **估算**（Order 参考利润、情景、竞品折算）必须写明口径与“估算/非结算/非承诺”，并写明来源范围与采集时点。
8. **同一批订单的不同切面不可相加**；全站流量/广告只作背景，不写成 FC 归因。
9. **缺口单列**且写清“会怎样改变判断”；不能因为一两条记录或几美分差额让整篇没有结论（工作目标：主要结论九成以上有证据覆盖）。
10. **详情折叠**：正文只留会改变读者理解的短说明，口径清单、样本说明、15 条以上明细放折叠区。

## 版式与交互（已固化，勿逐期重写）

- 顶栏：`展开明细 / 打印 PDF / 下载 HTML`；页内目录折叠。
- 组件：指标卡、结论条 `insight`、双栏图、可切换系列折线图、横向差额条形图、折叠原值表、行动卡（dl 字段）、新闻卡、来源折叠区、页脚免责。
- 交互：`data-series` 系列切换、`data-zoom` 放大/恢复、展开明细、打印、下载离线 HTML、情景敏感性计算。纯内联 JS，无外部依赖，离线可开。
- 打印样式：隐藏顶栏/目录/按钮，图表不缩放，A4 边距。

## 陷阱（已踩过）

- **穷尽分组的残差要算不要凑**：未被单列的项（如支付渠道里的其它通道）按残差补行，残差 = 总差额 − 已列各项。但**先用快照锁定本期额与对应期额，再算残差**：同一业务日存在两个采集读数时（如 10-11 的 $27,378.33 / $27,398.21），先统一到一个冻结快照，否则时点差会被误算进残差（会差出几美元到几十美元）。
- **两套范围不能合成一个利润数**：原生汇总／参考率与主站支付明细分母不同，分列；不把原生“利润率”写成毛利率或净利率，不再机械扣一次费用。
- **选样按变化绝对值**：地区与支付取变化金额最大的若干项，不按体量最大挑；未展示部分仍计入总盘。
- **验收记录要分开写**（已生成／已核数／已浏览器检查／已送达／已入池／已读取／已应用），前一项不得冒充后一项。
- **图表数值用未四舍五入的原值计算**，显示再四舍五入，否则占比与合计对不上。
- **同一金额不要在两处用不同采集时点**：一天有两个读数时统一采用与其它切面核平的时点，并在缺口里写明差值与原因。
- **等天数、等日龄才能比**：周对周必须等长；只发生了三天的周不能拿整周目标比完成率。状态类字段（问题单、未结、履约完成率）还要按**日龄**对齐——最新的业务日天然问题单最多、完成率最低，直接和上一日比会把成熟度差读成恶化；改用 T+2/T+3 的同日龄复核。
- **商品行标题不能当历史规格证据**：同一个 pid 在不同读取日显示不同标题（同一档今天“400 K coins”、次日“480 K coins”，另一档甚至出现“2500 K coins”而当日单均只有几十美元），标题取自当前商品主档、随下钻当日变化。判定档位/规格/捆绑/赠送是否变化，只能用商品变更记录或订单行规格，不得引用标题文本。
- **脚本退出码非 0 不得交稿**。

## 口径与来源（2026-10-15 核对，写报告前先对齐）

1. **两条成本/利润通道，不要混用**：
   - 金币定价输入用 **Order 最新成交单成本**（`fc.query_market_snapshot`，限定 `gid=1322,cid=1,genre=1`，PS/XBOX/PC 分平台，CNY/K，**只接受“订单发货”**；类型未知即失败，不回退旧成本）。
   - 经营参考用 **原生逐日参考率** `fc.query_reference`（pending 时有界复查同一请求；缺日保持缺失；它不是区间聚合器）；区间准确统计用 `fc.query_native_statistics`，并检查实际 `period`、来源范围与 `metrics.profitMarginPct`。
   - 预估利润 = **主站金额 × 对应期间参考率 ÷ 100**，标“预估、非结算”；月中/区间取不到就留空，不借昨日率、不平均日率，**也不得再对参考利润机械扣一次 5%**（5% 只用于定价贡献情景，以成本通道的成本计）。
2. **原生“利润率”不得写成已核实毛利率或净利率**；上游是 HTML 统计页，不是公开的 JSON 成本/利润接口；Admin 与 Order 的游戏 ID/身份不混用。
3. **目标值只抄原值**：营收/订单/客单/预估利润/新客/复购/发货完成率与利润率是分别给定的目标；周目标加总与月目标有差额（如 $830,000 vs $831,000）**保留原值，不为核平改写**；正式考核分母未批准前，写“管理参考”而不当考核结论。
4. **估算类与情景类必须标明口径、来源范围、采集时点与“估算/非承诺”**；全站流量/广告只作背景；竞品单列条件优惠、统一实际到账量与平台。
5. **建议负责人写角色并标“建议”**；模块 owner 不等于已接受责任人。
6. **不要混称来源**：服务器成稿（dashboard 侧）与桌面暂存版（本技能产出）是两回事，引用时要写清是哪一个、什么时间。

## 与定时任务的关系（现状，不代表下个周期成功）

经营管理每日 00:35、FC 日报每日 00:45、周报周一 01:45、整月月报每月 1 日 03:15；06:59 停止、07:00 前收尾，白天不补跑；**无月中与独立定价定时项**。本技能不新增/修改定时任务；被要求“明天早上交”的任务，先核这个 schedule 与任务库实际状态，不能把计划时间当已执行。

## 交付与发布边界

- 交付物是成品页（HTML）+ 同口径 Markdown，不要把结构化 JSON 当交付物。
- **暂存目录（当前默认）**：生成到 `/profile/desktop-reports-<日期>/`，并同内容复制一份到 FS 共享家目录 `/fs/desktop-reports/<日期>/`，一并写 `MANIFEST.json`（contract `hermes-desktop-reports-v1`，含碎值与 sha256、`not_in_fs_pool` 说明）。目录名和约定待用户确认后可改。
- **FS 共享池（dashboard 8895，contract `hermes-fc-shared-reports-v1`）只收录 FS 自己跑出来的报告**：池中条目来自 `/fs/tasks.sqlite3` 的 requests 行与 `/fs/reports/<task_id>/` 工件；`recover_reports()` 只对已存在的任务行做回送校验，`report_artifacts.py` 明确“no general file-write API”，dashboard 全部非健康路径返回 `401 login_required`（本机无凭据）。
  - 因此：**手写文件不会出现在池列表里**，不要为了“进池”去伪造 `<task_id>` 目录、metadata.json 或写库；也不要用桌面 token 去绕鉴权。
  - 要真正进池，只能（a）由原发布任务在合法空闲窗口完成发布并回收执，或（b）在 dashboard 提交任务让 FS 自己生成。两种都需要用户/发布任务动作；交付时把这个边界和已落盘的绝对路径写清楚。
  - 外部成品导入候选（运维侧显式登记 + catalog CAS，非 inbox 扫描器、非通用上传接口，目录刻意在 Desktop 的 `/fs` 绑定之外）**本轮未上线**；未收到上线与收录回执前，不得写“已入池”。

## 服务器成稿（FS 侧老板版）的交接契约

同一批证据除了桌面成品页，还会由 FS 运行时自动生成一份老板版（`/fs/reports/<task_id>/boss-semantic-v2-*.html`）。它不吃你的 HTML，只吃**你的正文 + 冻结证据包**，所以正文写法直接决定那一页能不能用：

1. **对照窗必须显式声明**：给结构化 `comparison_period:{start,end}`，或写成带完整区间的行（`对照窗：YYYY-MM-DD 至 YYYY-MM-DD`）。**绝不写行首只命名、不给区间的“对照/对比/环比(期|窗口)：…”**——排版层会判成“声明有歧义”，静默清空指标卡对比与 6 张图里的 5 张，不报错、不提示。行首不出现这些字样的叙述式写法（“…与上一自然日 A 比较”）是安全的。
2. **两个窗口都要取同一组维度明细**（平台/品类/国家/支付/队列）。只取对照日的当日总额，变化拆解、平台、品类三张图必然空白。
3. **正文不要再用 `#` 一级标题**：版式层已渲染页面标题，正文从 `##` 起，否则页内出现重复 H1。
4. 老板版是 FS 的产物：不要手写文件塞进 `/fs/reports/<task_id>/`；要复现或校验就在本地重放投影，产物落到自己的暂存目录。

声明契约、降级排查与修复位置见 `references/fs-boss-page-pipeline.md`；本地重放用 `scripts/fs_boss_replay.py`。

## 2026-10-17 真实学习复测补充：迁移假设与四类日期

1. 迁移题明确给定假设时，先在同一假设和窗口内回答；实际证据若来自不同日期/游戏/窗口，不得替换或反驳题设。实际核实步骤另列，不能锚定示例数字。
2. 分别记录事件发生/生效、信息发布、获知、业务行动执行日期。期内已发生且当时已知可作期内背景；期后知悉的期内事件放期后披露并注明回溯；期后发生不解释期内变化。任何一类均不因时间重合自动成立因果。


## 2026-10-17 用户纠偏：经营与销售是报告主线

日报先回答今天要处理什么，周报回答本周生意发生了什么、下周如何安排。先审经营结果、销售结构、客户和交付售后，再用流量辅助解释。不能因接入了营销数据而把经营报告写成广告周报；也不为了章节齐全而堆数。按照对收入、利润和客户影响挑选重点，异常与改善都解释。

经营覆盖收入、订单、客单、参考利润及已确认目标；销售按游戏/品类/商品/平台/市场和新老客定位变化；履约售后检查原生完成率、问题单、取消、暂停、退款金额及可得时长、原因与解决进度。项目报告只看指定游戏，全局报告才比较各游戏；不得挪用其他游戏数据。Admin字段可用就采用，Order补缺，不因网站/平台范围不同拒用已授权补缺字段，保留原生口径与来源即可。

已有问题单或品类数据必须分析，不能写成缺失。问题单状态数量、全体发货完成率、同一批问题单的最终履约/解决率分开；没有固定队列和状态流转，不伪造解决率或超时率。退款金额、退款笔数及问题单金额不是同一概念；字段不一致时保留原值并核查，不把0笔改成零退款。不要把退款再次扣入参考利润构造未确认净利润。

首屏及默认可见图表突出真正的经营重点，销量/商品结构/履约售后优先于辅助流量图。周报至少给出已有销售结构和履约售后证据对应的判断与行动；没有异常也说明改善及尚未解决事项。将相关任务分给运营、采购/履约、客服、数据、投放等适合岗位；有责任、产物、期限及复查结果，不能所有动作都变成查广告或做内容。报告不扩大真实业务写入权限。
