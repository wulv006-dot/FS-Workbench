# 经营报告创作方法 · 1.5.1（读者视角与自主设计）

本版来自用户2026-10-17的明确纠正：旧产出的质量不合格，报告方法重新建立。只替换报告创作方法，不删除业务事实、历史决策、来源合同、失败记录，也不扩大业务写入权限。报告方法的唯一正文是本技能及随附 METHOD.md；旧报告技能改为指向本技能的简短入口，不再同时提供互相冲突的写法。

## When to Use

- 需要经营日报、周报、月报、区间复盘、专项分析或简短经营问题解读。
- 用户反馈旧报告质量、理解或排版问题，需要重新分析或调整呈现。
- 需要把真实证据转为易读图表、关键分析、建议或简洁回答，具体设计自主。

## 按问题选择方法与输出

1. 历史examples只在有助于本次问题时按需参考，不是每次必读的前置条件，也不继承其数据或旧结论。用户2026-10-18已明确放开报告视觉：配色、字体、布局、图表及阅读顺序自主，FS只作宏观建议；旧“必须复刻/必须使用FS样式”的要求被替代。此例外仅限报告HTML。
2. 按本次问题采用METHOD.md和ACCEPTANCE.md的适用要求；复杂报告参考读者视角、场景覆盖、图表密度与互动指南，简短问答不套页面施工流程。历史施工脚本仅供阅读，不执行其旧路径或旧数据。assets中的FS样式可作参考，不是报告必选依赖。计算说明见references/example-notes.md。
3. 为本次报告建一份经过核对的事实对象：期间、对照期、采集时间、游戏、来源、原值、单位、分母和缺项。正文、卡片、图表、原值表都由这一份对象生成。历史示例只教方法，不能成为未来期间的事实。
4. 按问题明确本期情况、值得处理的事项和可行动方向，再选择阅读顺序；不固定句数、问题数、动作数或章节，简单问题可直接回答。
5. 简单问题直接返回简洁文本；复杂分析按需选择完整 `<!doctype html>…</html>` 文件交付，内联必要 CSS/JS/数据，可离线打开。不要把 HTML 包在 Markdown 代码块，不输出前后说明混入文件。独立另存学习/验收回执。

## 报告主线

经营结果 → 销售与客户变化 → 利润、履约和售后影响 → 现实活动与历史动作 → 优先行动与复查。流量和广告用于解释经营，不能抢占主线。根据实际重要性合并章节，自主安排阅读节奏；不要逐字段造章节，不要求每份报告凑齐相同章节数。

日报回答“今天先抓什么”，D-7为主对比、D-1辅助；周报回答“本周发生了什么、下周如何安排”，用完整自然周及前一完整自然周。月报采用真实月区间和已确认目标；专项报告围绕一个决策问题。数据缺失只约束相关判断，不令整篇退化成审计报告。

核心销售、订单、每单金额、参考利润采用 Admin 原生统计；同一字段 Admin 有值（含0）优先，缺失直接用 Order 补充，平台/网站差异不构成拒用理由。利润率缺于Admin时用Order利润率，参考利润=Admin销售额×该利润率÷100，明确是估算。详细口径和计算规则见 METHOD.md，不能自行改公式。

来源标签按行写实，不按整份报告统一：Admin 内部至少三块——订单统计（主盘）、支付明细（按支付时间、含当前状态，另一模块、另一分母）、原生品类/问题聚合；Order 的状态明细属 Order。不要把 Admin 支付明细写成 Order 明细，也不要把 Order 状态改标 Admin；周报按行保留 `primary.system=order.p2pah.cn`、`supplement.system=admin.p2pah.cn`。两模块并列时写明“同属 Admin、模块与分母不同”，不核平、不缩放。

收入量价拆解按 METHOD 的顺序公式，并只叫“订单量与客单的算术拆解”。认可范本与 `comparison.symmetric_decomposition` 用两期均值的对称算法，本身正确、名称与算法一致；顺序公式是本方法的选择，不是对范本的否定。任何公式都先按原精度核恒等，再展示；两项展示值相加若差 1 美分，注明舍入，不改原值凑平。

履约率跨期比较先看订单年龄：同一快照下不同支付日队列的完成率差异本身符合“越新越可能未完成”，不能拿较新队列偏低来排除年龄解释，也不能据此认定某日额外延误。聚合横截面分不清年龄与处理延误时，写“值得跟进、现有快照尚不能分清、先核未完成与问题单的实际等待时长与状态、次日复查同批”；要定量需同一批订单各自的 T+1/T+3/T+7 历史快照。

## 呈现约束与设计自由

用户2026-10-18最新明确：Hermes的经营分析能力已足够，下一阶段重点是按人的阅读与决策习惯解释和呈现分析，而非再限制推理。分析路径、问题挖掘、结论与设计方案自主；固定的是呈现效果：数据优先用清晰紧凑的图表，文字提炼重要结论、业务含义、建议及下一步，提供有用交互。FS视觉只作宏观参考；报告HTML的具体配色、字体、布局、图表类型与阅读顺序由Hermes自主选择，不强制复刻旧范本、FS令牌或组件。继续遵守此前确认的红涨绿跌语义、真实数据与必要的可访问性/离线交付边界。此例外仅适用于Hermes报告，不授权改造FS工作台或全站样式。
日报周报要检查销售与利润、商品/市场/客户、交付履约与支付、退款拒付及客户体验、运营策略（含新客优惠与复购）、广告及自然获客、真实游戏节点与活动、已有动作和效果，以及风险、机会、关键决策与待决。日报侧重异常和当日可执行事项，周报侧重变化、问题成因、跨环节影响及接下来的安排；全场景先看一遍，再按重要性组织，不能因某类工具数据多而偏题，也不要求每个场景等篇幅。无重要变化可简述，缺数据如实标注，不造数凑章节。
重点问题必须让读者看懂“发生了什么—我如何判断及可能的其他解释—经营影响—先做什么—何时如何复查”。保留有理由的怀疑与经验判断；建议应落到对象、最小动作、可行性、交付物、建议岗位、时间、衡量与调整条件。活动策划连接真实节点、目标人群、商品/渠道、资源与承接；有取舍时讲推荐理由，需业务决定的事保留选项、影响与所缺关键信息。不能用空泛的持续关注/优化策略代替分析，也不把建议写成已执行。

具体方法与已加载的data-storytelling、modern-web-guidance、humanizer-zh编辑原则见METHOD第六节。交互为理解服务；重点图表与结论默认可见，明细按需展开。图表不能过大、文字不能复读数字，也不能只剩漂亮空壳。

## 工作完成的判据

先完成文件与自查，然后在可用浏览器中检查1440px和390px、浅暗主题、图表切换、展开、键盘、打印和下载后重开，并按本次读者目标检查视觉层级、图表大小和文字密度；历史范本仅作参考。无浏览器能力时写明未验，不能虚报。仅工具执行成功或文件存在不等于质量通过。具体可执行的测量与下载核验步骤见 `references/verification.md`；任何验收都绑定被验文件 SHA，修改后重新验受影响部分，不能把改前 SHA 的通过当成当前稿通过。

真实学习回执须写已读文件SHA、对新旧方法的理解、被替换的旧文件及其备份、生成文件SHA、实际完成/未完成的检查。持久记忆只保存本方法入口和经确认的业务事实；不把本期推断、建议效果或失败稿结论写成长期事实。
