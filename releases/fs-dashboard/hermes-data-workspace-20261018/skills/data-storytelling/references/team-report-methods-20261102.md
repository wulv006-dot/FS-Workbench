# 团队经营报告取数与分析规范

版本：1.2　更新日期：2026年11月11日（订单邮箱导出补充；原月报实例仍为11月2日）
适用：各品类游戏的日报、周报、月报与经营问题分析；供业务同事及Business团队共享知识库使用。  
维护原则：共用分析方法保持一致，各游戏的商品、成本、定价规则和工具支持范围分别核实。

## 1 先知道这份规范要帮助你做什么

经营报告首先要回答一个业务问题：现在最值得抓的是什么，为什么，先做什么，哪些事情暂时不值得投入。数据是判断的依据，报告的目的不是把后台字段全部搬出来。

完整工作顺序是：明确要判断的问题和比较窗口，先取得销售、订单、采购毛利及主要获客数据，找出影响最大的变化，再围绕两三项主要矛盾补数，最后给出有主次的判断和行动。小额差异、少量缺项或广告归因尚在回补，不应让整份报告退回“无法判断”。只有会改变结论方向、问题排序、关键金额或行动风险的差异，才继续追查。

这份文档同时说明三件事：人在哪里看数据，已接入的工具怎样调用，以及这次月报实际怎样取得数据。它们不是同一层入口。

### 使用前选择你的工作环境

**用户最新约定：FS是Hermes原生对话的承载窗口。** Hermes依靠自己的记忆、技能和实际工具取数、计算、判断及组织回答，FS如实显示其返回内容，不二次改写或强套模板。本规范记录的旧FS接口、工具范围和上下文装配是当前路径示例，不是Hermes永久的能力上限；新入口以实际工具说明和用户授权为准。此为改造目标，不能据此宣称已接通。验收应核同一身份下的记忆、工具能力、对话连续性与内容呈现；不要求不同模型采样逐字相同。

| 你所在的环境 | 可以怎样工作 | 需要注意什么 |
|---|---|---|
| 有自己权限的FS、Admin、Order后台 | 按本文件的界面路径筛选、查看和导出 | 使用自己的已授权身份，记录筛选与日期 |
| 已接入FS工具的Hermes或其他助手 | 调用本会话实际可见的只读工具 | 先看工具schema、支持的游戏和任务范围 |
| 只有Business共享文档的ChatGPT会话 | 读规范和用户提供的脱敏文件，进行计算与分析 | 上传规范不会自动接通FS，也不会获得后台权限 |
| 已有授权的项目维护工作站 | 复用现有服务、档案和适配器 | 服务器内部地址不能直接当成同事电脑或云端会话的地址 |

如果Business会话没有FS连接器，应明确缺少哪条数据通道，改用同事导出的数据或管理员已配置的只读集成。不能假装访问了`127.0.0.1`，也不能把一段工具名当成已经执行的调用。

## 2 日报周报月报分别判断什么

### 日报关注异常和今天的动作

默认以北京时间昨日完整日为主，比较前一日及上周同星期；当日数据只能称“截至取数时刻”。先回答销售和订单发生了什么，主要落在哪款游戏、哪个地区、商品或渠道，是否需要今天处理。

日报宜突出一至三项变化：例如高金额未完成单增加、某地区购买型广告回报下降、核心商品缺货、促销后的实际订单贡献变化。不是每天都要把所有模块写一遍。对昨日已经安排的动作，要区分建议、实际执行和已看到的结果。

### 周报关注趋势和资源调整

使用明确的连续七天或团队规定的自然周，与前一等长周期比较。把单日波动放回周内节奏，解释哪些变化持续，哪些只是星期结构、活动节点或归因回补。

周报应能支持资源取舍：保留哪些有效单元，先修哪个问题，哪些市场可以小范围验证，哪些投入应暂缓扩张。价格、广告、内容、商品和履约的变化需要放在同一条经营链上理解。

### 月报先全盘再分组再拆游戏

先看全盘销售、采购毛利、订单、客单和新增需求，再说明增长或下降由哪些业务贡献。接着拆团队定义的品类组和重点游戏，最后给下一月的投入方向与验收方法。

完整月环比说明规模变化，但不能掩盖月底已经转弱。例如新品9月只经营了几天，10月完整月增长很大，并不证明月底仍在增长。因此月报还应看月内周趋势或首尾可比窗口。分组之外的游戏保留在全盘，不能把几个重点组称作全部业务。

### 问题分析围绕决策组织

用户问“是不是价格太高”，报告就应直接回答价格更可能影响哪一环，以及是否值得优先调价。不要把这类问题写成没有主判断的全字段盘点。

优先检查：购买需求是否变化，获客量和质量是否变化，进站后的商品与价格承接是否变化，采购与履约是否限制成交，客户和套餐结构是否变化。允许给出“我更倾向于先处理获客效率”的工作判断，不需要先证明精确的因果比例。

## 3 应覆盖的经营视角

下表是检查视角，不是每份报告都必须等长展开的目录。内部覆盖全面，前台集中呈现重点。

| 视角 | 要回答的问题 | 关键数据 |
|---|---|---|
| 销售与规模 | 少在订单量、每单金额，还是业务组合 | 付款销售、订单、客单、日周趋势、增量贡献 |
| 利润与成本 | 增长有没有留下利润，新增业务利润是否变薄 | Order发货销售与采购、采购毛利、毛利率、必要时同批实际成本 |
| 商品与平台 | 哪些商品、套餐、交付数量或平台变化最大 | Coins、Items等结构、SKU、实际交付量、供给和可售性 |
| 国家语言币种设备 | 哪里有需求，承接是否匹配 | 国家销售、下单设备、实际页面语言、付款币种、落地版本 |
| 广告 | 拿量还是成交效率变差，钱花在哪 | 费用、曝光、点击、CTR、CPC、转化、CPA、ROAS、实际地域 |
| SEO与自然流量 | 搜索需求、排名、点击和自然入口分别怎样变化 | GSC曝光点击排名、查询和页面；GA4自然入口及购买事件 |
| 优惠与价格 | 客户实际少付多少，促销后还有多少贡献 | 实际优惠USD、金额加权让利、新老客、礼包赠送、可比竞品 |
| 客户与复购 | 新客有没有价值，既有客群是否走弱 | 原生新客标记及销售、客单、成熟同批客户后续购买 |
| 履约支付售后 | 是否存在会影响成交和后续价值的阻塞 | 未完成金额与账龄、交付、问题单、退款、拒付、真实支付失败 |
| 需求与游戏节点 | 版本和活动是否改变购买需求 | 官方公告、活动生效与结束、商品需求及竞品变化 |
| 目标与前次动作 | 该调整资源了吗，之前的动作有效吗 | 有效目标版本、实际执行记录、执行前后窗口、复查结果 |

国家、语言、币种和设备是不同维度。英国订单不自动等于English UK页面或GBP付款；手机下单不等于FC的PC游戏平台。优惠码的推广分类也不等于网站归属或因果获客渠道。

## 4 数据选择的共用基准

### 4.1 销售订单客户优先Admin原生统计

付款销售、付款订单和原生客户指标优先取Admin经营汇总。同字段Admin没有而Order有时，使用Order补缺并注明来源，不因小范围差异拒绝一切已有数据。

ES导出和订单明细主要解释结构。它们不天然等于原生经营总盘，不能因为一份明细总额不同，就直接改写原生总盘或按比例缩放明细凑平。

看板已付款主统计保留付款记录，退款另列。逐笔接口、ES原状态和特定客户分析可能采用不同的付费投影，应按对应合同处理，不能给所有来源统一套“退款全部删除”或“退款全部保留”。

### 4.2 主采购毛利使用Order发货统计

现行主口径是Order“统计管理→发货统计”：在所选日期时间、游戏、网站及原筛选下，使用同一响应中的人民币销售总额减采购总额。

分游戏毛利率采用该行原值；全局毛利率使用总毛利除以总销售，不平均各游戏或各日的百分比。它仍可能包含部分已发货退款、争议、欺诈或问题记录，不称净利润。

逐单实际成本能力保留，用于某批广告订单、客户或商品需要进一步核贡献时；它不自动替换当前主展示口径。旧文档中的“USD销售乘参考利润率”和逐单主毛利方案，不能覆盖2026年10月30日的现行主口径。

### 4.3 先核范围再比较

每个关键数至少保留：来源系统、游戏、网站、日期、时间字段与时区、状态范围、币种和单位、采集时间、覆盖状态。给读者展示必要信息即可，不必把全部元数据堆在正文前面。

优先复用同窗口、同范围的现有完整档案。选择档案时先匹配问题所需的日期和筛选，再选择相应版本，不能把整个目录里最新的文件当成所需数据。

“来源数据截止时间”“采集时间”“报告生成时间”分别记录。HTTP200、工具名字存在、源文件版本和模型真实调用成功，是不同证据。

### 4.4 缺项不记零

有效零值保留；缺失、未回补、读取失败、输出截断分别标明。工具返回`content_index`或`next_offset`时，先判断是否只是输出没有展开，不要立即认定上游缺数据。

有可用核心数据时继续给方向性判断。只有缺项会改变某项具体判断时，限制该项判断，不把整份报告停在取数上。

## 5 常用取数路径和工具

下文用`<FS_BASE>`表示团队实际已授权的FS地址。本项目当前维护实例为`https://47.85.224.112`；团队成员应使用管理员提供的正式入口及自己的权限。

逻辑工具名如`fc.query_discount_analysis`，在当前FS研究工具注册中对应`mcp__fcro__fc_query_discount_analysis`。其他环境可能使用不同外层名称，以会话实际工具列表和schema为准。

### R1 先查能力目录与已有证据

Hermes先用`fc.get_data_catalog`读取任务可用数据和定义；用`fc.read_skill`读取已审阅方法。已有证据可用`fc.read_evidence`按证据ID和JSON Pointer继续展开；历史判断和动作分别看`fc.read_history`、`fc.query_action_history`。

```json
{}
```

以上为`fc.get_data_catalog`参数。

```json
{"topic":"methods"}
```

以上为`fc.read_skill`参数。目录反映能力或任务范围，不保证每个来源在本次查询中都有数据。先利用与问题相关的证据，不为凑齐目录而读完全部历史。

### R2 销售订单客户与总体结构

人工入口：FS“全局分析/经营分析”选择网站、游戏、时间，或Admin原生经营统计页。保留当前筛选回显。

Hermes工具：`fc.query_native_statistics`，可用注册profile受本次任务冻结目录约束。

```json
{"profile":"D4","start":"2026-10-01","end":"2026-10-31"}
```

日期示例为历史完整月，不是运行时默认日期。该工具没有`profit_site`参数，不要擅自塞入其他入口的字段；返回数据的实际网站与利润来源需要分别查看。

底层Admin原生汇总端点：

```text
/admin/order.Order/orderStaticsDetailByEs
```

本次月报使用现役`admin_summary.collect(request, game, start, end)`，通过`summary_bridge.dc_request`进入服务器已有HMAC代理。全站FC示例筛选为`pay_status=1`、`game=1327`、`site=""`、完整起止时间；`country_code`、`client`、`product_type`等保持任务需要的筛选。

服务器内部主代理为`http://127.0.0.1:8912`，备用8911，容器桥8913。它们不是Business云端或同事电脑的可直连地址，也不包含可共享凭据。旧Admin模拟登录8767已退役，不按旧教程恢复BATOKEN、验证码或动态码。

### R3 指定网站的主销售与发货采购毛利

人工入口：Order“统计管理→发货统计”，源页面端点：

```text
https://order.p2pah.cn/#/stats/admin_index/delivery.html
服务器读取的原生路径：/stats/admin_index/delivery.html
```

FS已认证聚合入口：

```text
<FS_BASE>/dashboard/fs-home/transactions/range.json
```

参数示例：

```text
mode=summary
profile=D4
start=2026-10-01
end=2026-10-31
grain=day
profit_site=all
profit_category=-1
profit_basis=shipping
```

`profit_site=all`为全部网站，`main`为主站；`profit_category=-1`为全部类目。必须按任务明确网站，不凭页面上的“MMOEXP”文字推定主站。该summary适配器会把日期包含的最后一日转成下一日00:00作为内部结束边界。

每日毛利曲线使用同一入口的`mode=profit-history`，保留相同游戏、网站、类目和`profit_basis=shipping`。服务器内部服务地址是`http://127.0.0.1:8931/range`，由现有已认证FS路由访问，业务同事不需要另建服务。

这层summary的强制刷新参数实际为`refresh=true`。其他页面或actual-profit层可能使用`refresh=1`；两者不能全局替换。一般读数不附强刷，先复用同范围档案和已有请求。

RS使用自己的`rs_site`、`rs_server`、`rs_category`，不能照搬非RS的`profit_site/profit_category`。服务器适配器分别为`rs_shipping.py`和`business_shipping.py`。

### R4 商品结构和指定单品

全游戏商品结构可从Admin/Order原生产品维度或`fc.query_es_order_structure`读取。全状态商品统计只作同源结构比较，不冒充已付款财务销售。

```json
{"profile":"D4","start":"2026-10-01","end":"2026-10-31","group_by":"product","status":"all"}
```

指定商品或模型使用`fc.query_product_orders`。当前支持已注册游戏的主站266；必须提供`product_id`或`model_id`之一，不能两者都给，也不能都不提供。

```json
{
  "profile":"FC27",
  "product_id":163329311,
  "start":"2026-10-01",
  "end":"2026-10-31",
  "max_pages":20
}
```

这里的PID是历史FC示例，只演示调用结构；运行前核实当前商品目录，其他游戏必须换成其真实Admin PID。直接PID查询不带`platform`；模型查询中，当前只有FC27允许平台筛选。单次日期最多31天，超过需要按合同分窗。

同一订单可能买多个商品。模型内整单USD必须去重，不能把每个SKU关联的整单金额相加当SKU收入；只有唯一核实的行金额才能称单品金额。分页或部分PID未完成时，模型合计仍不完整。

### R5 实际优惠和新老客让利

人工入口：Admin“订单管理→ES销售订单下载”。

```text
https://admin.p2pah.cn/#/admin/order/makeExcelByEs
底层导出：/admin/order.OrderExcelByEs/downloadsMake
```

Hermes优先使用`fc.query_discount_analysis`：

```json
{
  "profile":"D4",
  "start":"2026-10-01",
  "end":"2026-10-31",
  "group_by":"new_customer",
  "status":"all"
}
```

当前`group_by`可选`new_customer/type/day/channel`；`profile`可以是ALL或支持的准确游戏profile。一个查询窗口最多31天。切换分组复用同一文件集；有准确`ws_`证据档案时按当前schema复用`evidence_id`，不重复发起导出。

源列包含游戏、订单号、订单USD、原币实付、付款时间、原状态、新客标记、来源、国家、优惠类型、折扣比例和折扣金额。用户已确认“折扣金额”统一USD，不能再按GBP/EUR实付换汇一遍。

先保留全部原始状态，再选择本次问题的订单群体，去重后统计。`status=all`不是“全部都属于已实现净优惠”。新客标记订单的全部优惠，也不等于已核实的新客专属活动成本。

本次月报先复用`/var/lib/fc27-es-exports/`的完整月私有档案，通过`es_order_structure.archived_dataset`读取，去重并按状态选取。FC剔除43笔“验证·未通过”后，与Admin14,589单、$932,211.74核平。这个结果只说明该次FC群体，不能把“固定剔除43笔”或同名状态过滤写成所有游戏的永久规则。

### R5a 按站点、多游戏和日期导出订单用户邮箱

人工入口：已登录FS“数据分析工具”`/dashboard/data-tools/`。现行合同见[订单用户邮箱导出](../../../../../../knowledge/order-email-export.md)；UI/API源码`158ddab93103695ef13917bbd5368bbbe5c7b179`、生产`nav-20261111T113950Z`，发布及真实验收见[专项记录](../../../../../../docs/planning/order-email-export-20261111.md)。这不是R5的ES优惠导出，也不是已注册的Hermes/MCP工具。

## 6 计算方法

### 6.1 销售与客户

```text
客单价 AOV = 同一付款销售额 ÷ 同一付款订单数
付费客户均额 ARPU = 同范围销售额 ÷ 已核付费客户数
环比变化 = (本期值 - 对照值) ÷ 对照值
销售增量贡献 = 本期该游戏销售 - 对照期该游戏销售
```

对照期为零时不计算无穷增长率，写新增业务或低基数。各游戏新客数不能相加当全站去重新客；原生新客标记也不自动等于GA4的newUsers。

销售可以拆成订单数乘客单价。这个算术关系不能直接推成“价格导致了多少下降”：客单价也受套餐、平台、地区和购买数量影响。Coins有实际交付K时，再区分购买量与单位成交价。

### 6.2 采购毛利与广告贡献

```text
采购毛利 CNY = 同一Order发货统计销售总额 - 采购总额
全局采购毛利率 = 总采购毛利 ÷ 同统计销售总额
广告ROAS = 平台归因价值 ÷ 广告费
采购覆盖压力线 ROAS ≈ 1 ÷ 采购毛利率小数
```

最后一条只是筛查：假设广告订单毛利结构接近对应平均值。不能因此称某国家的广告订单已经盈利或亏损。最终贡献应使用同批实际收入、采购成本及实际可归属广告费，并说明其他费用是否齐全。未齐全不称净利润。

不把Admin付款USD销售与另一批Order人民币成本直接相减；不拿今天采购单价倒算整月历史成本。

### 6.3 实际优惠

```text
D = 同群体实际记录优惠USD合计
N = 同群体已核折后订单USD合计
单均优惠 = D ÷ 同群体订单数
实际让利率 = D ÷ (N + D)
平均实付折数 = (1 - 实际让利率) × 10
```

最后两条要求已核实N为折后金额、D与其同币种同群体，且分母关系适用。缺少这个关系时先报实际优惠USD与单均优惠，继续给可支持的经营判断，不伪造折扣率。

“折扣比例”源列和券面30%不代替实际让利；不将USD订单减GBP/EUR实付推优惠；不重复汇总整单与商品行折扣；未用券不算实际让利；已扣优惠的销售不再减一次相同优惠。赠送金币与地区定价另作说明，不把名义赠品价值随意加到优惠USD。

### 6.4 获客指标

```text
CTR = 点击 ÷ 展示
CPC = 广告费 ÷ 点击
CPA = 广告费 ÷ 对应平台转化
点击转化率 = 对应转化 ÷ 点击
GSC总体CTR = 总点击 ÷ 总曝光
```

原生转化率可能使用互动而非点击作分母，保留原定义。总体比率按总量相除，不平均每日或每个系列的比率。平均排名优先取同范围原生结果；确需合并时按适当曝光权重，而不是简单平均页面名次。

Admin订单除以GA4映射会话，不自动构成真实购买转化率；平台转化不是后台真实订单数；新客占比不是复购率。

## 7 怎样从数据得出结论

先用同源结果定位量级，再用不同环节的证据解释方向。例如FC月底订单下降而客单价稳定，优先说明少在订单量；再拆曝光、点击、购买承接、地区和商品，不能直接认定价格过高。

每项主要判断都应自然包含：看到了什么，我如何判断，这对业务意味着什么，建议先做什么，以及下一次看什么来验证。如果存在重要替代解释，用一句话交代，并明确它会怎样改变行动。

不要把“非随机实验”“部分数据”“小额差异”当作不作判断的通用理由。也不要为了给判断而编造精确因果比例。判断可以鲜明，来源和确定程度要诚实。

### 价格问题的推理顺序

核实际价格暴露与优惠，再看同档竞品和成本，接着看订单、实际交付量与采购毛利，最后看获客投入和同批客户贡献。当前售价有竞争力，不等于广告获客已经盈利；采购毛利为正，也不等于首单扣除广告费后为正。

### 国家与语言的推理顺序

先看已有成交与客户价值，再看实际地域广告效率、自然需求和现有语言页面，给出优先深化、先修复、小范围验证或暂缓扩张的排序。国家有销售不证明客户使用某种语言；语言页存在也不证明收录、支付和客服整条链都已做好。

## 8 呈现与交付

开头先给主判断和两三项优先动作。需要比较或说明复杂结构时优先用图；简单短分析可直接用文字。图表不必固定每游戏四张，更不能用“图很多”代替推理。

图表注明期间、单位、比较对象和必要范围。不同量纲分开；金额、比例和百分比点不能混；内部涨红跌绿并配正负号；非零数要有可见图元，柱状比较通常从零起。指标切换同时更新标题、单位和说明。长表、原值与技术细节放附录或折叠区。

交付前先审经营判断与主次，再审逻辑和语言，然后看实际阅读效果，最后核会改变判断的数据问题。HTML需实际打开检查桌面、手机和关键交互；静态检查或HTTP200不能代替阅读验收。PPT检查图表、字体、版面与可编辑性，并如实说明是否做过原生程序放映。

行动写建议主责、时点和验证指标，不把建议写成已执行。月目标需要有效版本和相同范围，未取得时不给虚构完成率。

FC当前专属规则（2026-11-10）是100K购买、赠0、实交100K，PS／Xbox／PC独立售价与自身订单八日金额加权优惠，以及双20%；1000K以上赠送按让利观察，不扩大100K硬门槛。当前竞品指针为Lootbar主锚、ArabUT全球第二参考、ItemD2R辅助观察。这些不是D4、Aion2或其他品类的统一利润线；其他游戏复用分析过程和取数方法，业务护栏另查本游戏有效规则。历史示例中的105K和共价只解释原期间，不能恢复成当前规则。

## 11 失败或数据不齐时怎样推进

| 情况 | 下一步 |
|---|---|
| pending、202或排队 | 保存原请求或查询身份，按返回间隔查同一个请求，继续分析已可用部分 |
| 返回Top或分页索引 | 展开完整计算数据或明确子集，未显示不记零 |
| 401、403或明确权限拒绝 | 停止该来源的重复请求，说明影响，使用其他已有授权数据 |
| 400、字段错误或日期超限 | 核当前schema及端点边界，按合同改参数或分窗，不能当空数据 |
| 写入/导出结果未知 | 先核原任务、清单和回执，不换ID盲重发 |
| 局部数据缺失 | 限制受影响判断，保留整体经营方向，不等待所有字段齐全 |

当日数据按现役短TTL刷新，完整历史档案优先复用；归因或状态修订保留新版本。报告取数沿现有锁和队列，不为缩短等待清锁、关服务、降频或停用FC核心自动定价及其依赖。
