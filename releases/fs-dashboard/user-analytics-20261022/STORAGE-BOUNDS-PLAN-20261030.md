历史存量：用户分析目录约 48.69GB，其中备份约 35.76GB；Docker 约 22.67GB；D4 约 5.76GB；主 Hermes 约 4.29GB、钉钉 Hermes 约 2.11GB；系统日志约 2.69GB。目录包含关系不能重复相加。部分 deleted-open 为 RAM memfd，并非同量的磁盘泄漏。

根因有两层：每天整库复制没有跨日轮换；普通汇总计算会保存整份私有人群记录和事件正文。现有相同正文哈希去重已经存在，但名单发生少量变化时，仍会产生另一整份大正文。抓取分层、流式校验及上次清理已上线，均不能自动缩小已存在的大正文。

## 推荐代码与使用场景

| 使用场景 | 候选行为 | 保留的能力与代价 |
| --- | --- | --- |
| 看经营、用户及项目趋势 | 公共汇总仍保存原冻结结果；新模式保存版本、查询、有效配置和校验值，不保存整份成员正文 | 汇总读法、权限、指标和 ID 不变；计算公共指标仍需要临时分析事实，不能承诺生产内存已降低多少 |
| 打开名单、分页、搜索或导出 | 按原事实版本批量重建，校验与当时名单内容一致；一份内存缓存、120 秒空闲自动释放；串行重建 | 首次打开会更慢；不重新抓后台，不为每个客户逐个扫历史；不同在途响应仍可能持有各自结果，不能把一份缓存说成整个进程只会有一份对象 |
| 翻旧报告、核退款前的名单 | 旧 inline/member_ref 仍照读；新配方使用冻结 v1 算法和版本化事实重建 | 旧 ID、成员归属、历史配置和权限继续生效；不删旧事实、修订或名单，不做全库 TTL |
| 备份恢复 | 新备份完成 SQLite 一致性复制与 integrity_check 后，以真实只读 Store 打开，并读一份冻结私有快照，再生成 v2 manifest | 空库首次安装也兼容；同机备份仍不能覆盖整盘丢失，异地恢复尚未验证 |
| 每日备份保留 | 明确启用后，只轮换本模块已验证点；至少保留最新两个，且当天点已验证；固定点和 UNKNOWN 单独保留 | 只保留约两天普通直接回退能力，额外保留 10/29 已演练点、10/23 小基线及专项材料；较旧的直接回退日期会失去，需要明确批准 |

未来新增的完整名单正文不再持久化；新配方保留有限配置、覆盖窗口和必要 ES 订单标记，因此实际大小随场景变化，不能保证每份都是几 KB。500 客户虚构夹具：配方 4,881B、原私有正文 516,226B；这是夹具对比，不是生产节省比例。

冻结重建必须保留所需订单事实、修订、身份及冻结 v1 读取代码；不能另设任务把它们按 90 天直接删除。用户常看三个月，不等于首单、长期流失、未决账目和幂等事实只需三个月。

## 保留与故障规则

默认缺少新配置时，`snapshot_storage=full`、`backup_retention.enabled=false`，发布兼容读取代码本身不会开始删除。

建议随后明确启用：

```json
{
  "snapshot_storage": "recipe-v1",
  "backup_retention": {
    "enabled": true,
    "keep_verified": 2,
    "protected_dates": ["2026-10-23", "2026-10-29"]
  }
}
```

自动轮换只接受 v1/v2 本模块、`same_host_recovery_copy`、合法版本和匹配日期；v2 需恢复检查及未漂移文件身份，旧 v1 需独立校验/恢复 sidecar。未知格式、额外文件、链接、部分副本、特殊目录、未来日期和固定日期全部保护。不补写缺失的原 manifest 来伪造成功。

轮换在原 jobs.lock 内执行，以当时计划及文件元数据重新核对；首删前再次核保留恢复点。每文件有持久意图和结果，删除中断留 in_progress 回执；下一次停止并要求对账，不盲目续删。文件在验证后若发生变化，不以旧回执当当前成功。保留操作失败不会覆盖已成功的新备份回执。

## 施工顺序与批准边界

1. 提交候选 PR，完成受影响 CI 和独立复核。生产代码目标仅 `/opt/fs-hermes-fc/` 下的 `user_store.py`、`user_query.py`、`user_jobs.py`、新增 `user_replay_v1.py` 和 `user_backup_retention.py`；由原 CAS/journal/锁发布链适配精确三旧两新目标。发布适配尚需针对这五个目标准备和复核，不能直接运行旧全模块发布脚本。
2. 批准后先发布兼容读取层，配置保持旧模式；原发布器等待在途任务自然退出，受控加载 Range。然后按精确配置 CAS 启用新写法和轮换，并受控加载 Range，让其已有 Service 单例读取新配置。入口短暂重载；不停止在途任务，不改 timer/schema，不重启 FC、其他 Hermes、Admin 或 nginx，不改权限和原生镜像。其他读取进程是否需要加载，以实际调用链复核，不能用本地测试替代现场验收。
3. 对 10/30 原备份做流式 SHA、SQLite 检查和只读业务恢复验证，成功后新增小型 `restore-check.json` 回执；不复制另一份 12.64GB、不覆盖生产、不启动恢复库 worker。10/29 原 manifest 缺失仍保留原状，以已完成的独立演练回执保护。10/30 未验证前不自动退休旧恢复点。
4. 验收新模式汇总与名单/分页/导出、权限撤销、旧冻结报告、原自然任务及首次真实备份轮换，分别记录源码、CI、合并、发布及自然周期。关闭写入策略可回到 full，但代码只能回到仍认识 recipe-v1 的兼容版本；已经退休的旧日期副本不可由代码回滚找回。
5. 按单独批准的精确历史清单处理。此前清过的 10/24、25、26、28 不重复清；不触碰核心财务/UNKNOWN/原始凭证或唯一回执。

难度：名单冻结重建中等，涉及版本、权限及旧快照；备份轮换中等，涉及真实恢复和失败对账；按清单退休旧备份较低。生产大库物理缩容较高，需另做克隆/容量/读写窗口与回滚设计，本候选不执行。
