# 候选：用户分析分层抓取与未完成订单定向复核

候选尚未合并或部署。运行变更仅 user_jobs.py、user_source.py、user_store.py；不改共享分页器、定时器节奏、数据库结构、价格或其他项目。

## 使用场景与最小实现

| 场景 | 候选行为 | 保留的保障 |
| --- | --- | --- |
| 看今天、昨天的用户变化 | 沿原每15分钟机会完整重核今天截至实际运行时刻、昨天全日 | 不把今天未来时间算成完整，不降低原近期时效 |
| 已支付、验证、发货、申请退款中的旧订单 | 每站每轮最多200个ID，按游标循环定向复核 | 查询不筛掉已经完成/退款的返回记录，能发现状态转变 |
| 投诉、调查、问题单等其他旧未完成订单 | 另有最多200个ID名额，独立游标 | 不挤掉快速组；缺失仍保留，下次轮转再核 |
| 旧已完成订单后来退款、更正 | 原独立历史队列仍按完整付款日轮巡 | 24小时为到期阈值，非完成SLA；包括超过7日、超过3个月的旧数据，不永久冻结 |
| 同一天留下很多旧半日窗口 | 按网站＋北京时间付款日归并；完整覆盖才有全日水位，缺口请求整日补核 | 不删旧证明，不让新前缀把旧尾部伪装成刚核过 |
| 人工强制核验 | 原 sync --recheck 真正调用来源；tick --recheck 可明确重试被合同错误停止的定向项 | 不走旧结果缓存，不把一次失败改成成功 |

快速组仅按已观察的Admin状态11/21/31/32/33/34/80分配调度优先级；不改订单有效性或财务规则。101目前属于“已完成”低频组，但仍有历史轮巡；并不认定它永远不再变化。退款及原排除状态也保留普通历史纠错。

实际旧库中约990张已支付/验证/发货/退款申请订单分散在226个付款日；按这些日期整天重抓会接近重扫历史，因此定向路径只读取选定ID。选择器流式读取核心订单投影，内存只保留符合条件的ID/key映射，再选有限批次；不读取大体积snapshot_members，不新建索引、表或大缓存。核心扫描成本以隔离实测为准，不能把400个请求上限说成扫描全程只有400项内存。

## 定向补正与整窗替换分开

原 replace_window 会把整窗返回集中缺失的旧有效订单置为无效。定向查询不能使用该语义。新 correct_orders 复用原字段、金额、状态、测试单校验，先验证整批，再在一个事务中只更正已选择且确实返回的旧订单；缺失保留，partial明确记录，不生成完整日覆盖。

身份、网站、订单号/ID漂移及未来付款时间拒绝；不会悄悄迁移客户。实际变化保存原revision并增加版本，未变化不增加业务版本；旧快照继续按原版本读取。进度文件仅存小型游标与计数，成功complete/partial后推进；缺失不是删除，下一次轮转并非承诺下一tick。

定向请求最多400个ID且限制编码后的GET长度；原生已验1000条分页，这里400以内必须首包完整。首响应total超过选择数、过滤被忽略、首包不完整、重复/错误ID或顺序不符均拒绝，不允许扩大成多页扫描。共享pages原守护不动。

权限、参数、投影或身份合同错误停止该站定向自动重试，失败可见；429/5xx等临时错误允许后续自然轮接续。坏进度文件保留、不跑源；普通历史队列仍能继续。健康信息按站保留最差状态，只提供计数和错误码，不输出游标、ID或客户信息。
