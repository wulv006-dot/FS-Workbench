# Matchday 竞猜追踪兼容与开发计划 · 2026-10-23

## 当前完成范围

看板已支持商品促销、赛事竞猜配置，以及商品购买、竞猜参与、中奖奖励核销三种漏斗。新增可选桥接文件 analytics/matchday-adapter.js；原 Matchday 页面没有改动或重新发布。预置 /Fc-27/Matchday.html 是计划路径，不是已验证的正式入口。没有录入真实赛程，不能把旧示例赛事当作本周比赛。

## 运营如何使用

1. 在活动配置中选择赛事竞猜，填写固定活动 ID、负责人、版本、正式域名/路径和周期（UTC）。先保持草稿。
2. 录入赛事后台实际 match_id、名称、开赛与封盘时间。此处仅供数据分组，不控制真实封盘、赛果、发奖。
3. 导出 JSON 给开发，审核后同步 analytics-config.js 注册表和查询服务白名单；运行 node build-seo.mjs 更新镜像。仅在浏览器保存不会更新服务器。
4. 完成测试后再部署真实页埋点。之后新增活动沿同一流程，无须另建看板。换球员增加版本，不更换 activity_id；新赛事用新 match_id，旧数据不重写。
5. 参与分析默认 24 小时；中奖奖励核销单独选择 720 小时（30 天）窗口。实际券有效期不同，应由运营调整窗口，不能把尚未到期券当最终失败。

## 两条独立漏斗

| 漏斗 | 事件顺序 | 谁证明结果 |
|---|---|---|
| 参与 | prediction_match_view → prediction_started → prediction_accepted | 前两步是浏览器行为；第三步仅在服务端成功保存后产生 |
| 中奖后核销 | prediction_reward_eligible → prediction_reward_issued → prediction_coupon_redeemed | 全部由后端真实资格、到账和订单核销证明 |

参与漏斗以同一 activity_id + activity_visit_id + match_id 顺序归组。奖励漏斗以同一 activity_id + reward_journey_id + match_id 归组，分母是中奖资格，不是全部参加者。未中奖不能计作奖励流失。分享、点击 My Coupons 只是意向，不是到账、核销或支付。

## 最小接入位置

已核对本机 fc27_matchday_phase2_20261013/v5/source/dist/app.js 与 handoff/BACKEND-HANDOFF.md。原部署需网站开发重新确认，不能从本机文件推断线上已经接入。

- 赛事详情实际可见：调用桥接 track('prediction_match_view', matchId)。
- 首次选择比分或选项：track('prediction_started', matchId)。避免每次修改都视为新参赛。
- 当前 api.entry(current.id, …) 调用：请求附带 bridge.context(matchId)，后端校验后保存关联。客户端响应成功也不能代替可追溯的服务端 accepted 事件。
- api.entry 的会员身份、封盘时间、唯一 member_id + event_id/版本冲突保护继续沿旧合同。追踪参数不能决定奖励或折扣资格。
- 服务端确认赛果与资格后创建稳定 reward_journey_id，落库并与原 entry 关联。到账、核销重用该 ID；一个资格一次事件，撤销/补偿另记，不覆盖历史。
- capture 函数由原站现有 PostHog SDK 与同意管理提供；桥接不绕过同意、不初始化第二套账号系统。保存的事件只用匿名标识、商品/赛事 ID，不上传会员邮箱、token、比分表单全文。

## 后端必须补齐

| 事项 | 具体责任与验收 |
|---|---|
| 登录及参赛 | MMOEXP 既有会话或短期服务器凭证；成功保存才上报 accepted；失败、封盘、重发不重复计数 |
| 赛果与发奖 | 真实权威赛果源和版本；资格与成功到账分开；发奖结果未知保留原操作 ID 对账，不能盲重发 |
| 优惠核销 | 订单实际应用券/码并按规则确认后上报 redeemed，使用不含原始券码的稳定引用；打开券页不算核销 |
| 真实购买 | 购物车、订单和支付回调保留活动及访问关联；支付成功服务端去重上报，退款另记 |
| 数据与权限 | 只读查询密钥存 FS 服务端秘密配置，原登录保护与角色权限；活动白名单、缓存、限流沿现有入口 |

## 分阶段推进

A：本次完成本地配置、漏斗算法、可选前端桥与合同测试。B：网站开发在测试环境接实际参赛保存、会员身份及赛程，核对成功/失败/重复/封盘四类。C：接权威赛果与真实券到账回读，再验核销订单；此阶段单独安排有额度和范围的真实业务验收。D：正式流量对照 PostHog、FS 和订单样本，检查移动端、跨日、渠道和版本。

正式上线前必须验证跨赛事不串漏斗、无中奖者不进入奖励分母、重复回调只算一次、未知写入可对账、测试事件与 production 隔离。已实现的测试只能证明算法与配置，不证明真实登录/发奖/支付成功。
