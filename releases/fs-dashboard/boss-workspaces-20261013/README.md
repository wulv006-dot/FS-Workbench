# 游戏监控台与经营管理台

将用户提供的两个工作台作为 FS 独立工作区，并按后续明确要求每天采集情报、更新经营目标分析。原包目标、负责人和图片保留；旧实际、历史判断不冒充当前结果。

| 入口 | 标题 | 副标题 |
|---|---|---|
| /dashboard/game-monitor/ | 游戏监控台 | 全球新游上线 · 版本赛季 · 开服节点一屏追踪 |
| /dashboard/management/ | 经营管理台 | 三组进度 · 健康度责任到人 · 目标沙盘与经营决策 |

游戏模块从配置的官方 HTTPS 白名单取文本，再以一次共享模型调用生成证据绑定的事件。发布时间与事件日期分离，只有明确日期、时间和时区才生成小时倒计时。来源拒绝、空壳和预算截断明确记录为覆盖缺口；原包资料只作为可切换历史资料。

经营模块每天读取 FS 目录及截至昨日完整日的项目实际，最多双并发，整体采集最多 420 秒。Admin MMOEXP 主站提供营收/订单，Order 同期间全站利润率仅用于估算利润。完成率、剩余日均需求和线性月末预测由确定性公式计算，再由一次模型调用生成定性建议；无数据不填零，不臆造原因。原 2026-10 目标/负责人保留，跨月明确过期，不自动迁移目标。沙盘草稿按原 FS 身份隔离在本机，不发布正式目标。

boss_daily.py 复用已发布共享 DailyReports.bounded_model、ai_advisor_model.request_model 和模型账本；不复制凭据或启动 FC 调度器。同工作区、同上海日期保留一个运行记录，重复 CLI 只回读原记录。模型未知结果不重发；明确无回执的 busy 在同次任务等待 20 秒后只再申请一次。采集失败保留上次结果，独立状态 JSON 显示本次失败。经营模型失败仍可发布标明 AI 失败的真实事实。

游戏每日 09:00，经营每日 09:30（服务器既有 Asia/Shanghai）。单位兼容现场 systemd 219、Python 3.9；Persistent=true，运行最多 600 秒。详见 [deploy/README.md](deploy/README.md)。安装沿用原 publisher 的窄范围扩展，只写三个源码、目标 JSON、四个单位，共八个首次安装目标；仅 daemon-reload，初次实际运行验收后再启用 timer。现有 FC 09:15 保持。

用户已明确授权放宽原模型日次数上限及人工解读费用；共享服务负责落实额度，保留单次 token、超时和跨进程并发限制。人工解读沿用服务端管理员校验、原请求/任务编号和 GET 跟进，未知结果不自动 POST。浏览器不持有模型密钥，原负责人姓名与客户/订单明细不发送给模型。模型输出不执行操作、不生成或写入售价。

现有 pr-fast 的 fs-boss-workspaces 组运行五组 Node 检查、20 项人工 AI schema 测试、游戏来源/日期契约、经营预测契约、执行器生命周期和八文件发布故障测试。所有测试为离线假来源/假模型；失败、空测试或必需 skip 均不通过。Windows 完整 dispatcher 的既有含换行文件名自检不兼容，Linux CI 须独立执行，不跳过该检查。

本目录不含现场业务数据、凭据或共享 Advisor 后端副本。前端发布在最终现场基线中保留 Advisor、原业务消费者和登录保护，通过原锁/CAS/备份机制新增两卡及旧监控跳转；旧静态数据保留作追溯。部署读回、真实角色/浏览器、实际模型回执和自然周期结果单独记录，源码或离线通过不等于上线验收。
