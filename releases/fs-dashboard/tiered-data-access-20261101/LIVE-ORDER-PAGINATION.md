# Live Admin orders: bounded pagination candidate

This is a local candidate, not a production deployment. It extends the existing authenticated live-orders route; it does not change FS permissions or enable a Hermes tool.

An authorized caller supplies `site_id`, `game_id`, `start`, and exclusive `end_exclusive` (Shanghai calendar days). Each request covers at most 28 days, starts no earlier than the existing 365-day boundary, and is limited to a configured site and game. When present, supply the returned opaque `next_cursor` on the next request with exactly the same scope and dates. A cursor is bound to the actor's current global grant, fields, and page size, and becomes invalid after process restart or permission/policy change. Each request fetches at most 20 records, 256 KiB, 10 seconds, through the existing single-in-flight admission. A sampled 50-row response exceeded 256 KiB; a 20-row request returned 135,608 bytes, without guaranteeing every future page fits. Retry 429 under the existing backoff; 409 means source changes or truncation were detected and the caller must restart that range.

Each response remains `status: partial`, `complete: false`, `semantics: live_non_snapshot`. Null `next_cursor` means the observed pagination reached its end, unless `limitation` says `page_limit_reached`; it does not prove a stable snapshot or complete customer history. Offset paging can miss a row if upstream mutations offset each other without changing total; no result should be called a complete snapshot. No historic-first claim follows from an absent earlier order or from being earliest in a selected range.

`live_order_consumer.iter_pages` is a bounded iterator for an existing authenticated caller: it splits a requested range into 28-day windows and follows cursors, with an explicit total page budget. The caller can save the last returned cursor and resume with `resume_cursor` using that cursor's original window and scope; a service restart or permission change invalidates it. When `customer_email` is supplied, the injected `fetch(query)` must send the query as a JSON POST body, never as URL parameters; otherwise it may use the existing GET route. It must call the authorized route and raise on non-success HTTP responses. The iterator neither provides identity nor connects Hermes. Exhausted budget, repeated cursor and upstream page limit raise errors instead of being called complete. The host has a separate 100,000-page guard per window; `page_limit_reached` is never reported as success.

Users with the existing private order permission receive `order_id`, `paid_at`, `status`, `pay_status`, and `customer_email` when available. Ordinary globally authorized viewers retain the existing non-private aggregate contract: `data` is empty. Continuation cursors contain keyed digests of up to 20 previous-page order IDs rather than the IDs themselves; these detect overlap with the immediately preceding page, not every possible change across a live scan. `customer_email` can be null and is not proof of a stable person across sites; the existing site-specific user identity rules remain authoritative. `pay_status` is raw source status; the existing exclusions/refund rules must be applied before classifying a purchase. A caller must not log customer emails or full response bodies.

The proposed exact-customer request is JSON POST to the same route, with `site_id`, `game_id`, `start`, `end_exclusive`, `customer_email`, and optionally `cursor`; unknown fields, non-JSON, oversized bodies, URL query parameters and absent or revoked private permission are rejected. Each returned row's source email must exactly equal the requested email or the entire page fails. Empty results and earlier range matches describe only the requested site/game/window; they do not prove lifetime-first status. No arbitrary SQL, URL or customer list is accepted.

Limited production read-only probes, 2026-11-02: Admin page 1 and page 2 returned one row each in descending order; both had nonempty email and empty uid. An `id <` source filter was not honored in a bounded probe, so this candidate does not rely on it. A synthetic nonexistent exact-email filter returned no matches, and a bounded positive email query returned a matching email. The current fixed internal Admin proxy uses GET to the upstream Admin interface but its inspected success/error log calls record only the path without the query. This does not prove how the upstream Admin server logs requests; verify that boundary before production use. The external FS endpoint accepts the email only in the body and does not include it in a URL. No full history, stable cross-site identity or lifetime-first status is proven.

Hermes is not wired: `hermes-server-unify-20261022/fs_readonly/__init__.py` currently fixes the caller to `wulv` and discards `**context`; it cannot safely be reused for a general employee's private query. `hermes-conversation-20261018/source/http/range_api.py` receives a verified actor for conversation calls, but the downstream worker/tool bridge must carry and verify that same run-bound actor/session before invoking the existing global private authorizer. The owner of those shared files must provide that binding; this candidate does not substitute a fixed user or new credential.

`source/range_api_live_pagination.patch` is a narrow integration proposal against the 2026-11-02 deployed route hash `e27607147abf0d92209f16984b780812184e329f9347b2fe98612ec05f5da9a4`; the companion fixture exercises that proposal. The live owner file can change independently and must be rebased with CAS/review before any release. The source-worker hash pin must match the delivered worker. No production configuration or service is modified by this candidate.
