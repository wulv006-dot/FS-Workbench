# Live Admin orders: bounded pagination candidate

This is a local candidate, not a production deployment. It extends the existing authenticated live-orders route; it does not change FS permissions or enable a Hermes tool.

An authorized caller supplies `site_id`, `game_id`, `start`, and exclusive `end_exclusive` (Shanghai calendar days). Each request covers at most 28 days, starts no earlier than the existing 365-day boundary, and is limited to a configured site and game. When present, supply the returned opaque `next_cursor` on the next request with exactly the same scope and dates. A cursor is bound to the actor's current global grant, fields, and page size, and becomes invalid after process restart or permission/policy change. Each request fetches at most 50 records, 256 KiB, 10 seconds, through the existing single-in-flight admission. Retry 429 under the existing backoff; 409 means source changes or truncation were detected and the caller must restart that range.

Each response remains `status: partial`, `complete: false`, `semantics: live_non_snapshot`. Null `next_cursor` means the observed pagination reached its end, unless `limitation` says `page_limit_reached`; it does not prove a stable snapshot or complete customer history. Offset paging can miss a row if upstream mutations offset each other without changing total; no result should be called a complete snapshot. No historic-first claim follows from an absent earlier order or from being earliest in a selected range.

`live_order_consumer.iter_pages` is a bounded iterator for an existing authenticated caller: it splits a requested range into 28-day windows and follows cursors, with an explicit total page budget. The injected `fetch(query)` must call the authorized route and raise on non-success HTTP responses; the iterator neither provides identity nor connects Hermes. Exhausted budget, repeated cursor and upstream page limit raise errors instead of being called complete.

Users with the existing private order permission receive `order_id`, `paid_at`, `status`, `pay_status`, and `customer_email` when available. Ordinary globally authorized viewers retain the existing non-private aggregate contract: `data` is empty. Continuation cursors contain a keyed digest rather than the previous order ID. `customer_email` can be null and is not proof of a stable person across sites; the existing site-specific user identity rules remain authoritative. `pay_status` is raw source status; the existing exclusions/refund rules must be applied before classifying a purchase. A caller must not log customer emails or full response bodies.

Limited production read-only probes, 2026-11-02: Admin page 1 and page 2 returned one row each in descending order; both had nonempty email and empty uid. An `id <` source filter was not honored in a bounded probe, so this candidate does not rely on it. A synthetic nonexistent exact-email filter returned no matches, and a bounded positive email query returned a matching email; this evidence does not cover full history or establish a new live email-filter API. It must not be passed through a URL until proxy logging and private authorization have been reviewed.

`source/range_api_live_pagination.patch` is a narrow integration proposal against the 2026-11-02 deployed route hash `e27607147abf0d92209f16984b780812184e329f9347b2fe98612ec05f5da9a4`; the companion fixture exercises that proposal. The live owner file can change independently and must be rebased with CAS/review before any release. The source-worker hash pin must match the delivered worker. No production configuration or service is modified by this candidate.
