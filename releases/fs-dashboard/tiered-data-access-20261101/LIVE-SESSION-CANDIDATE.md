# Live session candidate — not release ready

The dedicated HTTP candidate validates existing FS sessions with the existing local login service and derives the subject from its response. It does not trust an incoming username header or add accounts, keys, roles, or a new user permission list. It reuses `user_runtime.authorize`, including the ordinary global `unified-business` view rule for `/dashboard/users/` and its existing private-detail rule; authorization is re-evaluated before queued source work and after fetching. Site/game are checked against the connected data configuration; the source worker is still restricted to site 266.

The previously added `site_authorizer` placeholder was stricter than the existing users contract and has been removed. Configured `sites` and `projects` are data scope, not individual permission grants. Ordinary users with the existing global view permission receive only `source_reported_total` and the number of rows observed on the bounded page; `data` is empty. Existing private permission is required to return individual order rows (`order_id`, `paid_at`, `status`). This categorizes the *per-order record*, not every timestamp or status value in an aggregate, as private. Existing `user_contract.aggregate_only` forbids order identifiers in public aggregates, while `user_query.detail` returns individual order bodies only via `private_snapshot`, which checks `user_runtime.authorize(..., private=True)`. Revocation during a fetch causes denial rather than returning rows. The fixture extracts and executes the actual existing `user_runtime.authorize` function with a synthetic IAM policy; no production session or data is used.

`deploy/live_orders.location.conf` is an insertion candidate, not a complete nginx configuration or release manifest. It forwards only the existing session cookie names to the private backend. The backend independently revalidates the session, and repeats validation before the queued upstream operation. `deploy/range_api.secure-live.patch` is a zero-context patch for the exact read-only 10:43 UTC production snapshot (before SHA-256 `8cb8df2375f68e912ae0adc16e91312f6778a10c43b1e450479783b059053dbe`); the expected resulting SHA-256 is `e27607147abf0d92209f16984b780812184e329f9347b2fe98612ec05f5da9a4`. In a local fixture Git required `-c core.autocrlf=false apply --unidiff-zero` to preserve those bytes; the default Windows setting changed line endings and produced a different hash. Pin the full before and after hashes and do not apply on drift. `tests/fixtures/range_api_secure_live.py` is a test fixture, not an owner-file replacement. Both require current-owner review and a fresh baseline before any release.

The old route, old nine-target manifest, and earlier CI do not validate this candidate. No production changes or source requests are performed by these fixtures.
