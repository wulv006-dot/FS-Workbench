# 万圣节活动容量与记录保留方案

当前建议：先减少公开配置的重复计算和静态文件下载，再做翻牌记录的短期保留。现有翻牌记录只有约85KB，立即清理几乎不能改善访问体验；缓存优化的收益更大。购买修复单独发布，不等本方案施工。

- 110个静态文件约15.5MiB，服务启动时已读入内存；当前runtime默认响应no-store。实际外层主站CDN/代理是否覆盖这些头，尚需发布时逐项读回。
- 原只读进程快照：活动管理服务约74MiB，公开runtime约54MiB。这是观察时点，不是内存上限。

这说明本机上重复投影整份配置会排队；它不代表生产服务器只能承受25人，也不能据此承诺千人同时访问。正常浏览还包括停留、缓存命中、图片、上游网络等不同负载。

## 第一阶段：最小缓存候选

1. 对带**完全匹配内容hash版本号**的JS/CSS/图片/字体启用长期immutable缓存；未带正确版本的资源使用ETag重新验证。HTML、动态catalog、用户状态和交易接口不套这种缓存。
2. 对已脱敏的公开配置增加最多2秒的进程内缓存候选。发布文件或价格文件变更立即失效，且不得跨过任何仍显示价格的到期时刻。抽卡、原收据核验、加购claim和幂等判断仍读取当前配置。
3. 隔离验证冷/暖配置、发布变更、价格临界到期、过期资源版本及代表性并发。与本表同样负载比较后再定参数，不能只看HTTP200。
4. 如确需高频请求保护，先在隔离环境验证明确的全局准入上限；不能把回环IP当成访客身份，也不能随意信任X-Forwarded-For。超限必须在业务分配ID/写UNKNOWN前拒绝并带重试提示。

候选参数默认关闭。生产启用的新缓存/准入参数与对应回退命令需具体列明；不混入购买修复发布，不改变IP白名单、账号权限或优惠规则。

## 第二阶段：保留与清理

完整普通翻牌结果建议保留**当前美东自然日和之前两日**。例如美东10月29日，保留10月27日至29日完整内容；更早记录先列归档候选。每天前端生成新UUID，并不等于后台旧UUID可以直接删除。

目前服务端旧UUID文件若被删除，同一个旧请求可能再次进入随机抽取。因此归档前要先实现服务端到期拒绝，并为原UUID留下最小的“已过期”记录。这个小记录用于拒绝旧请求重新抽卡，不是继续保存完整商品明细，也不是永久识别某个人。

保护规则：

- UNKNOWN、文件损坏、未决操作以及任何无法完整核对的记录不进入普通清理。
- 加购/支付意图/操作幂等记录单独保留，不随每日翻牌清理。
- 只处理活动拥有的精确目录；拒绝符号链接、非普通文件、硬链接异常和路径越界。
- 先输出只读计划，逐记录绑定原UUID、SHA、时间和理由；真正归档前再次核对，发生变化就跳过。
- 先生成可恢复的压缩归档和校验，再原子替换成最小过期记录。恢复时不能把已过期身份重新变成可抽身份。
- 本轮不执行生产归档，不永久删除原记录；最小记录和归档本身的最终清除期限要另行批准，不能因活动结束或后续延期就盲删。

本次dry-run候选只有6份/3540字节。优先验证“不重新抽取、不重复操作、未知不丢”，节省空间是次要收益。

## 回退与验收

缓存参数回到关闭值后，应立即恢复原no-store/逐次投影行为；代码走原发布器单独候选、CI和独立复查。清理先保持dry-run，没有生产应用步骤；后续即使批准归档，也必须保存完整回执和恢复文件。

验收分别记录源码测试、隔离负载、实际响应头和自然运行效果。不得用本机负载替代生产承载验收，也不进行未经批准的生产压力测试。
