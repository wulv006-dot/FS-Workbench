## 行为变化

V6 原运行时根据完整 curve_key 识别变更平台，100K不变而大档改变仍识别为变更，不机械联动 PS/XBOX。原操作只凭绑定同一 ID 的完整目录、传播及必要 Order 投影回执收尾，账本冻结 site266 实际完整读回；UNKNOWN/PARTIAL 沿原 ID 只读对账。只有有据未发送才取消并释放租约。旧标量 Order+Admin 收尾流程保留。

原生当前完整读回及 V6 执行财务复验尚未接通：V6 NO_CHANGE 保持 PUBLIC_PENDING；`verify_quote(..., for_execution=True)` 明确拒绝缺少新验证器的 V6 请求。合成测试中注入证明可以验证协调行为，不构成真实执行能力或激活。

独立复核指出接收商品高档赠币漂移时，原代码会先 POST 再返回 PARTIAL。主控复现同一反例：ALL/proof不变，site266的1000K赠币30→300，新增测试先失败，实际 PARTIAL。修复在读取全部接收商品后、建立 send_intent 前复用 `curve_specs_match`，逐接收商品比较数量/赠币/折扣；身份沿 `read_row` 原合同核验。漂移返回 NOT_SENT / FAILED_BEFORE_WRITE，POST=0、Order投影=0，不生成确认曲线；原事后校验与只读恢复保留。

模拟桥失败也已定位：`78627c8` 增加 engine 的数量观察选择及不支持来源拒绝，但 `pricing_simulation.py` 仍锁旧哈希。只将 ENGINE_SHA 同步为当前候选 `ab93ebee23751e04f7950c9a165881bd3f15ac839aed72a3de5d9b72eeb29f16`；financial 和冻结历史 SHA 不变，本地与远端版本不匹配仍拒绝。该桥必须与对应 engine 同批候选装配，不能单独推送旧线上引擎。
