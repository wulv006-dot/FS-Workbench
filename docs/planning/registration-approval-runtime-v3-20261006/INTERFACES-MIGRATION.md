# Interface and migration contract

Public `/__auth/access/` is separate from homepage work. Existing nginx strips `/__auth/`; portal sees `/access/`. Web assets load the public API prefix. The bridge serves only four fixed static filenames. GET bootstrap sets a signed-independent random candidate session and returns CSRF. POST register creates pending user/request/audit with no dashboard activation. Register asks username/password/team/application purpose only.

API reads: GET `/api/bootstrap`, `/api/requests?after=`, `/api/audit?after=`. Writes: POST `/api/register`, `/api/login`, `/api/native-login`, `/api/apply`, `/api/logout`, `/api/decision`, `/api/revoke`; JSON exact fields and Origin+CSRF are mandatory. Request body max4096, duplicate JSON keys reject; decisions carry request id/version/action/reason. Bootstrap itself is not authorization; native identity must come from signed token and current complete membership source. Four current native admins can approve/reject/revoke; new registered users cannot become admin through any route.

Native original signature secret, cookie configuration and GROUPS remain service-local; no secret rotation/membership import or name-based conversion. Existing native account names reserve the case-insensitive registration namespace. Registered identity is `reg:<canonical UUID>`, never username; same-name collision after registration also blocks verification. No fc27sess migration or trust. Current policy is read from native `_fs_policy.ADMINS`, not a three-name snapshot.

New store: AUTH_DATA_DIR/registration-approval/registration.sqlite3 (directory0700, DB0600, current service UID on POSIX). Namespace lock is in that private directory. Schema3 is exact frozen users/requests/sessions/audit/limits plus native_revocations; pending/read-only/rejected/revoked states only. Password PBKDF2-SHA256 600000 rounds with random128-bit salt; session tokens stored as SHA256, expiry43200s and user epoch checked. Audit/request snapshots are append-only by schema triggers. User data is not exported to deliverables. Fresh DB contains no user/admin; existing native accounts remain in native GROUPS and their original policy.

v2 normal runtime requires exact schema3 with a retained external checkpoint; no automatic schema2 migration, missing DB recreation or recovery. A schema2-to3 change needs a separately reviewed migration retaining ledger provenance and witness. Unknown extra or changed tables/triggers/indexes/constraints reject without automatic rebuild. v5 temporary candidate DB is not an import source for production. Native memberships are evaluated on each verification; no read grant is stored for existing native users. New readonly decision bumps epoch, expiry/epoch invalidate revoked sessions; native explicit logout records signed-token digest/expiry atomically with candidate session deletion. See RECOVERY.md for explicit first initialization and backup/rollback rules.

Consumer trust boundary: current auth verify must provide X-Auth-User/X-Auth-Groups/X-Auth-Role; nginx captures and forcibly overwrites downstream headers. FC equivalent aliases may be emitted for compatibility only, not independent identity. Taskboard UUID/viewer path requires verified readonly; native admin requires exact current policy plus verified admin. Existing native taskboard editor state is preserved behind original global authorization, not used to grant any new registration write.

Desktop acceptance covers registration, existing portal login, pending state, admin approval, approved read dashboards, admin writes, revoke/logout/restart, denial and recovery. Mobile/390px checks are optional historic evidence only, never a blocking gate. No homepage card reorganization or analytics frontend dependency is introduced.
