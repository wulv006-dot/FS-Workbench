# Controlled initialization, recovery, backups and code rollback

Normal restart is open-existing-only. First init is a separate reviewed operator action, only for never-initialized registration root AND witness directory, with production writer ownership and explicit action-time approval. Do not call first init as a convenience when build fails. No generic reset, delete, recreate, restore-backup or repair API is provided.

Supported live pair: AUTH_DATA_DIR/registration-approval/registration.sqlite3 plus AUTH_DATA_DIR/.registration-checkpoint/state.json, alongside namespace.lock. DB exact schema3, witness status ready, generation and digest must agree. Deployment backups of code may omit user DB; storage backups must be obtained under the same namespace fence with a ready checkpoint and include the matching latest witness. Code rollback preserves this pair unchanged. Backup version identifiers must include generation, digest and provenance; time labels alone cannot prove latest state.

Missing/corrupt/rolled-back DB or witness: deny service startup/access. Preserve remaining DB, journal and witness bytes; do not delete evidence or retry first init. Identify a complete latest storage pair and ledger provenance through a reviewed recovery plan. Restoring an older DB or both old DB/witness can restore revoked qualifications and is prohibited. If latest revocations cannot be proved, keep access denied; any deliberate replacement of identity/session trust requires separate user-approved policy and action-time review, not an implementation fallback.

Pending checkpoint after interruption: keep denied. An operator must inspect exact schema, SQLite integrity, namespace exclusivity, checkpoint generation/digest and database logical digest locally (without exporting account/session records). If DB state exactly equals the pending after-state, a reviewed recovery may finalize that checkpoint; if it reflects an earlier/uncommitted state, it cannot be treated as current without proving retained latest revocations. v2 deliberately ships no automatic finalize helper. Record the recovery decision, exact hashes/generation and resulting denylist/epoch preservation. Do not edit witness digest to match any convenient backup.

SQLite's ordinary hot-journal recovery may restore the pre-commit database; the pending witness still blocks authentication. An interrupted operation may have committed even if client received503; UI must re-fetch after controlled recovery and never retry an unknown decision blindly. Duplicate decisions remain version-checked, and revoked sessions remain unusable.

This protocol does not prevent privileged external paired overwrite or require a new persistent secret. Its enforcement boundary is the namespace-fenced runtime and approved release/recovery workflow. Production root/SSH writes remain outside complete software enforcement; do not claim absolute anti-rollback. No production storage, backups or sessions were accessed during these tests.
