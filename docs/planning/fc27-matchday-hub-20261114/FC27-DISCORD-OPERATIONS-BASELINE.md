# FC27 Discord 内容驱动增长与转化项目方案

> 项目：MMOEXP FC27 Discord 运营机器人集群<br>
> 版本：v1.0｜日期：2026-11-14<br>
> 面向：美国、英国的足球迷与 FC 玩家<br>
> 部署背景：187 服务器及现有机器人体系<br>
> 文档性质：运营策略、产品需求及实施验收基线，不代表以下规划已经上线。

## 1. 项目目标与核心判断

以现实足球赛事为入口，通过公共频道共同看球、赛事讨论、战术解读和 FC27 阵容内容建立持续参与，再用明确标注的 MMOEXP 服务专区承接用户主动查询、福利领取与购买需求。

**用户最新修正：不能让“身份选择 → 定向私密推送”成为主体验。体育社区的核心是大家在同一场比赛下交流。身份仅服务自主订阅提醒、个性化入口和偏好，不把讨论拆散到私信。运营尽量自动化，由 Hermes 每日筛选话题和重点比赛，用户不承担日常排期与选题工作。Hermes 接通及自动编排属于待开发/待验能力，不是既有事实。**

**定位：Matchday → Match Squad。一起看真实足球，把比赛灵感带进 FC27。**

不建设一个“什么足球新闻都转发，最后贴金币广告”的群。优先服务足球迷与 FC 玩家的交集，以真实赛事带来话题，以游戏内容产生持续价值，以可靠服务完成转化。

### 1.1 成功路径

```text
站外原创赛事内容 / 创作者合作
  → 带来源标记的 Discord 邀请
  → 进入公共比赛频道与其他球迷一起讨论
  → 自选球队、游戏平台和提醒偏好
  → 参加赛事讨论 / 获取阵容模板
  → 自愿进入 FC27 工具与 MMOEXP 服务专区
  → 主动查价 / 领取符合条件的福利
  → 网站下单
  → 私密订单服务、复购与社区贡献
```

### 1.2 首期边界

- 试运行以每周两场重点赛事为初始容量，优先英超及关注度较高的欧洲赛事，不追求全赛事覆盖；由 Hermes 自动推荐与排期，而非要求用户逐场制定。
- 先跑通一条完整链路，再增加机器人、频道和奖励类型。
- 公共交流区以内容与服务为主，商业区明确标识品牌和用途。
- 不批量拉陌生 PS 用户进组，不抓取账号后群发邀请，不用机器人伪装真人购买或制造虚假热度。
- 本文不授权部署、发券、付费、对外发消息或修改生产环境。

## 2. 当前基础：已知能力与待验事项

最新 PR [#1070](https://github.com/wulv006-dot/FS-Workbench/pull/1070) 已合并，不能再将相关工作描述成“仅文档”或“尚未合并的草稿”。

| Lucky Loot | 独立服务已有活动、报名、截止、抽取、领奖及管理员对账能力 | FC27 专用奖励、条款、预算及真实零支付验收 |

### 2.2 Smart Score 的明确边界

- 将其作为赛事事实与订阅底座，在外围做讨论、复盘及 FC 内容衔接，不假定可以修改或私有部署其源码。
- 已有测试包含合成消息与真实比赛。合成事件不能作为正式群实时性能证明。
- 测试记录显示 `/predict` 可提交私密 1X2 预测；**私密结果不能靠读取公共频道获取**。
- 公共 API、导出协议、授权范围、覆盖联赛及服务保障尚未确认。
- 未确认官方可用接口前，不承诺“猜中自动发券”，也不绕过私密结果读取限制。
- 已有集成以 Smart Score 为主，不重新搭建一套冲突的 OpenLigaDB/ESPN 比分推送。
- 现有外围触发应保留应用、服务器及频道白名单；要求包含比分；同场讨论触发冷却，完场可独立触发。

### 2.3 奖励现状不能直接套用

已有 Lucky Loot 测试券记录为 **5 美元、特定 game1367 商品范围、每邮箱一次、30 天有效**。这不是已经验证的 FC27 通用免费券，也不能据此向用户宣传 FC27 商品可零支付领取。

## 3. 社区结构与成员旅程

### 3.1 建议频道结构

尽量复用已有频道，不为“看起来丰富”大量新建空频道。

| 区域 | 频道 / 功能 | 用途 |
|---|---|---|
| 入门 | Start Here、Welcome、规则与偏好选择 | 一分钟内知道群提供什么、选择球队和平台 |
| 真实足球 | 公共 Matchday（只读）、公共 Match Chat / 单场讨论串 | 同一比赛的观众集中讨论，事实卡双向链接讨论；明确剧透提示 |
| FC27 内容 | News、SBC、阵容/球员讨论、OBJ & Packs | 从真实比赛延伸到游戏玩法与目标 |
| MMOEXP 服务区 | Coins、Players、Offers / Rewards | 明确商业属性，提供用户主动查询与领取入口 |
| 支持 | 私密工单或私密交互 | 订单查询、异常券及售后，不公开订单个人信息 |

现有 EasySBC 的旧分类频道应保留至迁移验证完成。OBJ & Packs 已创建不代表内容迁移完成，不应提前删除旧频道。

### 3.2 新成员一分钟入门

1. 选择兴趣：真实足球 / FC27 / 两者都喜欢。
2. 可选球队及平台：PS、Xbox、PC。
3. 自选通知：赛事、FC 新闻、SBC/Evo、活动；允许一键关闭。提醒指向同一个公共比赛讨论入口，不把每个人引入独立私密直播间。
4. 提供一个低门槛首次动作：参加讨论、提交阵容问题或使用一次工具。
5. 福利和营销通知单独解释，不强迫所有足球观众成为广告订阅者。

优先采用 Discord 原生 Community Onboarding、Server Guide、Scheduled Events、Forum、Polls 和 AutoMod，再用自有机器人补足流程。实际能否启用应检查服务器配置与权限。

### 3.3 共同观赛优先的体验要求

- 不选任何球队身份也能发现当日重点赛事及进入公共讨论。
- 每场重点比赛只建立一个主要讨论入口，避免按球队拆分到无人互动的小房间。
- Matchday 比分卡、提醒消息、复盘与 FC 阵容内容均链接同一场讨论。
- 用户自主订阅的提醒只是“比赛开始了，来这里一起聊”，不是把比赛过程搬到私人推送里。
- “直播/看球”在本方案指实时比分、文字赛事信息和共同讨论；不包含未经授权的视频直播或赛事转播。可提供合法观看渠道信息，但不能重播受保护内容。

## 4. 机器人分工与技术边界

### 4.0 Hermes：每日选题与编排层（待接入/待验）

目标是“系统每天自主运营，用户只处理真正需要决定的例外”，不是每天让用户审核一份排期表。

**每日自动流程：**
1. 从经确认允许使用的赛程源、官方新闻源及内容源读取当天与未来 48 小时材料。
2. 去重并识别延期、改期、过时新闻及不可靠传闻；事实不足不发布。
3. 根据公开赛事重要性、社区成员自选球队的汇总兴趣、英美可参与时段、FC 内容关联性及近期覆盖重复度排序。不得据聊天推断成员的消费能力。
4. 在配置容量内自动选出重点比赛，输出选中理由、来源、时间、共同讨论入口及备用方案；无足够质量素材可不发。
5. 自动编排预告、开赛提醒、关键节点、完场复盘和次日 Match to Squad 草案。比赛延期时同步修正计划。
6. 已在允许范围内的低风险、模板化内容可自动发布；不让用户每日逐条批准。
7. 记录运行结果、来源、成本及失败项，每周汇总给运营查看。

**建议规则，可配置而非声称已有：**
- 每日最多一篇综合选题摘要，重点赛事按初始周容量编排；没有赛事日可选择一条可信的 FC 实用内容或不发。
- 优先有真实事实和讨论价值的节点；低质量流言、纯重复和只为刷活跃的提问不进入队列。
- 一场比赛的消息使用统一事件 ID，改判、更正、重试不会重复建帖。
- 模型可协助排序及写作，最终赛程、比分和价格必须由各自确定性数据源核验。

**只升级真正的异常：**来源冲突且影响赛果、商品或券条款改变、预算将超限、疑似版权/违规、用户投诉、后台权限异常、奖励状态无法对账。普通抓取失败先按配置重试或跳过，不反复打扰用户。预算超限则暂停对应付费/发奖步骤，不自动加额。

**最低人工负担：**首次确认来源、预算、发布范围及规则；首轮抽样验收，稳定后每周看一次简报，仅对上述异常作决定。启动阶段可由运营角色临时值守，不默认用户本人每日到场。

### 4.1 Smart Score：事实层

负责赛事、比分和已验证的订阅功能。外围系统消费允许获取的消息或正式接口，保留原消息链接。

禁止：让大模型补造比分、伤停、首发、赛果或所谓实时数据。

### 4.2 DeepSeek 会话机器人：内容助理

负责：
- 根据已确认赛事事实提出一个值得讨论的问题。
- 汇总真实用户观点，生成简短赛后复盘。
- 将真实战术转为 FC 阵容搭建问题或内容草案。
- 回答知识库覆盖的问题，未知内容明确说明。

要求：
- 明确标识 AI，不冒充球迷、买家或管理员个人。
- 英语自然简短，可区分英式足球表达与美国新球迷解释需求。
- 不自行报价格、不保证优惠资格、不承诺订单或交付结果。
- 不通过多个机器人相互聊天来刷活跃。
- 无真实话题时保持安静，不为了“带节奏”制造发言。
- 工具故障时说明无法核验，不能用模型估计替代价格或库存。

### 4.2.1 英语主持人设与网感

建议人设名：**Matchday Host · AI**。像懂球、会接梗的看球搭子，不像新闻播报机，也不假装是有真实看球经历的人。面向年轻 Discord 用户，短句优先，少用品牌口号；网络用语适量，不为英美成员强行套口音。

可用于提示词的英文风格约束：

```text
You are Matchday Host, an openly identified AI football and FC community host.
Sound like a sharp, friendly match-thread regular: brief, playful, and specific.
Use verified match facts. React to real moments or real member questions.
One thought, at most one question. Let people talk; silence is fine.
Never pretend to be a human fan, a customer, or someone who watched footage.
No invented scores, injuries, prices, purchases, crowd reactions, or testimonials.
Banter about the play, not someone's identity. No slurs, harassment, or pile-ons.
Do not manufacture engagement, start bot-to-bot conversations, or push unsolicited offers.
```

短句示例仅为模板，涉及事件的句子须在事实源确认后使用：

| 场景 | 英文示例 | 使用边界 |
|---|---|---|
| 赛前 | “Lineups are in. Which matchup decides this one?” | 已有确认首发才发布 |
| 公共入口提醒 | “Kickoff soon. One match, one thread. See you in Match Chat ⚽” | 只发给自主订阅者或公共活动入口 |
| 确认进球 | “1–0. That changes the game. Push for another or protect the lead?” | 比分已确认；不要描述未核验的射门过程 |
| VAR 待定 | “Hold the celebrations. VAR check in progress.” | 来源明确确认检查中 |
| VAR 更正 | “Update: goal ruled out. Back to 0–0.” | 及时更正之前的比分 |
| 回应用户观点 | “Fair shout. What would you change first: the press or the midfield?” | 回应真实观点，不伪造成员发言 |
| 赛后 | “FT. One player gets your MOTM vote. Who’s it?” | 确认完场后适度使用，不每场机械重复 |
| 游戏衔接 | “Taking this into FC: which part of that setup would you actually use?” | 战术内容已有事实基础；不硬接商品广告 |

禁止以“我刚看了直播”“我买过这家的金币”“大家都下单了”制造真实体验或社会认同。情绪表达可围绕已确认赛况，不挖苦受伤球员、不针对国籍种族或其他身份开玩笑。允许用户不回复，不追加催聊或机器人自问自答。

### 4.3 后台机器人：确定性交易与服务层

负责经过身份及权限校验后的查价、订单查询、福利资格判断与发券。

最小安全设计：
- 公共内容服务与后台写操作权限分离。
- 订单信息只在私密交互中展示，核验账户归属。
- 发券校验活动预算、用户资格、限领次数和商品范围。
- 发券请求使用唯一幂等标识；超时后先查结果，禁止盲目重复发放。
- 明确区分 `pending`、`issued`、`failed`、`unknown`，不将接口超时直接当失败。
- 管理员可审计、对账、暂停活动；兑换失败有人工处理路径。

### 4.4 Lucky Loot：活动执行层

复用已有报名、截止、领奖和对账能力，但先完成 FC27 奖励适配。第一期优先确定性资格奖励，不急于把比赛预测结果与有价奖励绑定。

### 4.5 内容发布流程

```text
授权或允许使用的来源
  → 抓取 / 订阅
  → 来源与发布时间检查
  → 去重、比赛与球员实体匹配
  → 大模型生成摘要或讨论草案
  → 风险过滤与必要人工复核
  → 发布并保留来源
  → 更新 / 更正 / 撤回
```

赛事事实来源与商业价格来源必须分开；重试、限流和队列不能导致重复消息。记录模型与 API 成本，给每场比赛和每日内容设置预算上限。

## 5. 面向英美市场的内容策略

### 5.1 三类核心内容

**A. Match to Squad：从真实比赛到 FC 阵容**
- 比赛中的三角配合、边后卫站位、压迫方式，对应什么游戏思路？
- 提供低、中、高预算阵容思路，强调预算与平台适用性。
- 真实球员表现不等于游戏卡数值，更不等于必然获得新卡或升级。

**B. 实用型 FC 内容**
- SBC / Evo / Objectives 是否值得投入，适合什么阵容。
- 球员测评推荐保留原作者链接，区分观点与可核验数据。
- 标注游戏版本、平台、数据时间，不把旧价格称为实时价。

**C. 社区贡献内容**
- 成员阵容诊断、赛后观点精选、战术复刻展示。
- 使用成员内容前取得相应许可；可匿名展示。
- 贡献价值看质量，不按发言条数无限奖励。

### 5.2 站外引流

- X：原创观点、关键战术图、赛后一句判断，搭配一个清晰 CTA。
- Shorts / TikTok / Reels：原创解说、战术动画或自录游戏复刻，不直接搬运受版权保护的赛事画面。
- 创作者：优先足球与 FC 双兴趣的小型创作者，采用可归因邀请链接。
- 不只说“进群领钱”，优先说“来讨论这套战术 / 获取阵容模板”。
- 付费合作或返佣应清晰披露；不得制造独立测评的假象。

### 5.3 时区与节奏

使用 `Europe/London`、`America/New_York`、`America/Los_Angeles`，通过 Discord 时间戳让成员看到当地时间。不要固定按北京时间或固定 UTC 偏移排期，以免夏令时错位。

英国成员参加赛前与直播讨论；美国成员保留赛后及晚间异步入口。活动至少提供适当的异步参与窗口，不把错过直播视为低价值用户。

## 6. 每场重点比赛的运营 SOP

| 时间 | 内容 | 机器人 / 人工职责 | 用户动作 |
|---|---|---|---|
| D-1 | 三个看点、相关 FC 阵容话题 | 内容助理起草，运营核验 | 订阅活动、分享观点 |
| T-60 | 已确认首发与一个讨论问题 | Smart Score 事实；运营检查 | 参加免费预测或讨论 |
| 开赛前 | 公示截止、剧透规则 | 活动系统锁定需要锁定的入口 | 确认预测提交 |
| 比赛中 | 关键节点，不逐分钟刷屏 | 事实源更新；有限触发讨论 | 在 Match Chat 交流 |
| 完场 | 事实复盘与真实观点总结 | 先核验 FT，再生成内容 | 评选表现、提出阵容问题 |
| 次日 | Match to Squad、成员内容精选 | 内容助理 + 人工审核 | 使用工具、查看服务专区 |

异常处理：VAR 改判、取消进球、延期、取消比赛、数据源中断、预测提交超时均需明确状态。无结算依据时保持待定，不擅自判奖。

首轮建议只做声望或徽章类赛事预测。Discord 原生投票可以改变选择，不应直接作为严格奖金或优惠券结算账本。

## 7. 留存、福利与转化设计

### 7.1 将声望与有价福利分开

| 体系 | 获得方式 | 用途 | 约束 |
|---|---|---|---|
| 社区声望 | 优质阵容解答、经审核内容贡献、有效活动参与 | 徽章、展示位、主持资格 | 不直接等于现金，不奖励灌水 |
| 福利资格 | 公示规则下的确定性领取或兑换 | 指定商品券或服务福利 | 有预算、限额、期限和适用范围 |
| 签到 | 可选轻量习惯机制 | 参与记录或非现金声望 | 不作为首要指标，不用连续签到惩罚制造焦虑 |

### 7.2 “免费、无门槛”的验收定义

如宣传真正免费，应验证：
- 至少存在符合条件的实际商品可用券完成 **0 支付**。
- 没有最低消费、强制充值、必买附加项或事后收费。
- 明示商品、平台、地区、账号资格、有效期、数量限制及税费处理。
- 若需注册，提前说明注册步骤，但不能把注册后仍必须付钱的券称为免费商品。
- 页面、机器人、客服和结算系统使用相同规则。

如只能抵扣部分价款，应称“抵用券”，不能宣传为“免费领取商品”。

### 7.3 可执行的转化路径

1. 成员在赛事讨论中产生游戏兴趣。
2. 内容提供明确的阵容、球员或玩法帮助。
3. 用户主动进入 MMOEXP 服务区，选择商品及平台。
4. 后台返回可核验报价和适用条款。
5. 用户主动查询福利资格或兑换，系统执行预算与幂等校验。
6. 跳转网站下单；Discord 不公开展示订单隐私。
7. 售后处理结果用于改善服务，不用于在公共频道制造购买压力。

### 7.4 用户分层的允许方向

以用户自选兴趣、平台、通知偏好和主动服务请求组织体验，不读取聊天来推断财富、消费能力或私人特征，不批量私信推销。

“主动查价的用户”可以得到其请求的报价与支持；这不等于机器人可以将其聊天记录扩展为营销画像。涉及 Discord API 数据的营销用途必须单独核对开发者政策，用户勾选通知不应被当作所有用途的豁免。

## 8. 合规与品牌风险：上线门槛

### 8.1 Discord

- 不骚扰、不批量陌生私信、不购买虚假成员或制造人工活跃。
- 机器人联系方式、数据收集及使用范围应符合 Discord 政策。
- 不将 API 获取的用户数据用于禁止的广告定向或用户画像。
- 清晰标注 AI 与商业专区；设置举报、退订、AutoMod 和人工处理机制。

### 8.2 EA FC

EA 官方规则对第三方金币买卖及金币分发有明确限制，可能导致金币清除、市场限制或账号处罚。**免费赠送或用券购买不构成规则豁免。**

因此：
- 不将“免费金币”作为默认增长主轴。
- 商品按类型逐项审核，不笼统认定所有 FC 商品均可推广或均被禁止。
- 不暗示 MMOEXP、Discord 社区或机器人获得 EA 官方授权。
- 在确认商品与活动可合规开展前，优先上线内容、讨论、非现金声望和可靠客户服务。

### 8.3 英美活动、版权与披露

- 不设计付费竞猜、充值提升中奖概率或购买额决定抽奖资格的机制。
- 有价奖励、抽奖和比赛活动的地区、年龄、参与条件及条款需适当审查。
- 使用自制战术图、获授权素材与来源链接，不默认可以重播比赛或转载博主全文。
- 创作者合作、赠品及商业关系应明确披露。

这些要求是上线检查项，不替代具体活动的专业法律意见。

## 9. 数据指标与效果判断

### 9.1 漏斗

| 阶段 | 指标 | 解释 |
|---|---|---|
| 获取 | 各来源加入人数、成本 | 使用允许的第一方活动/来源标识 |
| 激活 | 首次有意义参与率 | 发问、有效讨论或工具使用，不只算点击 |
| 定位 | 自选 FC27 兴趣及平台比例 | 判断引来的是否为目标交集人群 |
| 留存 | D7、D28 有意义活跃率 | 固定 cohort 和活动定义 |
| 服务意图 | 主动查价人数、有效服务请求 | 不等于购买，不做虚假意向推断 |
| 转化 | 可归因订单、领取与核销 | 区分免费核销、付费订单与复购 |
| 经济性 | 贡献利润 | 扣除折扣、履约、支持、创作者和模型成本 |
| 风险 | 退群、举报、错误报价、重复券、退款 | 增长不能以风险持续增加为代价 |

### 9.2 归因原则

- 前两周先形成基线，再制定增长目标，不承诺未经验证的行业转化率。
- 统一定义访客、成员、领取、核销、付款成功及退款。
- 避免同一订单被多个活动重复归因。
- 领取券的订单不自动等于增量销售；条件允许时设置合适对照组。
- 只记录完成服务和分析所必要的数据；技术上能采集不代表允许采集。

## 10. 30 天执行计划

### 第 1 周：确认基础，不扩功能

- [ ] 核对正式群权限、导航、服务器运行与失败告警。
- [ ] 跑一次 Smart Score → Match Chat → 完场复盘的自然赛事链路。
- [ ] 测量真实事件到消息的时间，区分源延迟与处理延迟。
- [ ] 确认聊天机器人实际模型、时区、预算和提示词。
- [ ] 明确 FC27 奖励商品、地区、平台、有效期与总预算。
- [ ] 若宣传免费，完成真实零支付验收。
- [ ] 建立首版来源归因和指标看板。

### 第 2 周：两场完整赛事运营

- [ ] Hermes 自动完成选题、赛程排序和排期；确认与 Smart Score 的接口或允许使用的输入契约。
- [ ] 首轮指定异常负责人并抽样检查，不要求用户每天亲自主持。
- [ ] 跑完赛前、赛中、赛后、次日的内容链。
- [ ] 收集真实用户问题，调整欢迎流程和内容长度。
- [ ] 验证无球队身份也能参与公共比赛；不同订阅提醒最终进入同一讨论。
- [ ] 只测试一个确定性奖励流程，不同步上复杂有价竞猜。

### 第 3 周：小规模增长实验

- [ ] 对比“阵容模板”与“赛事讨论”两个入口，保持其他条件尽量一致。
- [ ] 用小预算验证一位或少量双兴趣创作者。
- [ ] 优化主动查价与私密售后，不扩大陌生私信触达。
- [ ] 每次只调整一项关键变量，记录成本和负面反馈。

### 第 4 周：复盘与扩容决策

- [ ] 比较来源 cohort 的留存、主动查询、订单和贡献利润。
- [ ] 停止只带来薅券或低留存的入口。
- [ ] 修复关键错误后，再决定是否增加赛事、地区和奖励。
- [ ] 对未验收功能保留待办，不用文档上的勾选替代实际测试。

## 11. 实施任务与验收标准

| 优先级 | 任务 | 负责角色 | 验收标准 |
|---|---|---|---|
| P0 | 公共共同观赛改造 | 开发 + 社区运营 | 未选身份仍可进入，同场提醒汇入统一公共讨论，比分卡与讨论双向可达 |
| P0 | Hermes 自动选题与排期 | 自动化开发 | 每日有可解释选择记录、来源校验、预算限制、失败降级；无需用户逐条排期 |
| P0 | 正式赛事自然链验证 | 开发 + 运营 | 真实赛事、正确路由、原消息链接、完场复盘、异常记录完整 |
| P0 | 交易权限与发券对账 | 后台开发 | 鉴权、预算、限领、幂等、超时查询、管理员暂停可用 |
| P0 | FC27 免费福利合同 | 运营 + 商品 + 审核 | 商品范围、零支付事实、期限与限制一致，无误导用语 |
| P0 | 平台与商品风险审核 | 项目负责人 | 对 Discord、EA 及活动规则逐项记录结论；不合格功能不启用 |
| P1 | 英美时间与内容节奏 | 运营 + 开发 | 本地时间展示、DST、美国异步入口和通知退订正常 |
| P1 | 内容到服务的归因 | 数据 + 后台 | 从允许的来源标记至订单状态可追踪，退款与重复归因可处理 |
| P1 | 内容审核和更正 | 内容 + 开发 | 能保留来源、阻止无来源事实、对错误公开更正 |
| P2 | 声望与签到 | 社区运营 + 开发 | 质量优先、限频、不奖励刷屏、不与有价竞猜混合 |
| P2 | 扩大创作者合作 | 增长运营 | 有清晰披露、独立归因、成本及留存复盘 |

### 11.1 上线前待确定参数

以下按项目配置补齐，不在本文中擅自设为既定事实：
- 每月福利预算、每场预算、每日模型与 API 成本上限。
- FC27 可参加活动的具体商品与地区。
- 优惠券面额、有效期、每人限领次数及零支付商品。
- 自然赛事链路可接受的延迟目标。
- 人工值守、客服响应与异常升级负责人。
- Smart Score 数据使用授权、API 能力及稳定性边界。

## 12. 第一阶段结论

**现在最重要的不是再增加机器人，而是用现有底座完成一场真实赛事的内容、讨论、工具服务和结果归因闭环。**

优先顺序：
1. 将身份私密推送主线调整为公共共同观赛，身份只负责自主提醒与入口。
2. 核实正式赛事链路，接入 Hermes 每日自动选题与排期。
3. 确认 FC27 奖励与商品边界。
4. 以最少人工干预运营两场内容充分、不过度营销的赛事。
5. 用真实讨论参与、留存、服务请求和实际利润判断下一步投入。
