# FC27 赛事奖励：网站会员身份接线合同

状态：待 MMOEXP 网站开发确认现有接口；本文件是接入条件，不代表网站已提供这些字段，也不启用真实发券。

## 玩家路径

Discord 赛事卡只放公开活动链接。玩家点击后进入 MMOEXP 网站、完成网站登录、提交站内预测并查看自己的 Match Points。兑换也在这个登录态下进行，结果只显示在本人页面和券包；Discord 频道不展示邮箱、券号或个人领取状态。

## 网站侧需要交付的最小能力

由网站**服务端**根据当前登录会话提供以下已核实信息给 FC27 奖励服务，或提供等价的服务端调用；具体路径由网站开发决定：

| 字段／能力 | 要求 |
| --- | --- |
| `site_id`、`member_id` | 来自网站当前登录会话，站点须为 MMOEXP `266`，会员 ID 为稳定正整数；不能由浏览器请求体或 Discord 用户自行填写。 |
| 已验证邮箱 | 返回当前会员绑定邮箱及其验证状态／时间；未验证、已换绑而未重新验证时拒绝发券。邮箱只在受控服务端传给 Admin，不进入 Discord 链接或日志。 |
| 会话有效性 | 服务端确认登录未过期、账号仍可用；兑换提交时再查一次，不仅在打开页面时查。 |
| 本人券包查询 | 用同一网站会话读回刚发放的会员券 ID、券规则和状态，供玩家核对到账；不能只凭发券 HTTP 200 宣称成功。 |

建议网站开发提供一个**仅服务端可用**的当前会员查询合同，语义相当于：

```json
{
  "site_id": 266,
  "member_id": 12345,
  "email": "verified-member@example.invalid",
  "email_verified": true,
  "account_active": true
}
```

上面是字段示例，不是已发现的真实接口。若网站没有已验证邮箱字段，需先由网站原有邮箱验证码流程确认本人，再出具同等服务端断言；Admin `user.Member/index` 按邮箱查到会员、FS 员工登录态、Discord 用户名或私信自报邮箱都不能替代此断言。不得把浏览器 Cookie 复制到 187 常驻服务。

## 187 的发券动作

1. 网站服务从自身登录态取 `site_id=266`、会员 ID 和已验证邮箱。兑换请求只传奖项 ID，不接受自选收件邮箱或会员 ID。
2. FC27 账本用该会员 ID 原子检查余额、奖项份数和重复领取；返回固定 `claim_id` 与 `FC27R_…` 批次。重复点击返回原领取记录。
3. 发放前重新读取网站会员状态和 Admin 券详情，核对已验证邮箱、FC27 游戏 `1327`、有效期、定向发放状态及券规则指纹。任何差异暂停该笔，不换券或收件人。
4. 先持久化 `sending`，再沿现有 187 HMAC 代理向 `market.CouponGrant/import` **一次**提交一个已验证邮箱、原批次和券模板。同步成功需记录会员券 ID；异步任务只查原 `job_id`；超时或不明状态冻结并按原批次人工对账，绝不自动再 POST。
5. 网站本人券包读回该会员券及条款后，页面才显示“已到账”。未到账显示处理中／需人工核对，不发第二张券。

现有 `opt/mmoexp-fc-community/match_rewards.py` 是未接入运行服务的兑换账本；`opt/mmoexp-lucky-loot/coupon.cjs` 提供已核实的 Admin 发券和异步对账业务合同。首次联通须使用**新建的小额测试券**和用户已授权的本人测试账号；旧测试券 `1385` 已用作单次测试，不能作为正式奖池。

## 接口交付时的验收

- 未登录、会话过期、未验证邮箱、非 MMOEXP 站点、停用会员均无法领取。
- 浏览器篡改 `member_id` 或 `email` 不改变服务端识别的本人；Discord ID 不进入现金券资格判断。
- 同会员并发点击、刷新和跨设备重复点击只保留一笔领取和一个批次。
- 券模板变更、份数耗尽、余额不足时不调用发券接口。
- 发券超时或异步处理中，重试只查询原记录；不会再提交一次。
- 真实小额测试券发到**当前已验证邮箱对应的本人券包**，另一测试账号看不到，也不能代领。

网站开发回传：真实接口路径／调用方鉴权方式、上述字段语义、邮箱验证与换绑流程、本人券包查询方式，以及一套非生产测试会员。收到后先在测试环境接线和验收，再开放正式兑奖入口。
