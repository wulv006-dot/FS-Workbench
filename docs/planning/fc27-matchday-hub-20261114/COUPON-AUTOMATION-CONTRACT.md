# FC27 赛事奖励券自动创建与发放接线方案

状态：设计已定，自动创建未接入。执行基线为[FC27 Discord 运营方案](FC27-DISCORD-OPERATIONS-BASELINE.md)；本文件把 2026-11-15 的单邮箱实测转成后续施工合同，不代表已具备生产自动发券能力。

## 已验证与尚缺条件

- 用户已授权在 Admin Web 后台创建一张测试券，并定向发给其指定邮箱。券 `1385` 为 MMOEXP 站点 `266`、FC 27 游戏 `1327`、满 `$10` 减 `$0.50`、限领 `1`、每人 `1` 次、领取后 `1` 天有效。定向发放批次 `FC-27_FC27DiscordPilot2026_20261115` 的页面回执为 `done`、`1/1` 成功、`0` 失败、会员券 ID `1032255`。这只证明**创建和单邮箱发放**，没有进行下单、支付或结算适用性验证。
- 187 当前 HMAC Admin 连接身份有 `market/couponGrant/import` 等发放权限，但没有 `market/coupon/add`；创建接口 GET 返回业务码 `401`。Web 后台的“吴律”账号可以创建，不能据此推断 187 自动创建已获授权。
- 历史原生合同确认创建为 `POST /admin/market.Coupon/add`，定向发放为 `POST /admin/market.CouponGrant/import`，查询异步发放结果为 `GET /admin/market.CouponGrant/jobStatus?job_id=…`。创建请求使用 JSON `form.items` 并去掉 null；上线前须对**当前**前端和单次受控请求重新核对字段与回执，历史文档不当作活接口保证。
- 现有 [Lucky Loot 发券适配](../../../opt/mmoexp-lucky-loot/coupon.cjs) 已实现券详情校验、定向发放与异步任务对账；其[领奖状态机](../../../opt/mmoexp-lucky-loot/app.cjs)先持久化发放意图，再调用 Admin，未知结果不会自动重发。FC27 应复用此边界，不另建一套无对账的批量发券。

## 自动化目标与界面

在 FS 的独立 FC27 控制台增加“赛事奖励券”设置。运营先配置活动、券金额/门槛、有效期、适用游戏及可选商品范围、份数和总预算，查看用户实际能看到的条款预览，再启用该活动的自动模板创建与领取。每个活动或奖项档位创建**一个券模板**；每位符合资格的玩家只获一次定向发放，不为每人新建模板。创建券和发放券分为两个可单独暂停、对账的动作。

第一期只支持站内可核验的确定性资格（例如 MMOEXP 会员自愿报名），不把 Smart Score 的私密预测直接作为发券依据。Discord 原生投票可用于无奖讨论，但不读取投票人名单来判断谁能获券；[Discord Developer Policy 第 16 条](https://support-dev.discord.com/hc/en-us/articles/8563934450327-Discord-Developer-Policy)明确限制将 API 数据用于福利资格判断，换成自有 Discord 投票账本也不能绕开这条边界。若以后做“猜对领奖”，需另设计由玩家自愿参与的 MMOEXP 站内预测与身份、截止、赛果及异常复核流程；在该流程和适用规则核实前不自动发奖。

## 券模板合同

1. 创建前核对 `market/coupon/add` 权限、当前 Admin 会话、FC27 游戏范围及活动预算。缺权限立即停止创建，继续允许已有模板的手动单邮箱测试；不借用浏览器登录态给服务端程序，也不迁移浏览器 Cookie。
2. FS 生成唯一活动操作 ID 和不可复用标题，先写入本地操作账本。模板固定 `type=1`、`fetch_scene=4`、`mode_type=1`、`site_id=266`、`game_id=1327`、`is_open=0`（默认不叠加折扣码）；`attain` 为门槛，`reduce` 为固定金额，`limit_qty` 与预算一致，`repeat_qty=1`。日期或领取后天数只选一种。产品类型、单品 ID、地区/平台范围未验证时不推断，运营界面明示“FC27 全类目”或阻止上线。
3. 优先以 `status=0` 建禁用模板。保存后用原操作 ID 与精确标题查完整分页，再 `GET edit?id=…` 读回全部关键字段；只有读回一致、当前预算允许时才开启。**本次 Web 表单保存后实际显示状态开启**，因此不能假定后台默认禁用；若当前接口不接受/不保留 `status=0`，自动创建保持关闭，先验证明确的创建与启停合同。
4. 创建 POST 超时或结果不明时，操作进入 `create_unknown`；按原操作 ID、精确标题和 Admin 列表/详情人工或程序对账。不能换标题或 UUID 重发，以免产生第二张可用券。
5. 模板建成后锁定活动快照：金额、门槛、范围、有效期、总量、叠加规则与券 ID。后台改券时停止新发放并提示差异，不默默沿用旧规则。

## 发放与身份合同

1. 玩家可从 Discord 私密按钮进入领取流程；发券资格和每人限领取自 MMOEXP 站内会员及活动记录，不使用 Discord 投票人或聊天数据判断。仅凭 Discord ID 或玩家自报任意邮箱，不能断定邮箱属于本人。当前网站绑定接口尚待开发确认；未接通时使用现有 Lucky Loot 私密邮箱申领和运营审核，不自动向竞猜参与者批量发放。
2. 每位获奖者建立唯一 `claim_id`；以活动 ID + `claim_id` 生成稳定 `grant_batch_no`。发放前持久化已核网站会员、站内资格回执、券快照、目标邮箱（加密）和预算占用。控制台列表只显示必要状态，不展示原始邮箱。
3. 复用现有 HMAC 代理向 `/admin/market.CouponGrant/import` 发送 `site_id=266`、已核券 ID、原批次号、**一个邮箱**。返回同步 `success` 或异步 `job_id` 后记录会员券 ID/失败原因。`pending` 只用原 `job_id` 查询；`unknown` 冻结该 claim，先核原批次或后台会员券记录，不自动重发。
4. 控制台展示创建、启用、发放、已达上限、未注册待领、失败和未知的状态及预算余额。活动总预算、每天上限、每人一次、重复点击锁、运营暂停开关都在服务端执行。超预算或券规则变动即停发，不自动追加额度。
5. 用户只看到私密领取结果与券条款；公共 Match Chat 不发布个人邮箱、会员 ID、券 ID 或领取情况。奖励说明不宣称“免费商品”或“零支付”，直到真实结算口径验证。

## 权限开放后的最小验收

1. 读回新身份的 `market/coupon/add`，用 FC27 测试活动创建**一张禁用券**，核对创建响应、列表、详情和状态；若禁用语义不成立即停止。
2. 验证启用/暂停后规则读回；只对已授权的测试账户发一次小额券，核对原批次 `done`、成功行、会员券 ID 和用户券包。模拟网络超时后只能按原 ID 对账。
3. 用独立测试账户尝试重复点击、重复批次、超预算、错误站点/游戏、已满额、邮箱未注册和券模板漂移；逐项证明不会重复发放或扩大适用范围。
4. 真实订单/退款/折扣码叠加与贡献利润需要另行验收。当前测试只到发券，不下单或消费。

## 实施位置与回退

- 管理 UI：沿现有 FS FC27 控制台的管理员鉴权与 CSRF，新增券配置、预览、暂停和对账视图；没有公开创建 API。
- 业务层：在 FC27 活动服务中增加券模板状态机，发放调用复用 `opt/mmoexp-lucky-loot/coupon.cjs` 的合同或抽出共用模块；不复制密钥或变更现有 Lucky Loot 活动记录。
- Admin 出口：187 原 HMAC 代理，仅申请 `market/coupon/add`（以及经验证确实需要的启停节点）；权限到位后先做受控单次端到端验证，再打开自动模板创建开关。
- 回退：关闭自动创建与新发放开关，保留券模板、批次、会员券、预算占用和未知状态账本；不通过旧文件或数据库备份覆盖已发记录。既发券如需失效由运营按 Admin 当前可追溯流程单独处理。
