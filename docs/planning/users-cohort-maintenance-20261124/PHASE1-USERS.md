## 页面结构（只保留三块）

页头一行：数据截止日、配置版本、缺几天。

### 1. 新客复购队列（核心）

**输入**：首单月份范围（默认 2026-01 至上一个完整月）、游戏范围（全部 / 指定游戏）、时间窗天数列表（默认 30/90/180，最多 5 个，每个 2–365，升序）、回流参数 X/Y（默认 60/180，2 ≤ X < Y ≤ 365）。

**批次归属**：客户按站内首单（共享合同第 2 节）的上海日期归入唯一一个月份批次；首单 ES 标记为新客才进队列；待核单独计数。指定游戏时再按共享合同第 4 节过滤。

**时间窗端点**：首单时刻记为 T0。窗口 N 覆盖 `[T0+24h, T0+N 天)`。截止时刻 = 数据截止日次日 00:00。

**每个批次 × 每个时间窗 N**，每个客户恰好落入以下之一：

| 状态 | 条件 |
|---|---|
| 已满窗（分母） | `T0+N 天 ≤ 截止时刻`，且 `[T0, T0+N 天)` 订单覆盖完整 |
| 观察中 | `T0+N 天 > 截止时刻` |
| 覆盖缺口 | 时间已满但区间内有订单覆盖缺口 |

输出：分母、观察中、覆盖缺口人数；累计复购人数与比率（分母内、窗口内有复购的人 ÷ 分母）；复购金额（分母内客户在窗口内全部复购订单金额合计）与人均（÷ 复购人数）。

**首次复购分布**：只统计最大窗已满的客户，按首次复购距 T0 的天数落入 `[1,N1)`、`[N1,N2)`…、未复购。

**沉默后回流**：分母为「已满 Y 天、覆盖完整、且 `[T0+24h, T0+X 天)` 无复购」的客户；分子为其中在 `[T0+X 天, T0+Y 天)` 有复购的客户。输出人数、比率、回流金额。

**展示**：批次 × 时间窗热力表；观察中或覆盖缺口的格子灰色并标人数。点击任意格子可看名单并导出 CSV。

### 2. 客户阶段

所选首单日期范围内有效购买客户在观察日的阶段分布（共享合同第 5 节），可按新客/老客、是否复购筛选；另列所选期间从沉默或流失回来的人数。点击可看名单并导出。

以下三项沿用 `user_lifecycle.py` 现有计算，按共享合同第 5 节当前配置版本重算（用户 2026-11-24 确认保留）：

- **本期流入**：所选期间内新进入沉默、流失、长期流失的去重人数（现 `entered_silent` / `entered_lost` / `entered_long_lost`），一行展示，点击看名单。
- **每日回流趋势**：每个上海自然日从沉默回来（`silent_wakeup`）和从流失或长期流失回来（`lost_return`）购买的去重人数，一张折线图，两条线。现有按日趋势只聚合了 `lost_return`，需用现有事件新增 `silent_wakeup` 的每日去重序列。同一人同日只计一次；不同日的人数不相加成区间人数。
- **跨游戏流向**：只在「全部」范围显示，默认折叠。对每个目标游戏 G：按 G 自己的阈值判断客户在 G 已流失或长期流失，同时按另一游戏 H 自己的阈值判断客户在 H 为近期，计入「G → H」。不能用全站阶段代替单游戏阶段（现 `project_analysis` 比较的是「本游戏 × 全站」，需改写）。验收含「全站近期、目标游戏已沉默」的反例。

### 3. 查人

按完整邮箱查购买记录与时间线；名单下钻与导出。时间线标注首单、复购、进入沉默/流失/长期流失、回流（保留现有 `user_lifecycle.py` 的事件计算，只按新阈值配置计算）。

### 删除的展示与对外视图

已确认首购、首购身份待确认、已覆盖购买客户池、高价值刚进入沉默、需负责人核查的客户、项目经营汇总表（跨游戏流向之外的部分）、每日购买趋势（每日回流之外的部分）、全历史辅助回看、H=7/30 固定成熟二购。

只删除页面和 v4 对外视图里的这些项。时间线所需的阶段事件计算保留。经营看板复购率见下节。

## 经营看板复购率（用户 2026-11-24 确认）

**现状**：主卡显示「Admin 原生复购率」（Admin 汇总 `repeat_rete`，公式未公开）。本地期间复购率由 `local_repeat_source.py::attach` 在有授权用户的响应阶段注入 `supplement.local_repeat_rate`，只作为对账备注；`admin_scope.py::repeat_metrics` 只接受旧定义串 `at_least_two_distinct_valid_orders_within_selected_period`；FC 专用渲染把 `repeatRatePct` 当原生字段覆写卡片（`business.js` 等三份前端源）；`daily_archive.py` 拼区间时移除两种复购率。

**新定义（期间复购率）**：只看所选期间内，不读期间以外的历史。

- 期间购买客户：所选期间、所选范围内至少一笔有效订单的客户（按 `customer_id` 去重）。
- 期间首单：该客户在所选期间、所选范围内的第一笔有效订单，同刻按 `(paid_at, order_key)` 取第一笔。
- 期间复购客户：期间内另有一笔有效订单，其 `paid_at − 期间首单 paid_at ≥ 24 小时`。
- 期间复购率 = 期间复购客户 ÷ 期间购买客户；分母为 0 显示「不适用」。
- 「所选范围」为看板当前的网站与游戏。游戏为「全部」时任意游戏订单都算。
- 新定义串：`period_first_plus_24h_within_selected_period`。

**改动**（全部归一期）：

- `user_lifecycle.py`：期间复购按新定义计算，输出新定义串。
- `admin_scope.py`：校验新定义串；本地值与原生值保留为两个独立字段（`local_repeat_rate`、`native_repeat_rate`），主卡取本地值。
- `local_repeat_source.py`：仍只对「整日、主站 266、无国家筛选」的已授权查询计算，但改为独立取值：不再依赖响应里预先存在 `supplement.local_repeat_rate` 占位字段（现 `attach` 遇到无占位字段会直接返回原对象，需去掉此前置条件）。区间由日归档拼成的响应同样走此路径。主卡、跨游戏表和导出读同一份本地结果，分子分母一致。
- 三份前端源（`business.js`、`home-business.js`、`legacy-business.js`）：通用卡片和 FC 专用渲染都改为主卡读 `local_repeat_rate`，不再用 `repeatRatePct` 覆写；Admin 原生值移入收起的「补充指标」并注明公式未公开；删除「两种复购率待对账」备注；跨游戏表和导出同步改字段。
- 主卡显示「不适用」并写明原因的情形：全部网站、RS、带国家筛选、小时或非整日区间、FC 商品细分卡（Coins/Items 等，不把全游戏的率贴到细分卡）、无用户数据权限、本地读取失败。任何情形都不用 Admin 原生值顶替。
- **每日归档**：本地期间复购率不写入日归档（它依赖登录用户权限，且区间值不能由日值拼出），每次按查询区间从用户分析库实时计算。归档中的 Admin 原生字段照旧保存，历史归档不改写；多日归档拼成的区间，Admin 原生率显示「未知」（现有拼接已移除该字段，不由日值推算）。
- 同步更新经营看板八主卡合同 `docs/planning/business-dashboard-refresh-20261025/CONTRACT.md`：复购率由「保留原生定义」改为本地期间复购率（用户 2026-11-24 授权）。

## 权限

能打开 `/dashboard/users/` 的账号都可看名单、邮箱并导出（用户 2026-11-24 授权放开原「仅管理员」限制）。实施方式：本页的搜索、详情、快照名单、导出四类操作改为校验 `/dashboard/users/` 页面权限；不改 `user_runtime.authorize` 的公共 `private` 语义，其他资源（`/dashboard/analytics/`、`/dashboard/data-tools/`、实时订单接口）保持原权限。Hermes 和连接器沿用各自现有身份与权限。邮箱不进 URL、不进操作日志。

快照固定批次范围、游戏、时间窗、X/Y、筛选和配置版本；名单、导出、Hermes 结果都引用同一快照。权限撤销后，旧快照名单和导出下载按现有复验机制失效。

## 性能

三个入口共用同一后台作业与快照（复用 PR1325 的 `user_summary_jobs.py`，扩展到页面和 Hermes 入口），各入口只是首次等待时间不同：

| 入口 | 首次等待 | 未完成时 |
|---|---|---|
| FS 连接器（请求上限 25 秒） | 3 秒（现值） | 返回 `202`、`query_id`、`retryAfter` |
| 页面 | 10 秒 | 返回 `202`，页面显示「计算中」并自动续查 |
| Hermes 工具 | 10 秒 | 返回 `202`，工具结果告知按 `query_id` 续查 |

- 续查返回完整结果，或明确错误。宿主重启或作业被淘汰后，原 `query_id` 返回现有错误码 `users_summary_query_expired`（v4 沿用此码），调用方重新发起。

**连接器两条路径都要贯通**：

- `users.summary`（`action=connector_summary`）：沿用现有 `202` / `query_id` / `retryAfter`。
- `analytics.user_section`（现为 `action=tool`，同步执行并固定包装为 HTTP 200）：改为走同一后台作业。目录条目输入新增可选参数 `query_id`：首查时传查询参数、不传 `query_id`；续查时只传 `query_id` 和要读取的 `section`，与查询参数互斥（同时出现返回 422）。未完成时返回 HTTP `202` 与 `query_id`，完成后返回含 `snapshot_id` 的 section 结果。
- 不返回部分结果冒充完整。

## 验收

1. 单测：24h 复购边界（恰好 24h、同刻多单）、窗口端点、满窗/观察中/覆盖缺口三分、回流 X/Y、指定游戏过滤、待核排除、热力格子与名单一致、旧快照拒绝、本期流入/每日回流/跨游戏流向按新阈值计算且与名单一致。
2. 真实库只读核对：2026-01 批次随机抽 20 个客户，按订单明细手算复购与回流，与结果一致。
3. 冷查询：2026-01 至最新截止日、全部游戏，记录耗时。用同一个耗时 26–30 秒的查询，分别从页面、Hermes 工具、连接器 `users.summary`、连接器 `analytics.user_section` 发起，验证首次响应为 `202`、续查得到同一 `snapshot_id`；`analytics.user_section` 另验证续查读取指定 section、查询参数与 `query_id` 同传返回 422、旧快照被拒绝；重启后返回 `users_summary_query_expired`。
4. 经营看板期间复购率单测：期间内两单恰好相隔 24 小时（计入）、差 1 秒（不计）；上月首购、本期只有一单的老客（不计入）；分母为 0；上节列出的各「不适用」情形；旧归档读回仍显示原生值且不被标成新口径；同一客户两天各一单、恰隔 24 小时、只有两份日归档时，整段本地期间复购率为 1/1，整段 Admin 原生率显示「未知」。
5. 部署后真实入口：用一个有页面权限的非管理员账号，查 2026-01 批次 POE2 与全部范围，翻名单末页、导出读回；Hermes 回答「1 月新客 90 天复购率」与页面一致；经营看板主卡显示「期间复购率」且可展开分子分母，抽一个期间按订单明细手算一致；Admin 原生复购率在补充指标中可见；选「全部网站」时主卡显示「不适用」。
