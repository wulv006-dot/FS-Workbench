# 共享口径合同

一期（用户分析）和二期（客户维护）共用以下定义。任何一期需要改这些定义，先改本文件并单独合并，不在各自 PR 里各改一份。

## 1. 有效订单

沿用现有用户分析的有效购买判定（`user_source.py` / `user_store.py` 的 `valid`）：已付款、非测试单、非全额退款。订单按整单归属游戏，金额为整单 `amount_usd`，不跨游戏拆分。范围为 MMOEXP 主站（site 266）。

## 2. 新客 / 老客

客户在所选范围内第一笔有效订单上的 ES「是否新客户」标记：是 = 新客，否 = 老客。标记缺失、未匹配或冲突 = 待核，不并入新客或老客。

## 3. 复购

首单付款时刻 24 小时之后的另一笔不同的有效订单。首单后 24 小时内的追加单不算复购，也不重置首单。一单多商品只算一单。

## 4. 游戏范围

- 「全部」：首单和复购可以是任何游戏。
- 指定游戏 G：首单必须含 G，复购必须是之后含 G 的有效订单。
- 本期不做「游戏内首购（站内老客第一次买 G）」口径。

## 5. 阶段天数（每个游戏一套）

观察日距末次有效购买的天数，阈值 `[A, C, L]`：

| 阶段 | 条件 |
|---|---|
| 近期 | 天数 < A |
| 沉默 | A ≤ 天数 < C |
| 流失 | C ≤ 天数 < L |
| 长期流失 | 天数 ≥ L |

每个游戏只配置一套，用户分析页和客户维护共用。FC27（gid 1327）默认 `[14, 30, 60]`，替换旧 `fc-v1` 的 `[14, 30, 90]`；其他游戏沿用 `user_config.json` 现有 policy 映射。管理员可在客户维护页修改，修改留版本记录，生效后两页同时使用新版本。

## 6. 价值档（客户维护用）

按客户历史单笔最高有效订单金额（USD）定档，单笔达线即入档，取最高档：

| 档位 | 单笔金额 |
|---|---|
| 超高价值 | ≥ $300 |
| 高价值 | $200 – $299.99 |
| 其他 | < $200，不进入阶段维护 |

依据：2026-09-08 至 11-23 FC27 有效订单 26,958 笔、14,389 人；单笔 ≥$300 的客户 374 人（约 2.6%），≥$200 的 920 人（约 6.4%）。高价值下限由用户 2026-11-24 从建议的 $150 上调为 $200。门槛按游戏配置，修改方式同第 5 节。

## 7. 客户身份

- 用户分析：沿用现有已核主邮箱（`exact-primary-email-v1`），一个邮箱一人。
- 客户维护：按 Buyer ID（站内会员 UID）判断门槛，达标后才取邮箱入名单；无 Buyer ID 的游客订单用订单邮箱。沿用 2026-11-10 Buyer ID 候选的去重与邮箱冲突规则（[知识条目](../../../knowledge/customer-tracking/BUYER-ID-CANDIDATES.md)）。

## 8. 落地位置

新增共享模块 `releases/fs-dashboard/customer-segments-20261124/source/customer_segments.py`，提供：

- `stage(days, game)`、`thresholds(game)`：第 5 节。
- `tier(max_single_order_usd, game)`：第 6 节。
- `is_repeat(first_paid_at, paid_at)`：第 3 节的 24 小时规则。
- 配置读取：生产配置文件 `/var/lib/fs-customer-segments/segments.json`（带 `version`），缺失时用模块内默认值并在结果里标明 `config_source=default`。

两期代码只调用这个模块，不各自写死天数或门槛。本合同合并时只含模块、默认配置和单测，不改任何页面。
