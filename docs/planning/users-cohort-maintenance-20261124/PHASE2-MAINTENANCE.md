## 数据来源与入池

从用户分析私有库读取（共享合同第 1、7 节）：FC27 有效订单、客户邮箱、`customer_id`。按客户计算 FC27 历史最高单笔金额，达到 $200 才入池；不达标的客户直接过滤。库里已有邮箱，不需要逐个去 Admin 查邮箱。

## 阶段维护范围

与两份周名单并列的第三个范围，目前只开 FC27。

**分组**：价值档（超高 / 高）× 阶段（沉默 / 流失 / 长期流失）× 新客/老客。近期和待核阶段只计数，不进维护列表。

**每日运行**：等用户分析日更对数据截止日 D 发布成功回执后运行，观察日为 D。没有成功回执就不跑，页面显示「等待 D 日数据」。

**阶段进入事件**：事件键 = `(customer_id, gid, 阶段, 末购 order_key, 配置版本)`。对每个入池客户：

1. 用当前配置版本计算 D 日阶段，与本地保存的上次阶段比较。
2. 只有同一配置版本、同一末购订单下，阶段从低升到高，才记为**新进入**，触发规则。
3. 以下情况只更新本地阶段，记为**存量**，不触发规则：首次运行、配置版本变化、末购订单因补档或退款更正而变化。
4. 漏跑的日期按日期顺序逐日补算；补算出的新进入照常触发，派发前按第「派发」节重验。
5. 末购订单被更正为无效时，基于旧末购的未派发事件作废。

## 规则

一条规则 = 条件 + 动作 + 状态 + 优先级。

- 条件：游戏、价值档、阶段、新客/老客（可选）。只按系统计算的价值档匹配。
- 动作：发券（已批准的券模板，可为空）、预警（页面「待跟进」列表标红）、分配负责人（负责人名单可配置）。
- 状态：预演 / 自动 / 停用。新建规则默认预演。只有 FS 管理员能在页面上新建、修改规则或切换状态，服务端校验管理员身份。
- 同一事件命中多条规则时，按优先级从小到大处理。

**预演**：每日照常计算，列出「本来会发给谁、发哪张券、分给谁」，不发券、不分配。
**自动**：程序直接执行，不逐笔确认。

## 发券保护

以下三项在同一个 SQLite 写事务（`BEGIN IMMEDIATE`）中占用，成功占用后才允许发券：

1. **事件幂等**：唯一键 `(customer_id, rule_id, 事件键)`，同一事件同一规则只执行一次。
2. **客户额度**：同一客户 30 天内最多一张自动券（跨规则）。按发券记录创建时间往前推 30×24 小时计算；状态为派发中、待注册、UNKNOWN、已确认的都占额度，明确被拒的释放。
3. **规则日额度**：按上海自然日计每条规则的发券数，超出的记为「顺延」，次日用同一条记录继续，不新建。

## 派发

**派发前重验**（含顺延次日）：客户在事件之后没有新的有效订单；当前阶段不低于事件阶段；规则仍为自动且版本未变；券模板快照未变。任一不满足，记录原因并关闭，不发券。

**券模板核对**：规则启用时保存模板快照。派发前用 `coupon.detail` 重读，必须 `site_id=266`、`game_id=1327`、`fetch_scene=4`（定向券）、`status=1`、未过期，且与快照一致。`coupon.validate` 只作为附加检查（它允许 `site_id=0`，不能单独使用）。

**批次号**：`FCSM_` + 事件幂等键 SHA-256 的前 32 位大写十六进制，不含邮箱。发券桥只接受 `^FCSM_[A-F0-9]{32}$`。上线前先用一张测试券确认 Admin 接受该格式和长度。

**提交与结果**：

1. 提交前把批次号、规则版本、券 ID、收件邮箱、状态 `dispatching` 写入本地账本。
2. 调用 `grant` 一次，不自动重试。
3. 结果处理：
   - 有 `job_id`：保存，之后只用 `reconcile(job_id)` 查询。
   - 无 `job_id`（超时、进程退出）：状态 `UNKNOWN`，额度保持占用，进入页面「待人工核对」列表，由人在 Admin 按批次号核对后手动标记结果。不重发。
   - `pending_register`：收件邮箱尚未注册会员，额度保持占用，按 `job_id` 继续核对。
   - 明确拒绝：记录原因，释放额度。
   - 已确认：以 Admin 发放回执为准。

**执行身份**：复用 187 上 Lucky Loot / FC 社区赛奖励已在用的同一 HMAC 发券代理（`coupon.cjs` 的 `127.0.0.1:8911`），不新增凭据。上线前核实该身份具备读模板（`market.Coupon`）、导入发放（`market.CouponGrant/import`）和查任务（`jobStatus`）权限；缺任何一项先报告，不切自动。

## 分配与跟进

- 阶段维护的案件复用现有 `vip_cases` 与认领、反馈记录。同一客户在任一范围已有未结案件时，事件挂到该案件上，不新建；否则新建一个阶段维护案件。
- 规则分配只填空：只在 `owner IS NULL` 时写入负责人。人工认领与规则分配同时发生时，先提交的生效，另一方记为跳过。
- 改派是新增接口：只有管理员或 Hermes（见下节）可以调用，带期望的原负责人（CAS），不一致则拒绝。
- 反馈仍只能由当前负责人写入（现有规则）。

## 券模板

Claude 起草「档位 × 阶段 → 券面额 / 有效期 → 负责人」矩阵，用户确认后，由 Claude 在 Admin 按清单建券模板（site 266、game 1327、定向券），把券 ID 填入规则。建券前先核实现有账号有没有新建 `market.Coupon` 的权限；没有就报告，由用户在 Admin 建好后提供 ID。

## 效果

- **归因**：每张券按批次号关联核销记录（`memberCouponLog` 的 `grant_batch_no`）；每笔回购按事件归属到规则版本。
- **窗口**：从事件时间起算 7/30/60 天，只统计窗口已满且订单覆盖完整的事件。触发人群和发券成功人群分开统计。UNKNOWN、顺延未发的单独计数。回购为窗口内含 FC27 的有效订单。
- **基准**：用同一配置版本回算规则启用前同一档位 × 阶段的进入事件，按同样窗口统计回购率。不设随机对照组。页面同时标注当期所处赛季位置，提示赛季开启本身会拉高回购。

## Hermes 与连接器

**读**：分组名单、客户详情与时间线、规则效果、预演结果。

**写**：分配或改派负责人、写跟进备注、调整价值档。

- 写入只在 Hermes 会话能传递可信的 FS 用户身份时开放，操作人记为该用户；没有可信身份时拒绝写入，不用固定账号代替（遵守 AGENTS.md「不得通过固定 `wulv` 冒用调用者」）。
- 每次写入带 `request_id`，记录修改前后的值。撤回只在当前值仍等于修改后的值时执行（CAS）。
- 人工调整的价值档只影响名单展示和分配，不参与规则匹配，不会触发自动发券。

**不能**：新建或修改规则、切换预演/自动、直接发券。服务端对这些接口校验管理员身份，与客户端限制无关。

## 配置编辑

客户维护页的管理员设置里可修改共享合同第 5、6 节的阶段天数和价值门槛，按共享合同第 8 节原子写入新版本。修改后，下一次每日运行按「配置版本变化 → 存量」处理，不会因改阈值批量触发发券。

## 发布与回退

- 二期在一期部署完成后发布，发布包以一期已部署版本为基础重新生成，避免覆盖一期对 `catalog.json` 的改动。
- 回退顺序：先把所有规则设为停用（停止新派发），再回退页面、路由和代码。本地账本、额度占用、案件和待核对记录保留，已提交的发券继续按 `job_id` 核对。

## 验收

1. 单测：入池过滤、档位、阶段进入与存量判定（首次运行、配置变更、补档、退款更正、漏跑补算）、三项保护的并发占用、顺延与次日重验、模板核对、批次号格式、`grant` 无 `job_id` 时进入 UNKNOWN 且不重发、规则分配只填空、改派 CAS、Hermes 无可信身份时拒绝写入、人工改档不触发发券、预演不发券。
2. 预演上线：用真实数据跑一个自然日，人工抽查 20 个客户的档位、阶段与事件。
3. 自动发券：用户确认预演名单后，选一条规则切自动，跑一个自然日，核对 Admin 发放记录与本地账本逐条一致；模拟一次提交后进程退出，确认进入 UNKNOWN 且未重发。
4. 真实入口：新地址可打开、旧地址跳转、导航在新位置、两份周名单功能不受影响、连接器 `customer_tracking.*` 可用。
