## 数据来源与入池

从用户分析私有库读取（共享合同第 1、7 节）：FC27 有效订单、客户邮箱、`customer_id`。按客户计算 FC27 累计有效消费，用当次运行读取的配置版本调用 `tier()`，返回超高或高价值才入池；不达标的客户直接过滤。$500 只是初始配置值，入池与规则匹配始终用同一配置版本算出的档位，不另写门槛。库里已有邮箱，不需要逐个去 Admin 查邮箱。

## 阶段维护范围

与两份周名单并列的第三个范围，目前只开 FC27。

**分组**：价值档（超高 / 高）× 阶段（沉默 / 流失 / 长期流失）× 新客/老客。近期和待核阶段只计数，不进维护列表。

**每日运行**：等用户分析日更对数据截止日 D 发布成功回执后运行，观察日为 D。没有成功回执就不跑，页面显示「等待 D 日数据」。

**阶段进入事件**：事件键 = `(customer_id, gid, 阶段, 末购 order_key, 配置版本)`。对每个入池客户：

1. 用当前配置版本计算 D 日阶段，与本地保存的上次阶段比较。
2. 只有同一配置版本、同一末购订单下，阶段从低升到高，才记为**新进入**，触发规则。
3. 以下情况只更新本地阶段，记为**存量**，不触发规则：首次运行、配置版本变化、末购订单因补档或退款更正而变化。
4. 漏跑的日期按日期顺序逐日补算；补算出的新进入照常触发，派发前按第「派发」节重验。
5. 末购订单被更正为无效时，基于旧末购的未派发事件作废。
6. 每次计算前先把订单截断到观察日 D（含）为止；补算历史日期时不得使用 D 之后的订单。共享模块 `stage()` 遇到末购晚于观察日会报错。

## 规则

一条规则 = 条件 + 动作 + 状态 + 优先级。

- 条件：游戏、价值档、阶段、新客/老客（可选）。只按系统计算的价值档匹配。
- 动作：发券（已批准的券模板，可为空）、预警（页面「待跟进」列表标红）、分配负责人（负责人名单可配置）。
- 状态：启用 / 停用。只有 FS 管理员能在页面上新建、修改规则或切换状态，服务端校验管理员身份。
- 超时自动发放开关：每条规则一个，默认关闭，只有管理员能切换（见「待发区」）。
- 同一事件命中多条规则时，按优先级从小到大处理。
- 预警和分配在事件生成后立即执行；发券必须经过下面的复核与确认流程。

## 发券流程（用户 2026-11-24 确认）

### 条目状态

每个「事件 × 规则（带发券动作）」生成一个发券条目，状态只能按下列方向变化，每次变化用一条带原状态条件的原子更新（`UPDATE … WHERE state = <原状态>`），更新 0 行即视为已被其他操作抢先，本次放弃：

| 原状态 | 可转到 | 触发 | 额度动作 |
|---|---|---|---|
| 待复核 | 待发区 / 暂缓（终态） | 程序复核结论 | 无 |
| 待发区 | 已确认 / 已剔除（终态）/ 已过期（终态）/ 超时自动确认 | 管理员操作或到期处理 | 无 |
| 已确认、超时自动确认、顺延 | 派发中 | 派发器认领，三项保护占用成功 | 占用客户额度与当日规则额度 |
| 已确认、超时自动确认、顺延 | 顺延 | 当日规则额度已满 | 不占用 |
| 已确认、超时自动确认、顺延 | 重验未过（终态） | 派发前重验不通过 | 不占用 |
| 派发中 | 已发放 / 待注册 / 限额 / 已拒绝 / UNKNOWN / 派发中（异步任务未完） | `grant` 或 `reconcile` 返回，见「提交与结果」表 | 见该表 |
| 待注册、UNKNOWN | 已发放 / 限额 / 已拒绝 / 已人工结清（终态） | 对账器 `reconcile` 返回，或管理员人工核对标记 | 见该表 |
| 待复核、待发区、已确认、超时自动确认、顺延 | 已作废（终态） | 事件作废、规则停用或回退 | 不占用 |

表外的转换一律拒绝。

### 步骤

1. **生成待复核**：每日运行后，启用规则中带发券动作的新进入事件生成「待复核」条目。
2. **程序复核**（用户 2026-11-24 确认：现有 Hermes 服务没有可合规调用的系统身份，本期改为程序复核；接入 Hermes 判断另立后续任务，见文末「后续」）：
   - 触发：每日运行结束后，由客户维护后台循环执行。操作人记为系统身份 `system-maintenance-review`，不调用 Hermes 对话服务，不使用任何用户会话、不冒用管理员。
   - 输入：确定性数据工具给出的证据包。证据摘要 = 证据包规范化 JSON（排序键、固定数值格式）的 SHA-256，覆盖全部检查项的实际内容，包括从 Admin 读到的人工券与售后记录，不只用版本号或时间戳。检查项：事件后是否有新的有效付款；是否有未结售后、退款或问题单；30 天内是否已收到过券（自动券看本地账本；人工券见下方「人工券数据范围」）；是否已有人在跟进并已联系。
   - **人工券数据范围**（用户 2026-11-24 确认）：Admin 代理账号目前没有 `user.MemberCoupon`（用户优惠券管理）读取权限，2026-11-24 在 187 实测 8911、8912 均返回 401；`market.CouponGrant` 没有可用的列表接口。本期人工券只用 `user.MemberCouponLog`（用券记录）检查「30 天内用过的人工券」，已发未用的人工券暂时看不到。这个缺口要在复核结论和页面上写明（例如「人工券：仅核对已使用记录」），不能把查不到当成「确认没有」。技术为代理账号所在的 Agent 角色开通 `user/memberCoupon/index` 只读权限、并经负责人从 187 复测通过后，另提小改动把发放记录接入同一检查项。
   - 判定：任一检查项命中即 `hold`，原因写明命中项与证据；全部未命中为 `pass`。
   - 去重：复核记录键 = 条目 ID + 证据摘要；同一键只保留一份结论。
   - 输出：结构化结论（`pass` / `hold`、原因、所用证据摘要）。写回前重新生成证据包并计算摘要，与结论所用摘要一致才写回，否则丢弃结论重新复核。
   - 失败：证据缺失（如 Admin 记录读取失败）或复核异常时，条目保持「待复核」，不自动通过；下次循环重试。
3. **待发区**：「通过」的条目进入待发区，记录进入时间。「暂缓」为终态，管理员可查看原因。
4. **管理员确认**：管理员在待发区全选一键确认，或逐条剔除。剔除写为终态「已剔除」，不是取消勾选。确认人记为该管理员的 FS 账号。
5. **程序发放**：按下面「派发」节执行，发放前再次重验。

### 待发区超时（72 小时）

- 到期时刻 = 进入待发区时间 + 72 小时。按**到期时刻**该规则的开关状态决定：开启则转「超时自动确认」，关闭则转「已过期」。开关每次切换都写入历史（时间、操作人、开关修订号），到期判定从历史中读取到期时刻的状态，不读处理时的当前状态。
- 停机跨过到期点的条目，在恢复后第一次循环按到期时刻的历史状态处理。例：12:00 到期时开关关闭，13:00 管理员开启，14:00 服务恢复，该条目转「已过期」。
- 超时自动确认的操作记录写「超时自动发放」，并记下到期时刻生效的开关修订号、开启人和开启时间。仍须通过派发前重验。
- 剔除、确认与超时处理竞争同一条目时，以原子状态更新先成功者为准。
- 开关切换不算规则内容变更，不影响「规则版本未变」的重验。

## 发券保护

以下三项在同一个 SQLite 写事务（`BEGIN IMMEDIATE`）中占用，在条目从「已确认 / 超时自动确认」转为「派发中」时执行，成功占用后才允许发券：

1. **事件幂等**：唯一键 `(customer_id, rule_id, 事件键)`，同一事件同一规则只执行一次。
2. **客户额度**：同一客户 30 天内最多一张自动券（跨规则）。30 天从「派发时间」（条目转为派发中、调用 `grant` 前写入账本的时间）起算，往后 30×24 小时内占用；派发中、已发放、待注册、UNKNOWN 都按此占用；限额和已拒绝立即释放。到账时间不另取（回执不提供，Admin 发放记录本代理无权读取）。
3. **规则日额度**：按上海自然日、按派发时间计每条规则的发券数。额度满时条目转「顺延」，不占任何额度；次日由派发器认领同一条目重新执行重验与占用，不新建。

## 派发

**派发前重验**（管理员确认、超时自动确认、顺延次日都在实际派发前执行，读最新数据，不复用复核时的证据）：

- 客户在事件之后没有新的有效订单（订单截至最近一次日更发布）。
- 按当前配置版本重算：客户仍在入池档位、仍满足规则的价值档与新老客条件，当前阶段不低于事件阶段。
- 复核之后没有新增的售后、退款、问题单、已联系记录或收到的券（自动券看本地账本，人工券按上文「人工券数据范围」）。
- 规则仍为启用，规则内容版本未变；券模板快照未变。
- 配置版本自事件生成后发生变化的条目，一律按当前配置重算上述条件，不满足即关闭。

任一不满足，转「重验未过」并记录原因，不发券。

**券模板核对**：规则启用时保存模板快照。派发前用 `coupon.detail` 重读，必须 `site_id=266`、`game_id=1327`、`fetch_scene=4`（定向券）、`status=1`、未过期，且与快照一致。`coupon.validate` 只作为附加检查（它允许 `site_id=0`，不能单独使用）。

**批次号**：`FCSM_` + 事件幂等键 SHA-256 的前 32 位大写十六进制，不含邮箱。发券桥只接受 `^FCSM_[A-F0-9]{32}$`。上线前先用一张测试券确认 Admin 接受该格式和长度。

**提交与结果**：

1. 提交前把批次号、规则版本、券 ID、收件邮箱、状态「派发中」写入本地账本并提交事务。
2. 调用 `grant(coupon_id, email, batch)` 一次，不自动重试。
3. 按发券桥返回的 `state`（`opt/mmoexp-lucky-loot/core.cjs::grantResult`）逐项处理：

| 返回 `state` | 含义 | 本地状态 | 额度 | 后续 |
|---|---|---|---|---|
| `confirmed`（带 `member_coupon_id`） | 已发到会员账户 | 已发放 | 占用（自派发时间起 30 天） | 无 |
| `pending`（带 `job_id`） | 后台异步任务处理中 | 派发中 | 占用 | 保存 `job_id`、邮箱、批次号，后台循环用 `reconcile({job_id, email, batch})` 查询直到明确结果 |
| `pending_register` | 邮箱尚未注册，后台已记录 | 待注册 | 占用（自派发时间起 30 天，到期自动释放） | 有 `job_id` 则按上行核对；无 `job_id` 则列入「待人工核对」，管理员在 Admin 按批次号核对后标记为已发放、已拒绝或已人工结清。不重发 |
| `limit` | 该邮箱已达此券领取上限 | 限额 | 释放 | 记录原因 |
| `rejected` | 后台明确未发放 | 已拒绝 | 释放 | 记录原因，页面提示管理员 |
| `unknown`、调用异常、超时、进程退出 | 结果不明 | UNKNOWN | 占用 | 有 `job_id` 按 `reconcile` 核对；没有则进入「待人工核对」，由人在 Admin 按批次号核对后标记。不重发 |

**执行身份**：复用 187 上 Lucky Loot / FC 社区赛奖励已在用的同一 HMAC 发券代理（`coupon.cjs` 的 `127.0.0.1:8911`），不新增凭据。上线前核实该身份具备读模板（`market.Coupon`）、导入发放（`market.CouponGrant/import`）和查任务（`jobStatus`）权限；缺任何一项先报告，不切自动。

## 分配与跟进

- 阶段维护的案件复用现有 `vip_cases` 与认领、反馈记录。同一客户在任一范围已有未结案件时，事件挂到该案件上，不新建；否则新建一个阶段维护案件。
- 「同一客户」只按已核邮箱（及其稳定 `customer_id`）判断，不使用现有 `same_buyer()` 的 UID 优先匹配。旧范围案件的邮箱与阶段维护客户唯一对应时才自动挂案；同 UID 不同邮箱、或一个邮箱对应多个旧案件时，进入「待核」由管理员处理，不自动挂案，也不把一个人的联系记录用于另一个人的发券复核。
- 规则分配只填空：只在 `owner IS NULL` 时写入负责人。人工认领与规则分配同时发生时，先提交的生效，另一方记为跳过。
- 改派是新增接口：只有管理员或 Hermes（见下节）可以调用，带期望的原负责人（CAS），不一致则拒绝。
- 反馈仍只能由当前负责人写入（现有规则）。

## 券模板

Claude 起草「档位 × 阶段 → 券面额 / 有效期 → 负责人」矩阵，用户确认后，由 Claude 在 Admin 按清单建券模板（site 266、game 1327、定向券），把券 ID 填入规则。建券前先核实现有账号有没有新建 `market.Coupon` 的权限；没有就报告，由用户在 Admin 建好后提供 ID。

## 效果

- **归因**：每张券按批次号关联用券记录，字段为 `memberCouponLog` 嵌套的 `memberCoupon.grant_batch_no`（沿用 `campaign-analytics-20261023/backend/campaign_backend/analysis.py` 的现有关联方式）。用券记录含未付款订单，「用券」与「用券并付款」分开统计；已发未用的券不出现在用券记录中，发放数以本地账本为准。
- **统计单位**：每个发券条目（事件 × 规则 × 规则版本）各算自己的窗口。
- **触发人群回购率**：每条规则只统计自己的条目；同一事件命中两条规则时，同一笔回购会分别出现在两条规则的触发人群里。因此页面只展示每条规则自己的回购率，不提供跨规则相加的回购人数或金额。
- **发券成功人群的回购归属**：一笔回购订单只归属一个条目，即该客户在订单付款前、窗口内最近一次「已发放」的条目；派发时间相同时取条目 ID 最小者。窗口外的旧发券不参与归属。按规则汇总的归属订单数之和等于去重后的回购订单数。
- **窗口**：从事件时间起算 7/30/60 天，只统计窗口已满且订单覆盖完整的事件。触发人群和发券成功人群分开统计。UNKNOWN、顺延未发的单独计数。回购为窗口内含 FC27 的有效订单。
- **基准**：用同一配置版本回算规则启用前同一档位 × 阶段的进入事件，按同样窗口统计回购率。不设随机对照组。页面同时标注当期所处赛季位置，提示赛季开启本身会拉高回购。

## Hermes 与连接器

**读**：分组名单、客户详情与时间线、规则效果、待复核与待发区条目。

发券流程中的「程序复核」是客户维护后台任务，不经过 Hermes，不属于下面的对话写入。Hermes 可以读取复核结论。

**写**：分配或改派负责人、写跟进备注、调整价值档。

- 写入只在 Hermes 会话能传递可信的 FS 用户身份时开放，操作人记为该用户；没有可信身份时拒绝写入，不用固定账号代替（遵守 AGENTS.md「不得通过固定 `wulv` 冒用调用者」）。
- 每次写入带 `request_id`，记录修改前后的值。撤回只在当前值仍等于修改后的值时执行（CAS）。
- 人工调整的价值档只影响名单展示和分配，不参与规则匹配，不会触发自动发券。

**不能**：新建或修改规则、启停规则或切换超时自动发放开关、在待发区确认、直接发券。服务端对这些接口校验管理员身份，与客户端限制无关。

## 配置编辑

客户维护页的管理员设置里可修改共享合同第 5、6 节的阶段天数和价值门槛，按共享合同第 8 节原子写入新版本。修改后，下一次每日运行按「配置版本变化 → 存量」处理，不会因改阈值批量触发发券。

## 发布与回退

- 二期在一期部署完成后发布。发布包按 187 当前已部署内容生成增量，只含二期目标；合并前在 PR 中列出每项的活动源路径和 187 运行目标（含导航生成物、Nginx 路由、IAM 策略、`catalog.json` 中 `customer_tracking.*` 条目）。
- **发放与对账拆开**：发券派发器和只读对账器是两个独立组件。对账器只读本地账本、调用 `reconcile`、更新结果，不发起新的 `grant`。
- **回退顺序**：
  1. 停用全部规则并关闭派发器（停止新派发），把待发区未派发条目转「已作废」。
  2. 回退页面、路由、导航和派发相关代码。按目标逐项核对 187 当前版本仍为本批发布版本后再退回；若某目标已被后续发布改过，停止该目标的回退并报告。
  3. 保留以下目标，直到所有派发中、待注册和 UNKNOWN 记录都得到明确结果或被人工结清：对账器、本地账本、额度占用、案件，以及最小人工核对入口（「待人工核对」列表页、其 Nginx 路由、管理员权限校验和结果写回接口）。
- 回退验收：回退后，一笔有 `job_id` 的在途记录能继续核对到结果；一笔无 `job_id` 的 UNKNOWN 记录和一笔无 `job_id` 的待注册记录，管理员仍能在人工核对入口打开并标记。

## 验收

1. 单测：
   - 入池与事件：按配置档位入池（含下调门槛、恰好达到门槛、金额未知订单）、阶段进入与存量判定（首次运行、配置变更、补档、退款更正、漏跑补算且不使用观察日之后的订单）。
   - 复核：每个检查项单独命中时为 hold 且原因正确；同一条目同一证据只留一份结论；只改变 Admin 人工券记录（订单与本地账本不变）时，旧结论因证据摘要不同被丢弃；证据缺失或复核异常时保持待复核。
   - 待发区：到期前剔除后不再发放；到期临界时切换开关；停机跨过到期点后，按到期时刻的开关历史处理——到期时关、之后改开的条目转已过期，到期时开、之后改关的条目转超时自动确认；确认与超时竞争只有一方生效；表外状态转换被拒绝；顺延条目次日重新占用。
   - 派发：复核后收到人工券或新增退款时重验不通过、退款使累计消费跌破门槛时重验不通过、配置变更后的旧待发条目按新配置重算、顺延后第 29 天再次命中时额度拦截、三项保护的并发占用。
   - 发券结果：`confirmed`、`pending`、`pending_register`（有/无 `job_id`）、`limit`、`rejected`、提交后断连各一例，状态与额度动作符合上表，均不重发；无 `job_id` 的待注册在派发 30 天后释放额度。
   - 效果：同一事件命中两条规则时，发券成功人群的按规则归属订单数之和等于去重回购订单数。
   - 其他：模板核对、批次号格式、同 UID 不同邮箱不自动挂案、规则分配只填空、改派 CAS、Hermes 对话无可信身份时拒绝写入、人工改档不触发发券。
2. 首次上线：规则启用后跑一个自然日，人工抽查 20 个客户的档位、阶段、事件与程序复核结论；当天待发区不确认，验证 72 小时到期按开关处理。
3. 真实发券：用户在待发区确认一批（建议先少量），核对 Admin 发放记录与本地账本逐条一致；模拟一次提交后进程退出，确认进入 UNKNOWN 且未重发。
4. 真实入口：新地址可打开、旧地址跳转、导航在新位置、两份周名单功能不受影响、连接器 `customer_tracking.*` 可用。

## 后续（不在本期）

**Hermes 复核接入**：在 Hermes 服务中新增专用系统身份，权限只含「提交维护复核」与「按原请求 ID 查回执」，经安全审查后，在程序复核之上叠加 Hermes 判断（例如结合跟进备注）。程序复核的检查项与结论保留为底线：Hermes 只能把 `pass` 改为 `hold`，不能把程序判定的 `hold` 改为 `pass`。单独立项、单独合同。
