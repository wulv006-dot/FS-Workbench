## 1 交付目标

顾客在 187 托管的 MMOEXP 活动页选购商品，活动配置由 FS 维护，商品和优惠管理复用 Admin。选购结果通过统一接口进入主站购物车，由主站执行最终价格、合法优惠组合、支付及订单履约。FS 根据 Admin/Order 的实际优惠和付款结果统计活动订单。

本合同定义双方接口语义和验收结果。以下操作名及 JSON 字段属于**拟建设的统一合同**，不是现有 Admin/Order 的真实路由声明。正式 URL、请求方法、原字段映射由适配实现填入，不猜测接口。

### 1.1 双方分工

| FS / Work 交付 | 主站技术交付 |

| 已接受的全部页面、JS/CSS、素材、SEO及187运行服务 | 正式域名关联、购物车/结算的正式接入 |

技术收到的页面用于接入和联调。正式内容继续由 FS 在 187 发布，避免同时维护两套活动页面。

## 4 T02 商品报价和购物车交接

### 4.1 产品引用结构

```json
{
  "product_ref": {
    "site_id": "<主站站点ID>",
    "game_id": "<Admin游戏ID>",
    "model_id": "<模型ID，如有>",
    "goods_id": "<实际在售商品ID>",
    "sku_id": "<实际规格ID，如有>"
  },
  "platform": {
    "code": "ps",
    "attribute_id": "<真实平台属性ID>"
  },
  "quantity": {
    "value": "1",
    "unit": "item",
    "group": "<主站购买数量组，如有>"
  },
  "attributes": [
    {"attribute_id": "<规格属性ID>", "value_id": "<选项ID>"}
  ]
}
```

不存在的可选字段省略，不以虚构 ID 补齐。规格的最终 `attr` 或其他购买参数由适配器序列化，不让页面拼接未经校验的后台参数。

“已拥有 SBC 核心”的选择不应出现在实际购买行。既有固定包沿用主站真实包商品；临时拼选的几张卡保持各自原商品行，不能为了展示组合自行制造主站 SKU。

### 4.2 权威报价操作 quote

**输入**：

- `request_id`、`intent_id`。
- 商品行 `line_key`、完整产品引用、数量和属性。
- 目标币种。
- `activity_id / page_id / rule_version / benefit_binding_version`。
- 主站可信身份或会话引用（需要时）。
- 顾客已选择的其他券码或权益引用（接口支持时）。

**主站职责**：

- 确认产品、规格、平台和数量有效。
- 读取当前真实售价和已发布活动规则。
- 校验优惠适用范围、新客/会员资格、互斥、门槛、限额及品类保护。
- 计算统一币种和精度下的实际金额。
- 返回报价ID、版本、有效期、商品行及优惠拆分。

**响应示意，金额为虚构测试值**：

```json
{
  "status": "quoted",
  "quote_id": "test_quote_01",
  "currency": "USD",
  "minor_unit_scale": 2,
  "expires_at": "<服务端时间>",
  "rule_version": "test_rule_v1",
  "lines": [
    {
      "line_key": "line_1",
      "base_minor": 10000,
      "adjustments": [
        {
          "kind": "activity",
          "benefit_ref": "test_activity_benefit",
          "activity_id": "test_activity",
          "amount_minor": 1000
        },
        {
          "kind": "code",
          "benefit_ref": "test_main_code",
          "amount_minor": 450
        }
      ],
      "payable_minor": 8550
    }
  ],
  "payable_minor": 8550,
  "authoritative": true
}
```

前端自己的估算值不能放进权威报价字段。价格变化必须返回新报价并让顾客看到变化；主站创建订单时再次核验报价，不能无限使用旧报价。

### 4.3 选购交接 prepare_checkout

FS服务端向主站发送：

```json
{
  "operation_id": "<稳定唯一操作ID>",
  "intent_id": "<FS选购意图ID>",
  "quote_id": "<主站报价ID>",
  "activity_id": "<稳定活动ID>",
  "page_id": "<页面ID>",
  "rule_version": "<已发布规则版本>",
  "lines": ["<结构同产品引用，带line_key>"],
  "return_route_id": "<预登记返回路径>",
  "analytics_context": null
}
```

`analytics_context` 可选，不影响合法优惠资格。主站返回短期、可限定用途的交接凭证或正式交接URL。URL只携带不含身份、原始券码和商品金额的短期引用；不得把客户邮箱、后台Token放进URL。

主站收到浏览器交接后，在自身会话中完成受保护的凭证兑换和购物车写入。GET入口不因链接预加载直接新增商品；写操作需要现有请求校验和幂等保护。

### 4.4 幂等和原购物车

- 同一 `operation_id` 配同一内容重试，返回同一业务结果。
- 同一 `operation_id` 配不同内容，拒绝为冲突。
- 网络未知状态通过 `lookup_checkout_operation` 查询原操作，不能换ID盲重发。
- 保留原购物车已有商品；活动价只作用于适用商品和对应数量。
- 同一SKU分别从不同活动加入，或部分来自非活动入口，不能在合并行时丢失优惠归属。
- 首选整批校验成功后入车；若现有系统只能逐行，返回每行 confirmed/rejected/unknown，不能把部分成功报为全部成功。

### 4.5 登录和游客

普通商品选购尽量延续主站现有游客/登录流程。需要登录时保留原意图和报价上下文；报价过期则重新核算。

不要求将客户Cookie复制到187，不要求浏览器持有Admin凭据。已登录状态是否可直接延续由主站当前会话机制验证，不能仅凭“同一品牌子域名”保证。

## 5 T03 活动优惠和主站优惠执行

### 5.1 使用现有规则，不重复维护

FS 为活动配置入口，主站为最终执行者。原生Admin券/码直接绑定真实ID。需要额外活动优惠层时，主站接收结构化活动规则或读取已发布副本，避免每次结算依赖FS管理页面在线。

主站读取的发布版本应有可核对的版本/摘要及生效区间。发布或停用需返回实际状态；“API收到请求”不等于“已生效”。

### 5.2 叠加语义

现有活动设计为：当前售价上的额外10%，再按主站原规则处理coupon、code、points。以下行为必须明确：

- 活动优惠不占用或覆盖主站唯一普通优惠码槽位，除非双方正式选择了不同玩法。
- 原主站互斥规则保持，不能解释为券、码、积分任意同时使用。
- 门槛按活动前或活动后金额，封顶按行或按单，先后顺序和舍入由合同固定。
- 新客/会员资格由主站实际身份和历史判定。
- 不直接把全站SKU基价改低来实现某活动专属优惠。
- 各品类按已有保护规则执行；Players/SBC/Packs不自动套用Coins利润底线。

若某一组合未支持，返回 `STACK_NOT_ALLOWED` 或明确的能力缺口。不能先用客户端算出“已省金额”，再让付款时无提示消失。

### 5.3 规则和订单冻结

商品加购不等于永远锁价。报价有效期内如何保价、订单创建后支付有效期、活动结束前已创建订单是否保留优惠，必须采用主站既有规则或在此明确新增规则。

每笔订单至少能追溯活动规则版本、实际应用优惠引用、实际优惠金额和付款金额。售后不按当前活动配置重算历史订单。


## 6 T04 订单优惠回读与活动识别

### 6.1 首选现有后台读取

不要求为了上线另建一套订单系统或先开发Webhook。FS优先读取Admin订单和用券日志，再由Order补充详情/成本。

现有已观察到的关联字段：

| 原字段 | 已知用途 |
|---|---|
| `order_no` | 关联Admin订单与用券记录 |
| `discount_code` | 订单使用的折扣码引用 |
| 券日志 `id` | 日志唯一标识 |
| `coupon_id` | 券模板引用 |
| `memberCoupon.grant_batch_no` | 发放批次 |
| `use_time` | 使用记录时间，不能独立代替付款时间 |
| `site_id` | 校验主站范围 |
| `paytime / pay_status` | 主站付款时间和状态，状态枚举以现场为准 |
| `amount_usd_format` | 当前代码读取的订单美元金额字段，实际金额口径按原后台确认 |

券日志未在已读源码中保留完整活动层金额分摊，因此主站必须确认订单详情是否已有该信息；没有时补齐，不把字段名凭空写成已存在。

### 6.2 正式对账需要的语义

接口可以复用现有路径，但至少应支持恢复以下事实：

- 主站站点、稳定订单号、原订单商品行引用。
- 原付款状态、实际付款时间、订单原币种与实付。
- 已实际应用的活动规则、券模板、会员券/批次、折扣码等引用。
- 活动优惠金额，以及其他优惠分项。
- 可用时返回活动商品行实际分摊后的实收。
- 取消、退款、优惠撤销、状态更新时间。
- 可用时返回订单实际附带的活动ID及规则版本。

不能用“订单总共减了10%”识别某个活动。

### 6.3 归因合同

`已支付活动订单 = 实际应用活动绑定优惠 + 主站有效付款`。

活动页浏览记录不是必要条件。对已付款且命中活动专属优惠的订单，即使没有访问ID，也按用户要求计入活动来源。

原自然/广告来源字段保留供原经营分析使用；新增活动归因字段和“活动来源”视图，避免重写Admin原始来源。活动优惠来源与浏览器访问来源可以同时存在。

三页当前共用上层 `fc27-season2` 促销设计。若需区分 `fc27-weekly / fc27-sbc / fc27-trio`，应分配可区分的活动规则引用、模板或批次。若暂时只有共同引用，只能归到活动组；不能用最后打开页面猜测分配。

### 6.4 金额与退款

- 展示“关联整单实收”和“活动商品实收”两个不同指标。
- 没有行分摊就显示待分摊，不能把混合订单全额说成活动商品收入。
- 多活动命中同一订单，全局订单数与实收去重。
- 已经是实收的字段，不再扣一遍优惠。
- 原币种、Admin美元折算和Order人民币成本不能混加或直接相减。
- 退款使用原订单关联及稳定退款引用，不删除原付款事件，不因多次轮询重复扣减。

## 9 T07 可选通知与已有分析

Webhook或服务端事件用于缩短付款、退款、发奖结果的显示延迟，属于可选增强。没有它时，原后台增量拉取加对账仍可完成基础业务验收。

如增加通知：

- 服务端鉴权和验证签名/受控凭证。
- 通知ID、订单/操作引用、状态版本、真实发生时间。
- 重复、乱序和重试不产生第二笔业务事实。
- 收到通知仍可从原后台查询核对。
- PostHog付款事件只从可信服务端事实产生，不由浏览器点击触发。
- 无行为上下文的优惠订单不伪造distinct_id或访问事件。

## 10 能力状态与失败结果

### 10.1 能力状态

FS与页面根据主站真实能力回执开放功能，建议字段：

```json
{
  "integration_mode": "integration_test",
  "adapter_version": "test-v1",
  "capabilities": {
    "catalog_read": true,
    "authoritative_quote": false,
    "campaign_discount": false,
    "stacked_discounts": false,
    "cart_handoff": false,
    "member_identity": false,
    "coupon_management": true,
    "order_discount_readback": true
  },
  "verified_at": "<最近真实核对时间>"
}
```

这是能力结构示例，布尔值不是本次现场验收结论。模式和能力由服务端配置及验证决定，浏览器不能自行把false改成true获得权限。

### 10.2 统一失败语义

| 结果 | 页面/FS行为 |
|---|---|
| `MAIN_INTEGRATION_REQUIRED` | 标明主站未接入，内部预览可继续 |
| `PRODUCT_UNAVAILABLE` | 仅对应商品不可结算 |
| `SPEC_REQUIRED / SPEC_INVALID` | 引导补齐或重新选择规格 |
| `PRICE_CHANGED / QUOTE_EXPIRED` | 展示新报价并重新确认 |
| `RULE_VERSION_CONFLICT` | 刷新当前活动规则，不静默换版本 |
| `PROMOTION_EXPIRED` | 说明活动已结束，不继续承诺优惠 |
| `STACK_NOT_ALLOWED` | 说明不适用组合，按主站规则重新报价 |
| `IDENTITY_REQUIRED` | 走主站登录并保留意图 |
| `OPERATION_UNKNOWN` | 保存原操作ID，查询后再决定 |
| `REQUEST_CONFLICT` | 拒绝同操作ID的不同请求 |
| `UPSTREAM_UNAVAILABLE` | 显示暂不可用，不返回假成功 |

返回应包含可对账的request/operation引用、机器可读状态和适当的用户提示，不能在公开错误中泄露后台URL、Token或内部堆栈。

## 11 联调顺序

1. Work交付完整页面、候选配置、产品与优惠映射、测试适配器和本文。
2. 主站先返回正式路由及字段映射，双方锁定合同版本。
3. 接通商品报价与购物车；核对平台、数量、规格、旧购物车和重复请求。
4. 接通活动优惠与合法券码组合；核对规则版本及金额样例。
5. 从Admin/Order订单详情读回实际优惠并进行活动来源识别。
6. 核对两个原任务需要的正常购物会话、活动券及订单归因，排除竞猜与竞猜奖励。
7. 配置正式域名并切换真实适配器，完成两个任务逐页交易与活动优惠核销。
8. 验证失败、暂停、到期、退款和回退，不扩大到无关系统重构。

接口形态可适配主站技术栈，语义、身份边界、实际优惠证据和验收结果不可省略。

## 12 双方验收清单

| 用例 | 通过条件 |
|---|---|
| 普通活动商品 | 正确商品/规格/数量进入主站购物车 |
| 活动优惠 | 主站计算并记录真实活动减免 |
| 活动加5%码 | 测试基价10000、活动10%再码5%，应付8550 |
| 混合购物车 | 活动商品10000与非活动商品5000，活动后全单码5%，分别实付8550与4750 |
| 不允许组合 | 明确拒绝/选择有效组合，页面不承诺未兑现优惠 |
| 重复交接 | 同操作重复请求不重复加购 |
| 超时未知 | 原操作可查询，不靠重新下单解决 |
| 游客与登录 | 原有购买流程可用，登录不丢失选购意图 |
| 无浏览记录 | 真实优惠订单依然进入活动订单统计 |
| 通用券误匹配 | 未绑定该活动的通用券不归入 |
| 同优惠多页 | 页面级可区分；无法区分时诚实汇总到活动组 |
| 混合/多活动订单 | 整单与活动行实收清楚，全局不重复 |
| 退款 | 后台状态及实际金额更新正确 |
| 到期/暂停 | 旧链接不能获得新的失效优惠 |
| 数据与模式 | 预览/联调不进入正式成交数据 |
| 公开/管理隔离 | 顾客页面无法读管理密钥和后台原始数据 |
| 两任务范围 | 全部原页面按清单验收，不只验一个样板页 |

最终验收分别记录“页面完成、数据读写接通、187部署读回、主站交易接通”。只有四项均满足，且所有必需玩法通过，才将对应任务标为上线完成。
