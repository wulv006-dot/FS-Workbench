# Admin 逐笔订单查询边界

### Admin 逐笔订单查询的一个月上限（2026-10-21 实测）

`/admin/order.Order/index` 在支付时间 `paytime` 为 2026-09-17 至 2026-10-20 的真实只读请求中，返回 HTTP 200、`code=0`、`data=null`，错误为“下单时间查询范围不能超过一个月，请按月查询或缩小时间范围”。这是接口范围拒绝，不能当作登录失效、空订单或响应截断，也不能靠延长超时消除。

长区间逐笔订单查询采用按自然月切分的保守方案，每段保留游戏、站点、状态、实际时间字段和时区，完成分页、范围、重复订单及数量完整性检查后才能合并；任一段失败必须标为不完整，不能跳过异常行或放宽校验后发布。服务端精确按滚动天数还是自然月判定尚未核实，不能据此认定所有跨月查询都被禁止。

限制仅有上述逐笔端点的证据，不推广到 Admin 原生经营汇总、ES 导出或 Order 服务。原生汇总已有 34 天及 112 天完整返回的单次证据。继续通过全局 Admin 8767 消费现有会话，不恢复独立登录入口。

付款状态还需逐行核验：实测该端点在 `pay_status=1` 筛选中混入 `pay_status=2`、标签 `Refunded` 的记录，触发原 `cohort_paid_scope`。付费投影只纳入状态1；退款状态2须经过同样的游戏、站点、时间、身份、排序及分页校验后单独计数排除，未知状态继续失败。`source_scanned_total`/`source_scanned_received`记录完整源枚举，`source_total`/`received`记录付费投影，`excluded_refunded`记录排除退款，两者必须对账；不能直接用宽筛选总量当付费总量。这一投影不改写原生经营总盘或其他模块退款口径。规则确认、知识同步、补丁上线和真实完整取数/模型掌握分别验收，部署结果见本次修复验收记录。
