### 0.1 最新要求：限额不要卡死，给正常任务留空间

**资源受控不等于把任务限制到做不完。**旧版的1GiB新增内存、4GiB磁盘、32MiB缓存、200次请求、5个回填日、10分钟回填、8次Search/12次Fetch及240秒分析等数值，改为起步估算、调优参考或预警参考，不能不经现场核验就写成“到数即停”的业务拒绝条件。

超出常态参考，先观察增长、释放已处理对象、减少并发、分批、清理可再生缓存；仍有安全余量时让正常任务继续。只有达到实测配置的应急保护、上游真实限制、实际授权费用边界，或确实无进展/失控时才暂停相应任务。不得为了保持“未超参考数”悄悄漏采四游戏数据、删核心历史或截断正常推理。

## 3. “昨日”与“凌晨采集”的精确定义

### 3.1 四个日期字段必须分开

- `publication_date`：快照在北京时间哪天供团队使用，记为 T。
- `report_date`：业务目标统计日，D=T−1。
- `source_date / source_timezone`：上游真正统计的日期及时区。
- `observed_at / collected_at`：实际观测或读取时刻，UTC保存，界面可转北京时间。

例如，系统若于2026-11-04启用，第一次正常夜间批次为2026-11-05：业务统计目标为11月4日，初始30天目标窗口为**10月6日—11月4日**。这只是说明日期算法，不表示已经部署。实际启用日期由安装回执确定。

### 3.2 不能保证全部来源凌晨都提供完整昨日

GSC Search Analytics 按太平洋时间解释日期，官方也提示性能数据通常延迟2—3天；GA4报表处理可能需要24—48小时，处理期内数值会改变。[S1][S2][S3]

因此本版采用：**昨日是目标，不是伪造完整性的承诺。**

| 来源 | 今日快照如何展示 |
|---|---|
| Admin/Order | 取北京时间D的付款事实；按上游可用程度标记已取到/部分 |
| GA4 | 查询D日；有数但仍会处理则标“昨日初步值”；没有则标待上游发布 |
| GSC | 默认读取已结束、已提供的`final`源日；展示实际源日期，不改写成北京时间昨日 |
| 缺失昨日 | 昨日格为空，显示原因；最近可用数据只在单独标日期的区域展示 |
| 迟到/修订 | 下一夜修正历史，生成下一份快照；不在今天白天覆盖 |

在2026-11-05 03:20北京时间，洛杉矶还是11月4日11:20。那里的11月4日尚未结束，不能要求此时已有完整的GSC“11月4日”。本期不拼小时数据强行换算自然日，也不把GSC和北京时间订单做严格同日漏斗。[S1]

### 3.3 排名、页面状态没有“倒查昨日”的魔法

普通 SERP、页面探测和网页Fetch拿到的是**实际请求时点的状态**。没有已有历史样本，就不能把凌晨T的结果标成D日的排名或页面状态。

为严格执行“只用昨日数据”，本版默认采用**时点样本延后一日展示**：

| 夜间批次 | 本次新增观测 | 本次发布使用 |
|---|---|---|
| 11月5日凌晨 | 保存11月5日排名/页面样本 | 使用11月4日已存在的样本；没有则显示尚未积累 |
| 11月6日凌晨 | 保存11月6日排名/页面样本 | 使用11月5日凌晨实际采到的样本 |

这是“昨日一次采样”，不是“昨日全天平均排名”。新增观察记录留在工作区供下一夜使用，当前正式快照不暴露它们。

DeepSeek Search/Fetch的正文也记录实际观察时间；查询`before:`或找到旧文章，不证明网页当时内容或当时排名。新研究素材保存在独立AI工作区，在本期严格模式下到下一夜才作为历史研究证据使用，不回写基础快照。Hermes当夜可直接分析已发布的昨日事实；关闭AI时不采集这类研究素材。

## 4. 独立日更流程与日间冻结

### 4.1 基础链不再等待Hermes

唯一每日外部定时入口仍是`seo_daily_batch(publication_date)`，建议北京时间03:20由**FS侧现有调度器**启动，不注册到Hermes内部定时器。若当前定时入口实际由Hermes进程托管，需将这个SEO批次移到独立FS任务入口；不用四个游戏分别建timer。

**基础执行顺序：**资源检查与数据锁 → 昨日/近期纠错 → 有限回填 → 独立SERP/页面时点观察存入次日待用区 → 程序计算及规则提醒 → 校验 → 原子发布数据快照 → 本层清理与备份 → 退出。

基础发布成功后，由FS任务设施在本夜**非阻塞地**尝试提交独立AI任务；AI投递失败、队列不存在或Hermes不在线，只影响增强状态。不得把提交写成核心worker必须成功的最后一步，不得让AI异常改变`data_run=success`。基础清理和备份也不等待AI。

**可选AI顺序：**读取已发布`snapshot_id/facts_hash` → 检查当前开关/权限/预算 → 按开启游戏串行子任务 → 分游戏写独立不可变报告 → 本地状态汇总。只读当前包，不读取可变工作库。

### 4.2 时限与唯一发布

基础数据有效即发布，不等AI或最晚时点。基础发布最晚06:30，07:00前结束本批采集子进程；正式AI产物仍在06:30前封存。旧版06:10/06:20的停止新任务时点改为调度参考：根据任务预计耗时和可配置收尾余量判断是否来得及，不因距某个参考分钟还有一秒而机械拒绝。单游戏240秒仅作耗时观察点；有心跳、有效进展且仍在夜间时段与已授权费用内，可继续执行。无进展超时与最终墙钟截止独立配置，最晚不得越过本夜AI封存时间。基础发布太晚时跳过来不及完成的增强，不延迟数据发布，不在白天补跑。

每晚额外Google/Admin的200个请求、每来源5个回填日期及10分钟，只作为首次试跑的负载参考，不作为固定上限。在当前四游戏/30天范围内，只要上游配额、宿主余量及夜间时间允许，可以在本夜继续完成更多分片，甚至一次补齐。优先保证昨日数据和发布，临近收尾、上游限流或实际资源紧张时保存游标到下一夜；不能仅因到了参考次数就把完整可采的数据截成一半。

基础批次幂等键为`seo_daily:{site_scope}:{publication_date}`，不允许改配置版本绕开同日唯一数据发布。AI按`(snapshot_id, game, analysis_kind)`去重；已尝试且结果不确定的模型任务不盲目重发。参数/开关版本记为任务证据，不作为反复收费的变通方式。

只读源重试先用少量退避作为默认，重试次数和总耗时可配置，并遵守上游限流与本夜截止，不设置无限重试。401/403和明确不支持的接口不盲重试；付费请求提交状态未知时先对账，不因放宽次数而重复下发。夜间崩溃可恢复未完成数据批次；白天不补跑。白天恢复的Hermes也不追跑所有历史AI任务。

### 4.3 白天的固定数据与动态控制分开

指标、趋势、分页、证据和正式日报正文各自固定到版本，浏览器刷新、筛选、导出、缓存过期及服务重启均不得回源。共享FS数据白天更新也不得改变SEO快照。

开关、成员权限、任务负责人、处理状态和AI“关闭/故障”标识属于**控制与协作状态**，允许白天即时变化；不能把“数据冻结”解释成下午关闭AI必须等次日才生效。

不提供“立即采集/实时模式”，不注册旧版`seo.request_refresh`。总开关或游戏开关关闭时，也不接受该范围的AI聊天、联网研究、自动建议或新AI调查排队。已启用范围的白天主动问答，只能使用固定快照，可能发生模型推理费用，但不能联网补证或改正式日报。

一次数据发布后不再发第二个数据版本。重大事实错误可按既有授权撤销并回滚旧快照，保留真实日期；AI报告错误只能撤销对应AI产物，不得回滚正确基础数据。

| 来源 | 首次如何处理 | 不可用时 |
|---|---|---|
| GSC | 查询目标近30天已有日级表现，保留源时区和实际完整日期 | 缺日期留空；无权限标权限缺失，不判成零 |
| GA4 | 回读近30天已有报表与兼容指标 | 没有埋点的历史不能事后补造 |
| Admin/Order | 优先共享汇总，再按日/分页读取最低必要字段 | 历史来源字段缺失时付款可有、SEO归因仍未知 |
| SERP排名 | 只有已有精确匹配条件的历史样本才可导入 | 从首次真实采样日期开始；不采购历史包作为上线前置 |
| 页面状态 | 仅导入有日期与证据的旧探测结果 | 从首次探测积累，不通过当前HTML倒推旧状态 |
| 外部内容素材 | 可收录历史文章，但其发布时间与抓取时间分开 | 不把旧文章当历史排名/每日热度观测 |
| Hermes报告 | 可以回顾已有历史事实 | 标“回顾分析”；不伪装成30份当时生成的日报 |

某来源只有7天，就显示7天；其他来源已有30天照常展示。回填失败不删除已成功历史，也不把四游戏都重置到今天。

### 5.2 有界回填算法

首次固定 `tracking_started_on=实际启用日`，每来源另存`first_observed_date=第一次真实取得样本的日期`；启用日不自动生成一条观测，首个夜间样本晚一天就据实晚一天。第一批目标窗口为 `[D−29, D+1)`，共30个日历日；任务记录该固定窗口，不每天把起点往过去挪。

优先处理昨日与最近7天，再向前补。每个来源保存日期、分页游标、完成状态和错误原因；中断后只补未完成分片。白天不继续回填。

可恢复错误在后续夜间重试；确认没有历史/无对应埋点的日期标记`not_available_historically`，不每天重复请求。配置或权限恢复时可在后续夜间重新判断，不无限死循环。

UI同时显示“目标30天、可用X天、缺失Y天、最早有效日期、回填状态”。区间比较只用实际可比的完整窗口；上线三天不能显示可信的7日环比或28日行动效果。

### 5.3 日常纠错不是重新抓30天全明细

每日必做D日统计。对GSC/GA4小型日级汇总滚动复核近14天，对高维明细只重取发生变化、缺失或尚未完成的日期；每游戏先按少量日期切片起步，有实际变化且资源允许时扩展本夜处理份额。不能把“2个切片”写死为发现更多迟到数据也不得修订的规则；仍不无差别重抓30天全部高维数据。

Admin优先使用现有`updated_at`变更通道和订单ID去重，游标截止为当晚读取边界；只纳入已发生在D及以前的业务事件。只有无此能力时才采用有限支付日期回看，并如实标明旧退款修订覆盖不足。

历史修订先进入工作区，再进入下一份每日快照。保留“昨日公布值/本次修订原因”的最小日志，不复制每一次完整历史库。

## 6. 数据调取路径与查询合同

### 6.1 先复用缓存，但不能复用错口径

推荐链路为：`SEO夜间任务 → FS现有只读访问/缓存 → 必要时真实上游 → 最小事实与聚合 → 候选快照`。

共享缓存必须匹配来源、站点、游戏、维度、日期、时区、过滤、币种、归因版本。白天共享数据即使更新，也不改变SEO已发布快照。

### 6.2 GSC：搜索表现

```text
POST https://www.googleapis.com/webmasters/v3/sites/{encoded_site_url}/searchAnalytics/query
授权：现有Google只读身份；默认dataState=final；type=web；逐页读取。
```

参考资源为历史配置 `sc-domain:mmoexp.com`，现场核验。域资源不等于www主站；按授权资源和过滤正确限定范围。带页面过滤时不能强行使用不支持的聚合模式，记录返回的`responseAggregationType`。[S1]

| 报表 | 推荐粒度 | 作用 |
|---|---|---|
| 搜索总量 | 源日期＋必要国家/设备 | 搜索点击、展示趋势；不由Top关键词强凑总量 |
| 页面表现 | 源日期＋页面＋必要国家 | 映射四游戏、寻找点击率与内容机会 |
| 重点词 | 源日期＋已配置词＋国家/设备 | 重点词趋势；与SERP固定名次分开 |

不全量展开“词×页×国×语言×设备”。分页完整不意味着搜索词全集完整；GSC可能仅返回受限的高位行。[S1][S2]

每页默认500—1000行，提取点击、展示、位置加权分子与实际日期，处理后释放，不积累全量`rows`数组。没有记录不能一律认定为0。

### 6.3 GA4：自然搜索行为

```text
GET  https://analyticsdata.googleapis.com/v1beta/properties/{property_id}/metadata
POST https://analyticsdata.googleapis.com/v1beta/properties/{property_id}:checkCompatibility
POST https://analyticsdata.googleapis.com/v1beta/properties/{property_id}:runReport
```

参考property为历史配置 `541418940`，现场核验。只使用`runReport`等常规报表，不接`runRealtimeReport`。

过滤主站与`sessionDefaultChannelGroup=Organic Search`。日期使用property时区；若与北京时间不同，保留差异，不直接改property时区以迁就本模块。

优先读取`date/country/landingPage/deviceCategory`与`sessions/engagedSessions`；购物车、购买、收入、交易ID分组先验证兼容性和埋点。可选字段包括`addToCarts`、`ecommercePurchases`、`purchaseRevenue`、`transactionId`；支持时读取会话购买关键事件率。[S4]

与GSC对照时可单独看Google自然搜索；所有搜索引擎自然访问不能冒称全由Google贡献。保留抽样、阈值、其他行、分页和配额标记；调用额度与模型Token不是同一种东西。[S5]

### 6.4 Admin/Order：付款与归因

```text
SEO夜间任务 → FS业务只读适配器/缓存 → 现行Admin直接API/HMAC → 必要时Order补源
```

历史接口线索为`order/order/index`、`order.Order/orderStaticsDetailByEs`；实际大小写、参数、支付状态、日期分页和站点范围由现场合同确认，不猜一个已经存在的SEO订单接口。

最小字段：站点/排除分销依据、订单引用、支付时刻、更新时刻、付款状态、实际金额与币种、退款事件、商品行与购买游戏、原记录来源、可用交易/结账关联ID。SEO不保存用户姓名、邮箱、电话、IP或支付资料。

归因分层：

| 层级 | 依据 | 展示 |
|---|---|---|
| A | 后台留存的来源或结账关联证据可确认自然搜索，且已付款 | 后台可验证自然搜索成交 |
| B | GA4自然搜索交易ID与后台已付款订单准确匹配 | GA4归因、后台付款核验 |
| U | 空来源、缺字段、无法匹配或冲突 | 归因未知，不能叫SEO收入 |

A/B先按订单去重，冲突单列。空来源的旧经营规则不变。`landing_game`与`purchased_game`分别记录：从FC27页面进入买D4，不全归FC27商品收入。四游戏订单有交叉时，游戏订单数不可直接相加充当去重总订单数；金额按真实商品行分配并核对合计。

付款、退款、手续费、税和USD换算沿用FS原规则，绝不让AI猜金额。GA4购买事件次数不代替后台实际付款事实。[R1]

## 7. Hermes、DeepSeek与可选排名源

### 7.1 复用供应商不等于依赖Hermes进程

**Google/Admin/Order/SERP与页面探测由FS程序直接调现有数据适配器，不通过Hermes聊天、模型工具选择或记忆。**鉴权使用原FS身份/凭据设施；有某个源当前只有Hermes封装入口时，应复用其底层只读访问实现并解除启动依赖，不能仅换接口名字。基础字段与游戏映射由配置/规则确定，无法映射标未知，不等待模型猜分类。

可选分析继续走用户现有Hermes Provider与费用账本。W0只核验供应商标识、功能、base URL类型和使用回执，不输出密钥。SEO仅引用现有受控供应商配置，不复制第二套Key。

**本版DeepSeek Search/Fetch归入AI内容研究；关闭该游戏AI后同步停止。**无需为了它强配Bright Data。若未来某个基础数据任务明确需要独立Search/Fetch，可通过共享凭据引用设计程序直连，但必须单列数据源开关与费用；本期不默认实施，也不能在AI关闭时偷偷改成直连继续研究。

模型Key失效、Hermes配置缺失只影响AI；数据凭据不能通过活跃Hermes会话临时领取。

DeepSeek官方提供独立Search/Fetch端点，和模型接口使用同类Bearer鉴权；它们返回网页检索/内容，并不是Google固定条件排名。[S6]

```text
官方参考：POST https://api.deepseek.com/v1/tools/search
官方参考：POST https://api.deepseek.com/v1/tools/fetch
```

若当前为第三方中转，聊天成功并不证明Search/Fetch可用。须按当前供应商真实支持情况验证；不擅自把中转Key发给官方域名，不自动购买新账户，不复制第二套凭据。

功能不支持时：Hermes仍分析已有FS数据；研究区标未接入。核心看板不被阻塞，不能把模型回答当成成功搜索证据。

### 7.2 夜间研究的边界

仅对开启AI的游戏，Search 8次、Fetch 12次是四游戏合计的起步用量测算，不是任务停止线。按问题需要、已有证据和实际已授权供应商额度动态分配；证据不足但还有合理调查价值时，可以在允许范围内继续，不因第9次搜索或第13次抓取被机械拒绝。数据hash未变或证据足够时停止重复研究。Search默认`need_content=false`，必要页面再Fetch；按响应字节与可用内存控制读取，正文通常不长期落盘。[S6]

研究结果保留URL、发布时间（若有）、实际观察时间、摘要、证据范围、来源。根据第3.3节，新时点材料到下一夜才供正式历史对比使用。材料保存在AI自有区；基础发布器不读取其数据库、不等待其完成、不因其损坏报错。

技术SEO的HTTP状态、robots、canonical等以轻量直接HTTP检测为准；Fetch提取的Markdown不能证明页面HTTP状态、完整head标签或Google已收录。

### 7.3 只有需要固定Google排名才启用SERP

建议保留一个由FS程序调用的可选SERP适配器，使用独立的排名数据源开关，**不受Hermes分析开关控制**。Bright Data可作为免费档候选，DataForSEO等仅备选，不强制接入或充值。该源故障只影响排名卡，不影响其他来源。[S8]

采样键：`engine + keyword + location + language + device + effective_depth + observation_date`。一次搜索结果解析所有批准竞品，不每个竞品重查一次。

排名仅从自然结果中判断，不把广告或AI摘要混入序号。状态至少为：已找到、已确认范围内未找到、深度不足、失败、尚未采集。未找到不填101，失败不计作掉榜。只采到8个自然结果时，未命中不能据此断言不在自然前十。

建议免费优先规模为每游戏每市场5个重点词，最多4个市场、1种设备、1种语言，即80个唯一组合/日；这只是可选排名初值，不限制GSC/GA4的四游戏正常数据范围。

### 7.4 页面探测

四游戏每夜可先按80个已批准页面估算，核心页优先。当前已批准范围内有更多必要页面时，可以按夜间余量和上游负载增加份额，不为凑80而漏掉关键页；不自动漫游全站或新增未授权站点。单域先串行、全模块HTTP先用2个并发；现场允许时在配置区间内调整。连接、停滞、总体超时和正文大小仍有合理的可配置应急保护，不依赖一个对所有页面相同的过小阈值。

保存状态码、重定向、title、H1、meta robots、canonical、hreflang、内容hash及短差异。正常HTML解析即释放；排除登录、结账、支付和有副作用URL。新检测亦按实际观察日记录，次日纳入正式“昨日一次探测”区。

不部署常驻浏览器、不新增183远程入口、不接重型爬虫。外部页面中的文本不能扩展Hermes工具权限。

## 8. 指标计算与异常判断

所有数值与基础规则提醒均由程序计算，不需要模型；Hermes开启后只解释，不参与公式执行或事实校验。金额使用十进制或最小货币单位。缺失与真实0分开；分母0返回无可计算值，不输出无穷或伪0。

| 指标 | 公式/规则 | 关键限制 |
|---|---|---|
| 搜索CTR | 同口径`Σ点击 / Σ展示` | 不平均各行CTR |
| GSC平均位置 | `Σ(位置×展示) / Σ展示` | 只合并不重复、同聚合方式的行 |
| 名次提升 | `前一有效日名次−当前日名次` | 未入榜/缺历史不能造数；日期与条件必须可比 |
| Top10覆盖 | 确认前十样本数 ÷ 可判断前十状态的样本数 | 失败/深度不足排除，另报覆盖率 |
| 采集覆盖 | 有效完成数 ÷ 本次应采样数 | 不通过缩小计划分母美化 |
| 参与率 | `engagedSessions/sessions` | 同来源与粒度 |
| 购买事件/会话 | `ecommercePurchases/sessions` | 是事件次数比，不叫去重用户转化率 |
| 会话购买率 | 支持时读取原生购买关键事件率 | 不用GSC点击当分母 |
| 可信SEO订单 | A/B去重后已付款订单数 | U不计入 |
| SEO付款额 | 上述订单/商品行的既有收入字段求和 | GA4金额不覆盖后台事实 |
| 退款后净额 | 同规则付款额减退款额 | 明确支付期重述或退款发生期，不混用 |
| 客单价 | 付款额/已付款去重订单数 | 无确认订单时为空 |
| 归因覆盖 | 可判断明确来源的已付款订单/范围内已付款订单 | 不是SEO占比，不将未知按比例分摊 |
| 变化率 | `(当前−对照)/对照` | 对照0标“新增/无基线” |
| CTR变化 | 当前CTR减对照CTR，以百分点显示 | 2%到3%是提高1个百分点 |

例：三个词中A排第5，B确认在前十外，C采集失败。Top10为1/2=50%，采集覆盖为2/3≈66.7%。不是Top10=33.3%。

搜索趋势默认比较最近7个可比完整源日与前7个完整源日；实际不足14天则只给现有趋势。最近30天背景不表示已有前30天对照，不自动再补60天。用户数等不可加指标不从日值直接求和；没有预计算的区间指标就提示不可用，不因点击筛选而回源。

告警是每日批次结论，不是实时告警。初始候选规则可为“7日点击下降≥20%、绝对少≥30、对照点击≥100、可比覆盖≥90%”；这是排查筛选，不是统计显著性结论。数据缺失触发质量提示，不触发“SEO暴跌”。排名异常需连续两日有效样本；无两日历史不编造确认。

## 9. 基础快照与AI报告分开存储、分开发布

### 9.1 三个边界，不是三套系统

| 层 | 内容 | 写入方与故障边界 |
|---|---|---|
| 基础工作层 | 近期事实、回填、纠错、独立排名/页面观察、水位 | 夜间FS数据worker；Hermes无写权限 |
| 基础发布层 | 30天展示指标、有限明细、规则提醒、来源状态 | 只由基础发布器写；发布后只读；不含AI报告正文 |
| AI增强层 | 游戏开关下的任务状态、研究摘要、报告、建议引用 | 可选桥接worker/原Hermes；不能锁住或改写基础库 |

基础快照建议用小型只读SQLite或不可变文件集合，64MiB只是单包体量参考，保留当前和上一验证版本。超过参考时优先检查是否存了冗余明细，必要时分文件/分页；合理体量且仍在总运行预算内可正常发布，不能仅因超过64MiB拒绝整份快照。AI任务/报告可以复用确实独立的原FS存储；若原存储依赖Hermes服务、共享核心数据库写锁或不支持独立资源隔离，则使用一个小型`seo-ai/ai.db`及文件目录，不引入数据库服务。

AI输入可经FS只读分页接口或只读导出的有界事实包交付；AI不得持有基础工作库的长事务，不得获得修改发布指针、运行迁移或清缓存的权限。关闭或删除AI产物不删除指标历史。

### 9.2 基础快照合同

```json
{
  "schema_version": "seo_daily_core_v2",
  "snapshot_id": "seo-2026-11-05-example",
  "publication_date": "2026-11-05",
  "report_date": "2026-11-04",
  "business_timezone": "Asia/Shanghai",
  "games": ["FC27", "D4", "AION2", "WOW_FOREVER"],
  "history_start": "2026-10-06",
  "history_end": "2026-11-04",
  "facts_hash": "由基础事实确定",
  "data_status": "partial",
  "frozen": true,
  "daytime_collection_enabled": false,
  "sources": []
}
```

日期和状态仅演示结构。source仍保存实际源日期/时区、成功/尝试时间、覆盖日历、错误和计算版本。**这里不设置必须成功的hermes_status或report_id字段；AI状态不参与data_status计算。**

AI报告独立合同：`report_id、snapshot_id、facts_hash、game、analysis_kind、policy_version、input_scope_hash、model/provider_ref、knowledge_version、generated_at、report_hash、status、evidence_refs`。费用和账本引用不含Key。状态至少区分disabled、not_configured、not_run、queued、running、ready、failed、timed_out、cancelled、circuit_open、budget_exhausted，不把“关闭”显示为采集故障。

### 9.3 基础发布不接触模型

写候选包 → 关闭写连接 → 校验schema/日期/四游戏范围/金额/无今日事实泄漏 → manifest与流式hash → 同文件系统原子切换current指针 → 记基础成功。**全过程不导入Hermes SDK、不向模型发请求、不等AI心跳或报告。**

候选文件不依赖未checkpoint WAL。发布包只读打开。基础发布成功后即便可选投递完全失败，也不撤销成功、不重采、不恢复旧包。

AI只读已发布包，独立输出分游戏报告；其发布成功不改基础包字节、facts_hash、数据截止日或current指针。每游戏正式AI报告同夜最多接受一次，06:30后不自动补写；旧报告仅以旧日期/旧snapshot_id在历史页显示。

### 9.4 全页面同版本与恢复

第一页返回snapshot_id，分页/趋势/证据/导出继续携带该ID；AI报告仅接受与之匹配的事实版本。过期版本明确提示，不静默串用新旧数据。基础包撤销后，关联AI报告标失效，不拿旧证据分析新快照。

AI修复后默认只处理下一夜的新快照，不补历史欠账、不回写旧日报。完整数据备份恢复不要求AI文件存在；AI备份可独立跳过，但基础恢复必须通过。AI无权阻塞基础包轮换：使用有界输入或可续租的短租约；仍有有效进展时可在本夜总截止内续租，不以240秒机械失效。任务完成、取消、无进展超时或到达最终截止时释放；不长期钉住旧包。

## 10. Hermes可选增强、项目开关与故障隔离

### 10.1 两级开关，数据开关与AI开关不同

前台提供`SEO AI增强`总开关，以及FC27、D4、Aion2、WowForever四个独立开关。总开关只控制本SEO模块，不停止全局Hermes服务、不改变其他模块模型配置、联网能力或任务。

```json
{
  "module": "seo",
  "revision": 1,
  "ai_enabled": false,
  "projects": {
    "FC27": {"ai_enabled": false},
    "D4": {"ai_enabled": false},
    "AION2": {"ai_enabled": false},
    "WOW_FOREVER": {"ai_enabled": false}
  }
}
```

这是**建议的新安装默认值**：先在AI全关下验收基础链，再按用户需要启用；不是本次已替用户关闭线上服务。迁移时保留用户已经明确保存的选择，不用本示例覆盖。用户尚未指定哪款开哪款关，不能代选。基础四游戏采集保持开启，不随AI开关变化。

`配置允许 = SEO总开关 && 本游戏开关`；随后独立检查调用者权限、供应商能力、预算和运行时故障。配置关闭和故障降级分开，不因故障永久篡改用户开关。总开关关闭时保留各游戏的选择，重新开启后按保存选择生效，但不马上触发新日报。

设置存FS独立控制配置，不能只放浏览器localStorage、不可变数据包或Hermes会话记忆；Hermes宕机时仍可保存。沿用现有站点/项目管理权限与审计，使用revision/CAS避免多人互相覆盖。读取设置失败时仅AI禁用，基础数据继续工作。

### 10.2 关闭必须立即停止新增调用

| 操作 | 必须发生 | 不得发生 |
|---|---|---|
| 关闭单游戏AI | 禁止该游戏新分析、研究、AI聊天、自动建议；取消未派发任务 | 不停该游戏采集、回填、排名、规则提醒或历史查询 |
| 关闭SEO总开关 | 禁止SEO全部AI调用，保存各游戏原选择 | 不停其他业务Hermes、不停全局API供应商 |
| 在运行中关闭 | 写入新策略版本，禁止后续工具调用与结果发布，尝试取消本run | 不为停一个游戏杀整个共享Hermes进程 |
| 白天重新开启 | 控制状态立即变为允许；自动报告等下一夜 | 不立即追跑30天历史、不触发实时采集 |
| 清理AI历史 | 仅按AI保留策略处理AI产物 | 不删除事实库或来源凭据 |

每次模型/工具调用前、每次写正式AI报告/AI建议前，均核验当前开关、权限及启动时的策略版本。执行中变更为关闭，迟到结果不得作为当前有效产物发布；关闭后又开启也不能让旧run复活。建议使用总开关generation＋项目generation绑定授权，不因另一个项目的配置变化误取消当前正常项目。

设置接口只写控制状态并返回，不等待Hermes应答。已提交到远端供应商的请求可能继续执行或计费；必须如实记录cancel_requested与可确认状态，不能承诺点击关闭即刻退款或已停止所有远端推理。

### 10.3 分游戏任务，合并展示，不创建四套Agent

每夜每个开启AI的游戏最多一个报告子任务，使用同一个现有Hermes服务、同一套SEO Skill和一个串行低优先级桥接worker。关闭游戏不入提示词、不入研究范围、不参与AI总结，也不因全局报告被顺带分析；必要跨游戏线索仅来自同时开启且有权限的范围。

前台把可用结果拼成一份“日度分析”，拼接由程序完成，不额外调用模型写全局总评。某游戏失败不撤销其他成功报告；全部关闭时没有模型任务。每项目可先提供Top10异常及4k—8k tokens摘要，这只是首轮材料目标，不是异常总数或分析上下文上限。重要问题更多时分页下钻、补充必要证据；不要机械截断关键事实、减少推理质量或修改Hermes全局推理模式。调查调用按第7节弹性分配，同时遵守真实供应商配额和既有消费授权。

正式内容包括：变化、证据、可能原因/替代解释、缺口、建议、负责人建议、7/14/28天复查条件。基础规则提醒在模型关闭时仍存在，不能把规则结果冒充AI结论。

### 10.4 只读工具和独立动作

| 工具（建议命名） | 输入 | 边界 |
|---|---|---|
| `seo.snapshot_summary` | snapshot_id、启用且有权限的游戏、期间 | 读取已发布聚合和质量 |
| `seo.snapshot_drilldown` | snapshot_id、game、cursor、limit≤100 | 同版本明细，缺口不回源 |
| `seo.snapshot_rank_history` | snapshot_id、固定组合 | 真实历史，不倒填 |
| `seo.snapshot_evidence` | snapshot_id、game、evidence_id | 已存在证据，不接受任意联网URL |
| `seo.propose_action` | snapshot_id、game、证据、建议 | 当前AI开关有效才可新建AI提案；不直接改站 |
| `seo.queue_next_night` | game、问题、范围 | 开启且有权限才排下夜；关闭返回AI_DISABLED |

白天主动AI聊天只在相应开关开启且有权限时可用，使用固定包，不联网、不改日报。关闭AI不阻止成员查看数据或人工记录任务。已创建的人工待办/已获独立授权的业务执行不因这个分析开关被追溯撤销；本期不把网站自动写入挂在AI开关上。AI自动复查暂停，但人工跟进与基础数据继续。

### 10.5 不能只有try/except：至少隔离六处

| 边界 | 实施要求 |
|---|---|
| 启动与依赖 | 基础包不强制依赖Hermes SDK/Key/进程；单独安装基础能力即可启动。不得配置基础服务Requires/BindsTo/PartOf到Hermes |
| 调度与退出 | 独立FS日更、锁与data_run；AI提交/执行/账本失败不更改数据任务成功或触发数据重试 |
| 线程/连接/队列 | AI不得占基础请求池、数据写锁或高优先级采集队列；一个AI在途，其余为小型有界记录 |
| 数据与权限 | Hermes只读事实，不写core.db/current/基础健康状态；AI库损坏/写满不能锁住数据发布 |
| 前端与健康 | 基础卡片先加载；不以Promise.all等待AI成功。AI组件懒加载、有独立错误边界；核心health不探Hermes |
| 资源与配额 | CPU/内存/文件/Token单独限额；先暂停增强，保护基础和其他FS业务 |

容错采用简单、有进展感知的配置策略。连接超时沿供应商实际延迟设置，不统一写死3秒；区分连接失败、等待首个输出、流式无进展和任务总时长。240秒改为耗时告警参考：仍有有效进展、资源和已授权费用允许且能在本夜截止前收尾时继续。停止条件是已配置的无进展超时、最终墙钟截止、确认授权错误或应急保护，不是单纯“比预期慢”。仅对明确未提交/可安全重试的失败退避；提交后超时未知先对账。熔断按故障类型、连续失败和冷却状态配置，不因两次短暂网络抖动必然关闭整夜；同夜可少量探测恢复，禁止白天自动补跑或无限探测。401/402/403、缺配置按真实原因结束相关增强；格式问题仅影响该游戏。所有调整只作用SEO桥接，不增加基础发布等待。[S14]

SEO AI排队只留当前夜间批次的每游戏1个任务（最多4个）与有限“下夜调查”问题，不长期积压补跑。恢复后不抢占其他模块已有任务；实际共享Hermes无法隔离SEO run资源时，先保持SEO AI关闭，基础照常上线。

### 10.6 产品状态不混淆

基础层显示“数据已更新／部分来源待发布／数据更新失败”。AI单独显示“已关闭／待下次夜间生成／分析完成／暂不可用／预算不足”。用户主动关闭不是故障。无需占据整个看板的全屏警告，不因为AI失败禁止进入其他页签。

关闭后当前AI卡片隐藏或显示简短关闭提示；旧报告不删除，在有权限的历史入口仍可看，标原游戏、日期和snapshot_id。重新开启后也不把旧报告顶成当前结论。

顶部显示四游戏范围、发布日期、业务统计日、基础快照版本、来源延迟、近30天覆盖；另有`SEO AI增强`总开关和本游戏开关。总开关关闭时子开关可保留选择并提示“总开关已关”，不能造成数据禁用的误解。

## 12. 弹性资源、容量与释放机制

### 12.1 数字作为起点，实测决定运行空间

本节覆盖旧版固定资源上限。资源策略只需是现有部署/任务配置的一部分，不新增资源调度服务。W0读取宿主资源与已有关键任务，选取代表性四游戏分页、回填、发布和备份样本，记录常态与峰值。没有历史峰值时先用安全的小批采样校准，不为等待长周期观测而停掉全部施工。

| 项目 | 起步参考，不是业务拒绝线 | 弹性与保护方式 |
|---|---|---|
| 基础Worker | 旧512/768MiB、合计1GiB仅作容量讨论参考 | 根据实测峰值及主站余量留出突发空间；超常态先降并发/分批，不立刻杀进程 |
| AI桥接 | 旧128/256MiB仅作参考，不承载整个Hermes | 与基础分开保护；有独立资源上界，但上界按真实输入/输出和宿主余量配置 |
| CPU | 不机械固定0.4核＋0.1核 | 低优先级、主站优先；空闲夜间可多用，关键业务受压再节流 |
| 任务并发 | 一个基础批次、AI默认串行、HTTP先2个 | 单批次唯一发布不变；内部读任务可在经过验证的并发区间调整，核心库保持合适单写入方式 |
| 单页取数 | 500—1000行起步 | 按实际响应大小和内存余量调节，始终逐页处理，不累计全量大数组 |
| 进程内缓存 | 32MiB是起步目标 | 使用字节统计、TTL/LRU和可配置上界；缓存多一点能明显减少重复解析且余量足够时可放宽 |
| 响应大小 | 旧JSON 4MiB、HTML 2MiB作参考 | 提取必要字段、流式读取；大于参考但仍安全时不全盘失败；异常超大响应保留有限应急上界并标部分 |
| AI材料 | 4k—8k tokens首轮摘要 | 有价值的下钻可补充材料，不机械压低全局推理配置；上下文仍遵守模型上限和已授权费用 |

应急内存保护仍须存在，但由实测后的`operating_ceiling`与`emergency_stop`决定，不用旧文档里的1GiB生搬硬套。基础、AI桥接、共享Hermes增量要分别核算，并预留FS原业务峰值与宿主安全余量；不能只看瞬时“空闲内存”就不断上调。应急值必须有限，配置有记录且能读回，不得使用“无限”作为默认。

首次配置时给正常样本峰值留明显余量；可把约1.5—2倍样本峰值作为讨论起点，但需考虑样本是否覆盖回填、备份和同时运行的旧业务，不能把这个倍率重新当成统一硬指标。没有足够空间时先缩小并发/页大小和延后非必要任务，不抢主站资源。

`MemoryHigh/MemoryMax`等机制按宿主实际能力配置在独立scope中；达到常态预警和触发应急终止是两件事。AI不得与基础共用一个会一起被终止的进程，也不把整个共享Hermes装入SEO额度。[S11]

共享Hermes的单run取消、低优先级、有界输入/产物和费用账户余量仍需验证；无法隔离时保持SEO AI关闭，基础继续。短进程完成即退出，正常、异常、取消、关开关路径都释放连接、锁和租约。

### 12.2 磁盘：常态预算、临时余量与应急底线分开

旧版“目标2GiB、3GiB告警、4GiB即停”改为**2—4GiB的起步体量参考**。4GiB不是永久停止线。若正常数据、一次性30天回填或备份轮换暂时超过参考，但宿主安全余量和部署配置允许，则继续；不为了守住4GiB拒绝当天快照或删除有效历史。

W0分别配置常态预警、允许的持续运行空间、临时制作/恢复空间和不可侵占的宿主保留空间。应急上界有限但留足余量；在已经配置的运行区间内，分类预算可自动调整，不逐项重复审批。超出该区间或需要新增存储、购买服务器时，再汇总影响与选择，不自动采购。

| 类别 | 旧版估算MiB，仅作量级参考 |
|---|---:|
| 基础与AI数据库及索引 | 768 |
| WAL/数据库临时文件 | 128 |
| 短期错误及调试响应 | 64 |
| 正式/候选/租约中的快照 | 256 |
| 本模块运行日志 | 64 |
| 两份小型备份及清单 | 1664 |
| 备份制作、恢复验证及应急工作区 | 1024 |
| 报告、行动证据与新增产物 | 128 |
| **参考合计，不是停止阈值** | **4096MiB** |

以上分类可在实测总预算内调剂，不变成八个分别碰线就报错的小配额。必须统计全部实际文件，包括共享Hermes中由SEO产生的专属产物引用/增量；不得仅因放到了共享目录就从SEO容量统计中消失。

新写入前预估峰值：已有文件＋候选/备份制作＋恢复验证＋WAL和日志增长。允许为备份轮换和首次回填临时借用已预留空间；任务结束主动回收。单包64MiB、快照集合256MiB同为参考，合理超出时可分页/拆文件或使用已配置余量，不直接否决全批。

默认保留当前及上一份快照、两份已验证备份；制作新副本期间允许第三个候选临时存在，但必须预留空间并在验证后轮换。失败时不得为减小体积删除唯一可信备份，不永久保留每天整份数据库。

### 12.3 保留策略不因放宽容量而失控

| 数据 | 维护策略 |
|---|---|
| 展示历史 | 最近30个日历日，真实可用多少展示多少 |
| 日级事实/排名/页面状态/最小归因缓存 | 默认滚动35天；清理前保留必要行动基线；不删原FS历史 |
| 研究摘要/失败片段 | 摘要默认30天，失败片段默认72小时；有实际字节统计与滚动清理 |
| 正常HTML/成功原始响应 | 默认不落盘；经允许调试时按24小时逻辑有效期与下夜物理清理 |
| 正式AI日报 | 每开启游戏保留最近30份；小型正文与证据分开，不保存整套模型上下文 |
| 日志 | 默认7天、按合理文件大小轮转；64MiB仅作量级参考 |
| 导出 | 最长24小时可访问；到期拒绝读取，下夜清理；必要进行分块导出 |
| 行动证据 | 复用现有任务保留策略，结束后默认最多180天，只保留最小基线与结论 |
| 快照和备份 | 当前＋上一可信快照，两份已验证备份；临时候选使用预留空间 |

容量预警不能成为缩短30天展示窗口、删除未归档行动证据或保留备份不完整的理由。遇到必要保留与资源冲突，先清可再生数据、降任务负载并明确缺口。未来扩游戏、增加长期历史不是本次自动放宽范围。

### 12.4 清理不依赖Hermes，释放机制照常实施

每个子任务结束关闭对象和删除自身无用临时文件；到期整理、数据库维护、备份归FS夜间维护。AI关闭或故障时AI旧产物仍清理，清理AI失败不阻塞基础发布或维护。

TTL失效和日志轮转可以本地执行，不触发上游。过期但未物理删除的文件仍计入实际占用；不得用逻辑过期伪装释放。只处理SEO登记的数据与目录，校验活动租约、路径和符号链接；不碰主库、共享Google原始历史、其他会话、正式知识或凭据。

逐页读取→计算→提交→释放；不同时持有原始JSON、大数组和DataFrame的多份全量副本。删除批次可按现场负载调整，不追求一次清空全部到期数据。新SQLite库的增量回收、WAL维护及短事务沿既有设计；逻辑删除、可复用空闲页、实际释放字节分开记录，禁止删除在用WAL或对全FS做VACUUM。[S9][S10]

备份使用一致性机制、流式hash、manifest和隔离恢复检查；基础和AI分别记结果。预留新备份与检查空间，验证成功再轮换旧份。禁止全库重建11GB数据、一次性读入大备份、系统级drop_caches或为SEO重启主站。

### 12.5 到达参考值不停止，到达真实风险才降级

| 状态 | 判断 | 行为 |
|---|---|---|
| 常态 | 位于预期体量/耗时 | 正常执行 |
| 预警 | 超过历史参考，但有进展且资源仍健康 | 记录和提示；按需减并发、增量处理、回收缓存，允许继续 |
| 弹性区间内 | 峰值超常态，仍在配置允许空间、上游配额和授权费用内 | 自动调整工作份额，不要求用户逐次批准，不影响正确数据发布 |
| 实际压力 | 持续资源紧张、增长异常、可能侵占关键业务保留空间 | 先减AI和探索，再延后回填/可选采样，保存游标和可用结果 |
| 应急保护 | 到达现场配置的最终边界、异常失控或确认不可安全继续 | 停止受影响新工作或取消对应任务，保留旧快照；不牵连主站/自动定价 |

宿主原有保护优先，不能因本次要求而撤销。旧版85%/90%、5GiB/2GiB只作讨论参考；实际判断同时考虑绝对可用空间、增长速度、inode、备份需要和原业务保留，不只看单个百分比。上游硬配额、错误授权或已授权费用不足仍须尊重。

资源配置的最小字段建议为常态目标、告警值、允许区间、应急值、临时余量、适用任务、测量依据和变更记录；使用现有配置文件/管理入口即可。不自动扩购买资源，不建设复杂调度平台。

### 13.1 DeepSeek测算

中文官方价为Search、Fetch分别每1000次成功请求5元。失败/空结果的计费按官方规则；模型token另计。同一官方账户可使用现有余额，但第三方中转的可用路由、价格与额度通用性必须按其实际合同验证。[S6][S12]

按每晚Search 8次＋Fetch 12次、31天且全部为成功请求：`20×31=620次`，网站工具费用示例为`620÷1000×5=3.10元/月`。这是工具调用测算，不包括模型推理、多轮调查、重试成功调用或供应商加价。

模型费用统一公式：`未缓存输入tokens×相应输入价＋缓存输入tokens×相应缓存价＋总计费输出tokens×输出价`，按实际币种/百万单位换算。费用未知写未知，不能因为用了既有Key就显示0元。赠送抵扣与真实现金支出分开。

原50元/月仅为SEO增量费用估算/提醒参考，不新增一条与现有已授权供应商额度冲突的僵硬月限。复用真实有效的供应商余额、已授权消费范围和现有成本账本，在该范围内按任务价值动态分配，合理波动先提示而非立即切断；仅凭账户有余额也不能视为可无限消费。用户没有授权的现金支出、自动充值、订阅升级、新供应商采购仍不执行。全部关闭后不再新增SEO模型/研究调用，已提交请求仍须如实对账。独立SERP若开启仍消耗其数据源额度，AI开关不是排名源总开关。

### 13.2 可选免费排名预算

Bright Data官方当前给符合条件的新账户每月5000免费credits，SERP普通请求1credit；多产品共用同一池。已充值账户免费用完可能消耗充值余额，因此系统也要限制，不仅关闭自动充值。[S8]

## 14. 故障处理与安全边界

| 情况 | 基础层 | AI增强层 |
|---|---|---|
| Hermes未安装/进程停机/Key无效 | 正常启动、采集、计算、发布和读取 | disabled/not_configured/unavailable，独立提示 |
| 模型超时、限流、余额不足 | 不等待、不回滚、不重采 | 有界终止/熔断，次夜再评估 |
| 单游戏关闭AI | 四游戏数据均照常更新 | 只停止该游戏新增调用，不分析其内容 |
| AI库损坏、队列故障或报告目录写满 | 不读其库、不等其锁；发布继续 | 限额内失败记录，必要时停增强 |
| AI前端组件加载失败 | 数据页与基础操作正常 | 局部错误边界，不全屏报错 |
| 单游戏/单基础源失败 | 其他成功数据发布，缺失不补0 | 只基于可用事实，不能补造数据 |
| 基础候选全不可用/校验失败 | 保留旧快照原日期 | 不生成挂在新日期上的假日报 |
| 白天Hermes恢复/AI重新开启 | 固定数据不变、不开新批次 | 自动报告等下一夜；有权限用户可主动固定快照问答 |
| 发布后报告错误 | 数据不受影响 | 撤销该AI报告，不能回滚正确数据 |
| 基础快照被合法撤销 | 显示回滚版本与原因 | 关联报告标失效，不再当有效分析 |
| 宿主磁盘/机器故障 | 按FS既有恢复机制，不能保证可用 | 优先停增强，不把资源压力扩散 |

基础health只反映自身可读包、FS鉴权和核心依赖，不以Hermes心跳作为readiness。增强健康从本地状态独立展示，不让每次查看页面都探测模型。故障恢复不修改用户开关，不自动开启付费替代模型或补历史任务。

密钥不进入前端/Git/模型上下文，数据访问权限由FS控制。SEO分析只读基础事实；外部网页指令不得改变权限、预算、时段或开关。主站内容、改价、优惠、外发执行继续沿原授权，不因开启AI自动获得写权限。关闭分析开关不撤销其他模块或早已独立授权的业务操作。

跨游戏报告和工具须校验游戏范围：关闭D4后，不能通过“全局SEO总结”或工具下钻间接把D4重新送给模型。本规则限定SEO上下文，不全局限制用户在其他明确授权任务中对D4提问。

## 16. 验收清单：基础与增强分别交付

| 验收项 | 必须有的证据 |
|---|---|
| 四游戏真数 | 每款来源/配置回执或独立缺口，不以选项代替接通 |
| 一日一次与昨日 | 一个FS定时入口、唯一基础发布；源时区与延迟正确；无今日观察倒填 |
| 历史30天与冻结 | 固定回填窗口与覆盖日历；白天同snapshot_id事实hash一致、无回源 |
| 无AI也可用 | 在Hermes未运行/未配置Key/缺可选SDK环境，基础能冷启动、采集、发布、查询、导出、维护 |
| 基础无需等AI | 模型永久挂起、投递失败、队列损坏，不延后基础发布、不改data_run、不触发重采 |
| 总开关作用域 | 只控制SEO，不停止全局Hermes、其他模块或原供应商 |
| 项目开关 | 任一游戏关闭后，其基础指标/排名正常；该游戏新增模型与研究调用为0 |
| 在途关闭 | 新调用被拒、未派发任务取消、迟到报告不发布、OFF→ON不复活旧run；远端计费状态如实 |
| 分游戏隔离 | 成功报告可独立展示；关闭/失败项目不进入全局AI提示词或阻塞其他结果 |
| 存储与页面隔离 | AI库锁/写满/组件崩溃仅影响AI；基础包hash不变、主要页面可用 |
| 白天恢复 | 不自动补报告/研究/历史；主动聊天仅开启项目、固定快照，无新源数据 |
| 权限 | 关闭不能绕过后端；并发设置CAS有效；跨owner/游戏正确；基础数据权限沿FS |
| 资源 | 实测常态/峰值、关键业务保留与弹性区间配置可读回；超过旧参考不误杀，真正危险时隔离降级；共享Hermes增量另说明 |
| 容量与恢复 | 全路径/临时峰值计入；4GiB仅参考；越过预警但有安全余量可继续；临时借用任务后回收；关AI仍清理，基础无AI备份可恢复 |
| 费用 | 开关前后可对账；8/12次和50元仅参考，不替代真实授权；实际上游配额/费用边界有效；不自动充值或改全局预算 |
| 发布状态 | 基础：界面/真数/部署/自然周期；AI：未启用/已配置/真实调用/故障隔离，各自列状态 |

建议相同夹具开启/关闭AI各跑一次，基础指标与归一化facts_hash应完全一致（排除运行时间等元数据）；核心发布不等待AI，无论注入多长的AI挂起都不应串行增加同等等待。另测超过旧请求次数、回填分钟数、缓存或快照体量仍在允许区间时能继续；无进展和真正资源危险时能保存结果并有界退出。实际时延与资源阈值由W0实测确定，不凭文档承诺生产性能。

**基础产品验收允许AI未配置或全部关闭；增强层未通过不能宣称已启用。**正式业务验收不能靠停止生产共享Hermes来做破坏性证明，优先在隔离环境复制真实接线；必要生产维护须已有授权。
