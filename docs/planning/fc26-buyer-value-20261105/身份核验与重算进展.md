# FC26 客户身份与赛季价值复核（2026-11-05）

## 当前结论

buyer_id 对客户分析有明显价值：它覆盖了大量没有注册 UID 的游客订单，并能连接游客时期和注册后的消费。应以经过范围核验的 buyer_id 为主要关联候选，UID 作注册身份辅助。不能把 buyer_id 直接解释为设备码或邮箱哈希，也不能通过 UID 的关系把多个 buyer_id 自动合并。

**本次已核到新增字段和原样本，尚未取得按 buyer_id 精确查询的全年订单。因此尚无新的 buyer_id 全赛季价值结果，不能宣布旧约 $46 已被新方法验证或推翻。**

## 已核事实

2025年9月重新导出的 ES 文件包含 buyer_id、uid 两列，45,217 行、1文件、解析失败0。普通 Admin `order.Order/index` 当前返回 UID，但没有 buyer_id；两者不能混称同一接口。

| 范围 | 订单行 | 有效 buyer_id | 有效非零 UID |
|---|---:|---:|---:|
| 九月全游戏导出 | 45,217 | 45,217 | 13,801 |
| FC26 | 2,684 | 2,684 | 905 |
| 与旧测算完全相同的首购样本 | 80 | 80 | 24 |

FC26 的 2,684 行对应 1,999 个 buyer_id。920 条新客户标记单对应920个不同 buyer_id；这一月份没有同buyer重复的新客标记。78个 buyer_id 同时存在 UID=0 的游客订单与非零UID订单，说明只靠注册UID会漏掉一段真实消费记录。

原样本按原确定性规则重建，其日期、金额层和首单金额签名与旧冻结证据完全一致；80个buyer均不同。这个样本在9月有94条订单，其中8个buyer在当月有多笔；这只是9月事实，不是全年生命周期结果。

补充配对：80个样本均可按首购日期、金额层、首单金额唯一对应旧冻结结果。新buyer路径9月94条、旧邮箱路径9月94条；逐条按付款时刻和USD金额比较，94条全部相符，80客户均无9月新增或缺失记录。因此当前没有证据说明旧路径在这些客户的9月漏单；仍需全年buyer查询才能判断后续消费是否漏计。旧冻结订单哈希使用未保存随机盐，所以本次是精确时间与金额多重集相符，不宣称直接订单ID等值，也不外推网站范围或全年完整性。

FC26有1个buyer对应3个不同非零UID（3单、3个付款日）；全游戏范围另有2个buyer对应多UID、12个UID对应多buyer。ES文件没有site、email字段，不能据此判断共享账号、账号更换、跨站关系或数据错误，自动合并须保留冲突信息。

## 旧结果应怎样理解

前次冻结160个9月首购客户的加权赛季收入约 $162.55/人。乘 FC27 十月采购毛利率28.15%，得约 $45.76，即汇报里的约 $46。这是把成熟历史客户收入套用FC27毛利率的理想贡献估计，**不是逐客核得的实际全年利润**。

若套 FC26 历史代理毛利率31.86%，约 $51.79；状态保守收入约 $155.15 乘31.86%约 $49.43。这些分别是场景值，不相加，不当净利润。九月样本订单来源为空，不能称广告新客专属LTV；观察至2026-08-31不等于每客满365天，也不代表全年各月新客。

## 实际入口与当前缺口

- ES人工入口：`order/makeExcelByEs`，菜单为“ES销售订单下载”。
- 下载生成：`/admin/order.OrderExcelByEs/downloadsMake`，通过现有 Admin HMAC 8912 适配器调用；保持原请求与文件回执。
- 文件读取沿原可信xlsx下载器，使用其既有 User-Agent。旧python3缺HTTPS依赖导致首次下载失败；切换已安装SSL解释器并补齐原读取器请求头后，同一原回执成功下载，没有重复生成。
- 当前前端 `indexMake-320146dc.js` 明确导出游戏参数为 `gid`。已按用户提醒补做 `startTime + endTime + gid=833 + buyer_id` 完整组合：2025-09-24返回187行，187行全为FC26，但目标buyer只有1行。由此确认游戏筛选生效，而此导出接口的顶层buyer参数仍未筛选。该结论仅限这一真实接口与参数组合，不能推广为后台没有客户筛选能力。
- 另外定位到实际ES订单列表：`orderes/order/index.vue` 对应 `index-07c718ed.js`，`baTableApi` 将 `/admin/order.OrderEs/es` 拼接为 `/admin/order.OrderEs/esindex`。按现有表格的 `search[]` 格式传游戏、网站、付款日期、buyer并限制10行，接口HTTP200但业务返回401 `You have no permission`。未获得客户数据，也没有绕权限；因此不能判断此列表的buyer筛选是否生效。
- 剩余需要开发确认的是：新增UID/buyer筛选的真实读取入口及字段编码；若就是上述ES列表，需确认现有只读HMAC身份是否已获该动作权限。不要为此恢复已退役8767或使用浏览器凭据。

## 给开发核对的脱敏请求示例

以下来自当前前端的实际列表地址与表格编码，buyer_id用占位符，不含客户数据或凭据。通过已有HMAC适配器GET调用，不需要浏览器登录态。

```python
endpoint = "/admin/order.OrderEs/esindex"
params = {
    "limit": 10, "page": 1, "order": "id,desc",
    "search[0][field]": "gid", "search[0][val]": "833", "search[0][operator]": "=",
    "search[1][field]": "site_id", "search[1][val]": "266", "search[1][operator]": "=",
    "search[2][field]": "paytime",
    "search[2][val]": "2025-09-24 00:00:00,2025-09-24 23:59:59",
    "search[2][operator]": "RANGE", "search[2][render]": "datetime",
    "search[3][field]": "buyer_id", "search[3][val]": "<原样本buyer_id>",
    "search[3][operator]": "=",
}
```

本次返回：HTTP 200；业务 `code=401`，`msg="You have no permission"`。这表示现有调用身份在这一路径被拒绝，不是证明参数错，也不是证明无该客户或查询结果为零。普通订单列表、导出生成可用，不代表ES列表读取动作同样授权。仅请开发确认新增字段查询是否在该入口、正确筛选编码及原读取身份的动作权限，不需要开放全站写入或其他权限。没有继续尝试其他权限路径。

## 精确查询打通后的计算约定

1. 优先同80客户作前后配对核对；再决定是否需补充独立样本。不要因为后续消费低、历史缺失或身份冲突就随意换掉样本。
2. 按真实网站范围、buyer_id关联；保留UID变化和原订单ID。订单跨查询按订单键去重，不把身份关联等同归并所有UID。
3. 首购前付款历史用于验证站点新客/FC新客；未付款记录不算消费。固定主站266、FC26、有效付款日期及截至2026-08-31。
4. 30/60/90/180日及赛季累计收入分别计算，包含只买一次的人。全体首末购跨度、复购者跨度及复购比例分开；跨度不是寿命预测。
5. 每客窗口收入=同客同范围窗口付款订单金额之和；分层均值按原候选群体层权重合并。旧样本与新buyer样本比较新增/缺失订单和客户差值。
6. 实际采购贡献须匹配同订单历史全部交付成本。成本覆盖不足时，实际值保持partial；收入×固定毛利率另作估计，不能包装成实得利润。
7. 退款/争议原状态及实际退款金额分开。无实际退款金额时，整单剔除只能作为保守情景。
