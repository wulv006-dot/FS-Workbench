# FC27 金币履约的历史事件取证

对比 2026-11-09 至 11 日与 2026-11-16 至 18 日。范围是 Order 的 MMOEXP 主站、FC 27（Order gid 1322）、Game Coins（cid 1）。日期和日志按 Asia/Shanghai。订单列表的原生时间筛选明确为付款时间，详情最早的入队事件另外校验落在本期。跨付款日与提单日的边界订单可能缺失。

## 样本与计算

- 原生列表选择「已完成」和「曾为问题单」是／否，在每期前、中、末三日各取至多两页。按平台、数量段和曾问题标记分层，每组按稳定的订单键散列选择至多两笔，优先覆盖不同日期。原归档未包含整批历史日志，样本配额不代表问题率。
- 商品原始标题提供购买 K，按 1000K 切段，赠币只用于核对完整交付。详情逐项核对要求数量、已交数量与成功发货记录的数量加赠币。历史问题依据状态日志中曾出现状态 6，经原列表「曾为问题单」的标记验证。日志缺失或状态冲突保留未知。
- 耗时为最早的已核 Order 入队日志到末次成功发货时间。核对最早日志状态为新订单、末态日志为已完成，并逐项核对全部已发货数量。中位数只用有确切时间的样本，P90 使用 nearest-rank。当前末态和首次发货耗时另有事实来源，各自不能替代历史问题或完全交付耗时。
- 样本只覆盖最终已完成的订单。尤其最近日期里的未完成、取消和更慢订单不进入样本，两期终态成熟度可能不同。样本结果用于定位需复查的履约环节，不能外推全量问题率或完整发货 SLA。

## 复跑

使用现有 187 封装，将 `releases/fs-dashboard/fc-project-review/fulfillment.py` 作为 `InputFile`。在原认证的 Order 浏览器和原采集锁内仅读已核路径。锁繁忙时本次读取不走其它身份。示例为本期，替换日期读取同期。

```text
flock -n /var/www/dashboard/fs-home/transactions/collector.lock timeout 115 docker exec -i fc27-cloud-browser python3 -B - --start 2026-11-16 --end 2026-11-18
```

输出为期间对齐的 JSON。 `coverage.payments` 保留已读页、可见尾页、候选和续页情况。 `coverage.outcomes` 保留明细排除原因与成功数量。 `rows` 按平台、购买量段和历史问题状态放入项目复盘的 `ordersData.delivery`。运行 `python -B releases/fs-dashboard/fc-project-review/fulfillment_test.py` 可校验拆分发货、数量冲突和跨期排除。

## 两期实取结果

| 已付款候选期间 | 列表候选 | 等额入样 | 核实历史问题状态及末次发货 |
| --- | ---: | ---: | ---: |
| 2026-11-09 至 11 日 | 240 | 24 | 24 |
| 2026-11-16 至 18 日 | 230 | 24 | 24 |

每期 PS、Xbox、PC 及两个购买量档各取两笔曾问题和两笔非曾问题订单，所有平台与数量档的曾问题样本中位时长都较高。本期 PC ≥1000K 的曾问题／非曾问题样本中位数为 308.05／24.52 分钟。本期 PS <1000K 两笔曾问题订单的中位数为 928.85 分钟，其中一笔 1,824.25 分钟。同一格只有两笔，P90 等于该格最大值。虽然本期六个曾问题格都短于同期样本，近期仍在途的订单可能更慢，无法由此断定履约整体改善。

输出为 `fulfillment-2026-11-09.json` 与 `fulfillment-2026-11-16.json`。实际详情的商品标题取自原 HTML title，发货记录含状态 0、1。完成依据仍是可对齐的份额、发货时间和原状态事件。

## 完成率独立口径

截至北京 2026-11-19 16:51–16:52 读取，Order 原生付款日筛选内分别分页在途、已完成、已取消，每类再按「曾为问题单」是／否分开。六个分区都取到尾页。按原商户订单号合并，全部订单的商户号均可解析，未出现同一原生 ID 重复。

| 付款期间 | 完成 / 总订单 | 完成率 | 在途 | 取消 | 实际购买 K 覆盖 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2026-11-09 至 11 日 | 707 / 737 | 95.93% | 18 | 12 | 723 / 737 |
| 2026-11-16 至 18 日 | 548 / 597 | 91.79% | 33 | 16 | 578 / 597 |

- 实际购买量来自 187 已发布共享 ES 的商品投影， 按同站商户订单号与平台关联。期间同一版本 `se_95100f3a49db858470e18ebbb046d5fd`。未关联购买量保留未知档，仍在全队列分母中。
- 已知购买量且曾为问题单的 <1000K 完成率为 130/144（90.28%）→ 94/123（76.42%），本期 28 单在途。≥1000K 为 74/78（94.87%）→ 44/48（91.67%）。两个期间距付款结束的时间不同，这些数字展示截至读取时的进度。
- 48 个分层样本提供已完成订单的发货时长。分层配额独立于上述完成率分母。样本按真实提单日志日期输出日均值、中位数、P90 和样本数，首次问题到末次发货沿同一订单的首条状态 6 与实际发货时间计算。

合并读取入口使用同目录的正文脚本，调用方传经过核实的闭日范围。运行最长 125 秒并沿用共享锁。输出的 `completion.asOf` 是付款队列读取时点。分区未读完整时仍保留覆盖和已观察记录，完成率留空。

```text
python3 -B fulfillment_completion_bridge.py --start 2026-11-16 --end 2026-11-18
```
