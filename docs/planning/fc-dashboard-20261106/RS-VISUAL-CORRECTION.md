# FC 与 RS 通用界面对齐修正

本修正落实用户原先已确定的 RS 通用呈现及本次截图标注。此前把旧 FC 内容堆入连续区块、仍使用独立大图和表格，是交付偏差；本次直接复用现有 RS 组件，不新增另一套设计。

## 目标和边界

- 保留筛选 → 概览 → 利润率与销售趋势 → 结构分析 → 用户与消费 → 组内项目对比。组内对比只在全部商品显示。
- 概览仅保留通用指标，删除正文销售来源/运营关注的大块卡片。来源、缺口保留在紧凑说明中，不伪造缺失客户指标。
- 趋势使用原通用成对图表区域和图表实现；单日不再生成两张独立巨幅单点画布，不补造小时或分类数据。
- 结构使用原 RS 国家排行与地图、支付排行、设备占比组件；增加商品类别环图和当前粒度分类趋势，保留已知子集/缺失提示。
- 用户与消费放在结构之后，用紧凑柱图/环图组合；必要表格默认折叠，保留原下钻与导出。
- 用户划叉的履约、日报和事实报告不在主页面展开。履约使用已有抽屉入口，日报使用已有报告中心入口。
- 不改后台分类/利润/权限/缓存合同，不改 range_api.py 或 P0，不为界面修正重启后台读取服务。

## 本地实现与验收说明

- 直接复用原 RS 的 `trendCard`、`geoCard`、`payRow`、`crossSec`；离开 FC 时按原占位恢复节点，不复制同 ID 组件。
- 利润和销售在一个原生趋势卡内分上下两区；FC 多点图高度分别 220/240px，单日/单小时只有汇总时不画虚假的趋势。窄屏图在卡内滚动，保留可读轴字。
- 分类环图与分类日/小时趋势并排；国家排行与地图、支付排行与访问设备使用原组件。其他入口原先默认折叠结构，FC 显式显示结构，离开 FC 后仍保留原折叠偏好。
- 消费区结合金额档柱状图、环图和折叠表。新老客历史未验证时仅画总量，不生成新老客分组。用户累计环图为静态图例，不产生后端不支持的 user 下钻参数。
- 缺金额按“已知子集”提示；分类缺日断线。毛利悬停字段为 `shipping_sales_cny` / `gross_profit_cny`，币种 CNY，未提供的发货订单数保持暂缺。
- 三入口同步了 FC 适配，保留原先各入口与非 FC 行为差异。修复小时行到原生图所需的 day/idx 映射。
- 401/403 在 JSON 解析前处理；固定 API 的受保护读取重定向同样清空旧 FC 图表、消费、KPI 与抽屉。普通网络失败仍保留明确标记的旧快照。

本地预览使用 `tests/fc_rs_visual_fixture.cjs` 的模拟 API，屏幕顶端明确标记 MOCK DATA。截图是实际渲染器的本地视觉证据，不能作为真实金额对账、部署或生产角色验收证据。

## 用户确认视觉后的原生指标修复

用户指出 Admin 原有的新客人数、复购率、新客占比被显示为暂缺。原 `supplement_fields.extract` 的 `new_people`、`repeat_rete`、`new_people / total` 仍在；问题是 `fcUpdateMetrics` 用未验证明细的空值覆盖原生汇总，并把补充指标也改为空值。

三入口新增 `fcNativeAdminMetrics`，只从当前 exact 响应的 Admin supplement 读取原值，校验 FC profile、Admin game 1327、已付款状态、原生统计接口、日期/小时实际半开窗口、站点及筛选。全站与主站各自验证；分类、平台、客户、金额档或卫星合计不套全游戏客户值。不累加每日人数、不反推复购率、不用付款人数替换新客占比分母，也不启用明细客户信任开关。

同时恢复同范围 Admin 的付款人数、新客付款、纯销、退款、履约/支付成功率和 ARPU 补充字段，保留单位、零值和旧缓存标记。消费明细仍按未验证身份处理，不因汇总卡可用就划分新老客。

独立检查提出的两处展示问题一并修复：分类缺口提示用单一节点更新，反复缩放不累加；同一天的小时区间显示小时数，日期覆盖按首尾自然日计算。

现有部署身份的只读 SSH 预检返回 `Permission denied (publickey)`，远端探测未执行，也未尝试替代凭据。四资产静态发布构建器已通过隔离 schema/alias 模拟，但缺新鲜现网 CAS，未生成声称可发布的正式清单，更未 apply。

追加本地验收：三入口原生指标各 20/20，视觉各 39/39，原 FC 全流程回归通过；包含零值、单项缺失、受限筛选不借全局值、当前小时 14:37 截断、错配实际窗口、提示幂等及小时计数。三入口语法与 pr-fast 自检通过。这些是本地 mock 及合同证据，未宣称真实 API 本时点值或生产修复完成。

## 当前小时合法缓存修正（#872 合并后）

#872 的静态版已经以 `nav-20261106T113924Z` 发布；实际页面已读回昨日 Admin 原生新客 115、复购率 91.77%、新客占比 34.95%，并确认结构区使用通用组件。以上是历史缓存的原值，并非新鲜采集承诺。

后续确认小时缓存仍有遗漏：`SummaryCache.key_of` 不包含动态 `period`。相同原始小时范围再次读取时，响应 query 的截止可能由 14:37 前进到 14:39，合法缓存中的 Admin 与 profile 实际截止仍是 14:37。旧前端要求完全相等，误将 11 项原生指标清空；此前“当前小时 14:37”测试只覆盖首次读取，未覆盖这个缓存命中场景。

本次仅修改三个前端入口：接受从所选起点开始、未超过请求实际截止和所选末小时边界的采集前缀，继续要求 Admin/profile 的实际期间一致及原有权限、站点、付款状态和细分条件；无 query.period 时仍只接受完整闭小时。卡片标出原始统计截止，保留采集时间和后端 stale 状态，不重算指标、不调用明细补造汇总。新增真实渲染器测试执行同范围第二次普通读取，保持原采集时间、rangeId 和 Admin/profile 期间，同时推进请求截止，断言 11 项仍保留。
