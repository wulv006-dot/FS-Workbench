## 固定归档与读取

全部在47.85.224.112云服务器，与用户电脑开关机无关。

- 主归档数据库：/var/lib/fs-data-archive/catalog.sqlite3；现有gzip不可变完整源响应及三个月滚动保留规则不变。
- Hermes固定读取：/fs/nightly-data/YYYY-MM-DD/，宿主机对应/var/lib/fs-hermes-fc/fs/nightly-data/YYYY-MM-DD/。
- daily/weekly/monthly/management/management_weekly.json为各报告指针，包含业务区间、状态、缺项、snapshot_id、SHA及不可变JSON文件名；证据保存在同目录SHA.json。
- FS研究使用既有注册证据与计算工具；服务器原生聊天可直接读取上述私有文件，再按权限调用工具。禁止以目录存在、mtime或任务completed替代范围/来源/完整性/SHA核验。
- 固定经营事实复用，流量近5日修正与第6日完整封账读取保持；空缺不补零、人数/率不逐日相加。估算只留报告，不能写入真实归档；原报告保留，补齐后按原修订入口追加核对。

## 恢复和告警

复用原fs-hermes-ops-bridge五分钟入口。营销日采、渠道日缓存、管理事实仅在失败且非活动状态时，每15分钟最多3次重试；不重启正在运行的共享服务/浏览器、不重新登录。写入请求前记原operation_id；系统调用超时/未知保留现场，先对账，不重放。原归档15分钟周期、渠道原Restart=on-failure继续。

当日01:45仍缺数，沿Hermes原生cron API建立一个可读回的只读补查任务；唯一日期名称+原生ID+创建意图防重复。模型最多20分钟/03:00前结束是任务约束；原生运行时仅有既有活动/空闲保护，本次不伪称新增了硬墙钟终止。补查结果存在才算产出，不凭任务创建成功称完成。

02:15仍缺数或报告失败/结果未知，通过原Hermes飞书watch联系Codex；当天同一故障不重复派发，未知通知保留outbox。Codex需明确回复事件ID接单；未接单不等于自动修好。原白名单之外不让Hermes擅自部署任意补丁。05:30后仍失败，报告明确缺项/依据/不确定性与后补条件；管理事实全缺时只发缺数说明，不把FC局部数据冒充全项目经营。
