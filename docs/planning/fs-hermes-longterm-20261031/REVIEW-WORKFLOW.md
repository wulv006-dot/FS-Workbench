# 独立Business审查交接

用户2026-10-31明确的本项目流程。Personal继续承担B线开发与技术主控，Business A继续施工，独立Business审查员仅做Review；审查不代替施工交付。

## 通知与结果

1. Personal B、Business A创建或更新本项目PR，并确认该版本准备好审查后，主动通知独立审查员。整包由主控创建集成PR时，由主控发通知；A未开PR的分支候选先交主控集成，不虚构PR通知。
2. 每次通知必含：PR完整链接、最新完整head SHA、本次目标、实际改动范围、已做检查，以及对应施工聊天和主控抄送目标。检查区分本机模拟、独立运行、CI、实际模型与生产；没有完成的如实写未验。
3. 审查员核对GitHub当前最新head，在自己的独立工作树审查，不操作施工目录。记录PR、head及审查范围，同一提交避免重复审查；不因一句旧结论把新head标成通过。
4. 结论发回对应施工聊天，并抄送Personal主控。问题写明文件位置、触发条件、影响和建议；施工方在原工作包/PR修复，固定新head后主动通知复查。
5. PR有新提交时旧审查结论不直接代表新版本通过；审查员核对差异后明确给出针对新head的结论，复用有效证据时说明范围。
6. 审查员不改代码、不提交、不合并、不部署、不真实业务写；结果仅通过聊天交接，暂不向GitHub发布评论、批准或驳回。不新增账号、凭据、权限、安全配置或付费模型调用。
7. 多PR到达时排队，一次在自己的独立工作树处理一个PR，不同时切换两个PR；先记录新通知，当前项完成后再处理下一项。

通知模板：

```
PR：完整URL
head：完整SHA（可附base SHA）
目标：本包要恢复/实现的行为
范围：实际路径及接口/消费者
检查：具体命令、结果与未验边界
回送：施工聊天链接/ID；抄送Personal主控
```
