## 现在并不是“已完成 V4，正在实施 V5”

需要分清三件事：

| 对象 | 当前应如何理解 |
|---|---|
| 已有 FS / Hermes | 已有业务系统及历史开发成果继续存在。用户确认已有读数据、订单、用户、写商品、改价、折扣优惠、自动上新及活动承载等能力。施工时核对实际入口和当前授权，不重新从零做一遍。 |

**纠正此前措辞：不能写“在已完成的 V4 成果上继续”。应写“在现有 FS/Hermes 上，按本文件核验并补齐能力”。**

本次未审计所有其他 Work 会话或生产活动版本，因此不声称外部绝对没有相关开发。正确做法是：没有实际证据的新增项不计完成；现场已经完成的项核验后复用，不重复施工。旧 Hermes V2 / W5、原用户看板、定价 V3 等属于各自历史项目，不与这次方案编号混为一谈。

# 一、长期目标与项目范围

## 1.1 最终要得到什么

用户提出目标和经营约束，Hermes 判断需要什么证据、选什么模型和执行者，形成方案，调用已授权的业务能力，安排团队完成专业工作，接收成果并复查效果。

**用户管理目标、重要取舍、授权边界和业务知识；不再逐次手工安排取数、复制数据、切模型、导出文件、催每个任务。**

系统最终形成：

**目标 → 按需事实 → 判断与计划 → 程序／模型／员工／岗位 Agent → 真实执行与产物 → 效果复查 → 方法改进。**

“AI 蜂巢”指围绕同一目标可靠协作，不是让大量 Agent 永久在线互相聊天。一个任务要有明确负责人、交付物和验收条件。

## 1.2 FS 与 Hermes 的关系

| 层次 | 主要职责 |
|---|---|
| 用户与负责人 | 给目标、定取舍、批准重要边界、维护知识、检查结果 |
| Hermes | 调查规划、模型与执行者选择、动作比较、任务拆解、业务验收、持续复查 |
| FS 共用底座 | 身份、数据、工具、计算、文件、任务状态、执行与真实回执 |
| 原业务执行器 | 继续承担自动改价、商品／球员上新、优惠、活动配置与发布等已具备能力 |
| 团队与岗位 Agent | 完成被分配的内容、研究、专业流程；人类负责质量和例外 |

模型不是数据库；聊天记录不是经营账本；团队成员不是自动获得全站权限的管理员。

## 1.3 必须保留的现有资产

沿用现有业务来源、后台认证、自动化执行器、发布流程、知识审核和已验证方法。已有功能只有在真实不适用时才改，不因新的总方案而全部重构。

用户已确认的业务能力按“存在、待核入口”登记；资源位和更多网站前端配置按“后续能力”登记。账号具备权限、Hermes 已接通工具、本目标允许执行，是三个独立事实。

前台逐步收敛为必要经营概况、目标与任务、待审事项、重点对象及效果记录。旧页面只有在替代能力验收、依赖确认后才退役，不先删页面再期待 AI 补位。

### 能力开放原则（2026-11-01用户补充）

目标是充分使用Hermes已有Agent框架能力。在现有合法身份、数据范围、工具和任务授权内，普通资料读取、调查分析、计算、公开检索、文件生成与修改、目标拆解和工具选择应连续自主完成，不逐次索取同义批准，不为未知费用、局部缺项或完整观测不足另设没有依据的全局门槛；真实不足如实保留，不因此阻断其他可完成工作。

固定材料任务的三文件工具、特定报告的只读工具集，只约束相应任务，不能提升为Hermes全局能力上限。官方工具发现、按需装载等机制先核实际工具目录、调用链和现有授权，再做兼容；不能仅因工具名称或包装与旧预设不同就禁用，也不为通过检查伪造工具已接通。通用能力优先复用框架与现有FS工具，不新造替代Agent执行器。

核心敏感边界保留真实身份、凭据和客户隐私、跨用户数据隔离，以及直接影响售价等经营动作的合法性。用户有明确需求且处于已有有效授权范围时，Hermes可调用现有规则与工具完成改价等操作，继续由原执行器核当前价格/成本规则、执行和读回，不永久只给建议、不重复同一授权，也不另建绕过原writer的改价路径。新对象或实质超出授权的动作再核具体缺口；平台真实拒绝、原ID/UNKNOWN对账及现行业务财务规则保持。

本条明确施工方向，不等于尚未验证的工具已上线。当前先恢复真实材料执行，再按实际缺口逐项释放普通能力；真实A2业务scope未证明前仍不能以页面admin或文件授权冒充。普通能力、任务上下文限制、业务权限、技术兼容与隔离测试守卫分别核对，不混成一套全面禁用规则。

## 1.4 本项目不做什么

不重建整个 FS，不复制原定价引擎和采集器，不建立第二套客户数据库，不把全部订单向量化，不要求首发配置十几个常驻 Agent，不默认引入大型消息平台、微服务拆分或全仓重构。

本文件不讨论席位采购，不重新分配订阅，不把个人和团队的使用额度视为可以任意合并的运行资源。能力建设与实际计费通道分别管理。

# 二、双线分工与共同维护规则

## 2.1 A 线：FS 工作台、数据工具与执行协作底座

A 回答：**怎样让工作真实完成，权限、状态、数据和文件都可靠？**

负责持续会话、UI、上传和解析、搜索、隔离计算、文件生成与下载、权限、目标／任务展示、受控数据接口、数据与文件生命周期、现有业务动作适配，以及后期团队接单和回写。

A 不自行决定高价值客户定义、优惠策略、模型选择或经营目标优先级。A 接收 B 的需求，用现有服务实现可核验的工具。

## 2.2 B 线：Hermes 推理、按需经营与工作编排

B 回答：**为了目标，应该查什么、交给谁、怎样判断和采取行动？**

负责目标理解、业务知识引用、DeepSeek/OpenAI 路由、证据交接、查询计划、用户筛选和追踪、动作比较、执行者选择、任务拆分、业务验收、效果评测和方法候选。

B 不自行另建后台登录器、采集器、文件库、客户库或平行写入者。数据和执行都通过 A 提供或原系统已有的受控工具完成。

## 2.3 共同部分只维护一份

共同维护一套任务身份、授权范围、事实及证据、文件登记、动作回执和阶段状态。

公共入口、共享服务、数据库迁移、controller 和发布配置由一个明确维护者改动。两条线可以并行开发，公共生产安装仍串行协调。只开一个 Work 任务时，可在一个任务内按 A/B 责任推进，不要求额外创建 Agent。

**两线是责任分工，不是要求自动开外部/Codex 子任务。**涉及生产仍使用本机获批通道；不新建云端 SSH，不借团队协作放开服务器管理入口。

## 2.4 依据冲突如何处理

用户最新明确决定与现行已确认业务合同优先。本文定义未来能力与工程顺序，不覆写当前有效的定价、来源、退款、发布和权限规则。

历史方案只供追溯，不作为恢复旧参数的依据；正在运行的业务合同也不能被“长期只读”的旧规划永久封死。能力开放通过对应阶段和有效授权实现。

## 2.5 已确定的两个工作区主从关系

用户最新指定：**个人版为主施工，工作版为协同施工。**“主／协同”是工程责任和集成关系，A／B是功能责任线，二者不能混为排序。

| 责任 | 个人版主施工 | 工作版协同施工 |
|---|---|---|
| 项目身份 | 项目技术主控、集成负责人，同时施工B线 | A线独立施工负责人，向主控交付可验收成果 |
| 主要实现 | Hermes目标、模型路由、查询计划、用户追踪、决策与后期任务编排 | FS界面、会话、附件、联网工具、计算、文件、权限、受控查询、存储与后期执行适配 |
| 统一事项 | 维护唯一主文件、当前阶段、任务边界、接口共识、共享代码归属、整体验收与发布协调 | 按同一主文件施工，提出接口和范围修改建议，通过PR／任务记录交接 |
| 局部自主 | 在B线范围直接开发、测试，不替A重复实现 | 在A线已分配范围直接开发、测试、提交PR，不是只读或审稿助手 |
| 生产和跨模块 | 按现有授权统一协调合并、安装与读回，不获得无限业务批准权 | 默认不独立发布共享生产服务；专项代办需明确范围、入口与授权 |

用户仍决定经营目标和重大授权。主控不能改变用户规则；协同方可以提出异议和替代方案，但不能自行另建主方案或绕过集成发布。

两个工作区的共同事实以仓库正式主文件、任务记录、代码提交、PR及真实回执交接，不把另一工作区的聊天或记忆当作已自动同步。这里只安排用户明确启用的两个Work，不额外自动创建外部Codex或子Agent。

## 2.6 启动、代码归属与交接

先启动个人版，确认主文件正式仓库路径、实际基线、A/B第一轮范围和公共文件唯一维护者；工作版可同步只读核对A线，不必等待主控完成全部设计。已有明确范围的独立代码与测试可并行，公共文件和数据库迁移先明确归属。

每个并行任务使用自己的分支和独立工作目录／worktree。不得同时修改同一checkout的索引或相互切分支，不覆盖未提交改动，不用清空工作区解决冲突。实际路径由阶段0核对，不在说明里假设E盘或D盘某个目录必然可用。

每个工作包至少明确：负责人、当前阶段、基线提交、实际可改路径、交付物、接口依赖和验收条件。交付附PR／提交、相关测试、真实调用状态、未完成项和下一步；原始客户数据与密钥不进入交接文件。

同一共享文件每轮只有一个维护者：默认由个人版主控集成，或明确授权工作版独占修改；另一边提需求或补丁而不同时写。主控复核并汇总进度，不重做协同方已通过的实现与全部测试。

个人版暂不可用时，工作版继续已分配的独立开发和测试，不自动升为总控、不接管生产发布；角色移交需用户明确指定并记录基线与待办。无跨工作区消息工具时，以共享仓库任务／PR传递，不声称已经通知或唤醒对方。

## 3.1 依赖原则

阶段0之后，A 的工作台和 B 的模型／查询研究可以并行。B 不等全部 UI 美化，A 不等全部经营策略研究结束；需要的真实工具接口完成后即可会合。

当前执行顺序由顶部2026-11-01用户纠偏覆盖：先完成阶段1，暂停阶段2及以后新增施工。上句保留一般依赖关系，不得据此恢复本轮分散推进；阶段1所必需的具体接口修复仍由原owner协作。

阶段3以阶段2的目标、证据和动作范围为前提，但无需等所有用户分层场景完成。已有自动化自然运行不受此阶段划分影响。

阶段4可以提前做一个非生产技术可行性验证，但不抢占阶段1—2的主要施工资源；账号未开通或连接未完成不阻断基础能力。

阶段5需要阶段2的经营判断、阶段3的真实执行，以及阶段4选定协作模式。某岗位自动触发不可用时，可由员工主动接单完成活动，但必须如实标注人工启动，不把它记成自动蜂巢验收。

阶段6按已经验证的流程逐步开放，不要求一切必须等远期资源位接口齐全。

## 3.2 每阶段都有可用成果，不做一次性大交付

某阶段有独立价值的子闭环验收后可以先交付；但阶段整体未过关就保留“部分完成”，不擅自把总进度改成下一阶段已完成。

后续功能可以研究接口，不能把未来字段、完整组织编排或全站资料迁移变成当前小闭环的前置条件。

# 五、阶段1：让 FS 内的 Hermes 真正能完成工作

**首个验收请求：**“这是本周的真实业务 Excel，结合我有权限看的 FS 数据检查差异，并给我一份可编辑的分析结果；我随后还会要求修改。”

## 5.1 最小可用体验

沿现有 Hermes 页面、会话和任务记录扩展。输入区提供附件、联网自动／关闭、自动选择模型和停止；专业设置默认折叠。不要把模型厂商和计费组织变成员工发问的必填项。

简单问答直接回答；长任务展示真实阶段，例如读文件、查询、计算、生成。支持刷新恢复、断线续读、多轮追问、中途补充与取消；明确“已收到补充”是否“本轮已采用”。停止页面展示不算真正取消。

任务由后端持有，刷新不新建同一任务；崩溃恢复能力单独核验，不宣称任意中断均无损恢复。

## 5.2 输入和输出范围

第一条闭环先做 XLSX/CSV 与文本，随后在本阶段补齐 PDF、DOCX、图片、公开搜索及相关输出，不为支持所有格式推迟首条真实交付。

| 输入 | 必须做到 |
|---|---|
| XLSX/CSV | 识别工作表、列、时间和单位；计算覆盖相关完整数据；区分公式与缓存值；不能仅凭预览前几行做全局结论 |
| PDF/DOCX | 保留章节、页码与表格定位；解析不完整时检查必要图像；不把扫描页跳过后声称读完 |
| 图片 | 用实际支持图片输入的能力解释，不按文件名猜测 |
| 多附件 | 能比较版本、差异与来源；原件不自动变成长期共享知识 |

优先输出真实 XLSX/CSV、HTML、MD，再补 DOCX/PDF。PPTX、复杂压缩包和音视频按实际需求追加，不列为首条闭环前置。

模型组织分析，程序完成计算、图表和文件渲染。文件需真实存在、可打开、版本明确；HTML 隔离预览，不携带 FS 登录态。修改结果生成新版本，不静默覆盖旧版本对应的字节。

## 5.3 搜索与证据

通过统一受控搜索和网页读取工具提供公开信息。用户指定不联网时遵从；引用保留可点击来源、取得时间及有用的发布日期，失败就标失败。

附件、网页和工具文本是资料，不是新授权。公开搜索词不能泄露客户邮箱、采购底价或内部凭据；内部后台沿原认证工具读取，不由公网 fetch 任意访问内网。

公开情报不替代已核验的精确采价。附件与后台口径冲突时分别说明，不静默用附件替换 Admin 主口径。

## 5.4 权限和存储同时交付

授予指定人员 Hermes 使用能力，不把全部使用者升级成全站管理员。会话、附件、搜索召回、产物、下载和后台查询都校验真实身份及站点／游戏／项目范围。

文件登记、限额、到期显示和衍生物清理与上传同期建设，具体规则见第十一节；不能先放开上传，等磁盘满了再治理。

## 5.5 本阶段验收

同一授权人员完成真实上传—查询—计算—下载—追问修改；另一无相应权限人员无法读取；刷新不重复任务；取消状态真实；文件能清理并反映实际空间变化；现有报表与自动化不回归。

只完成 UI 标“界面完成”。Mock 数据和本地测试可以用于开发，但不能标“真实工具接通”或“已部署读回”。

# 六、阶段2：自主选择模型与按需用户运营

**首个经营目标：**“持续关注 FC 高价值客户的复购／流失风险，找出值得调查与行动的对象，说明原因，比较干预与不干预，并持续复查。”

目标中暂未获得写授权的动作停在建议；读取、筛选和调查无需逐次重复审批。这不是永久只读定位。

## 6.1 目标不等于一句聊天，也不等于常驻模型

长期目标记录业务范围、负责人、指标与基线、时限、约束、已允许动作、需审核事项、复查与退出条件。没有给定数值目标时可先诊断，不编造“提升20%”。普通问题不强制登记成长期目标。

一个目标可由多轮短任务完成；每轮结束保留必要状态，等待新事实或下次复查，不让一段超长上下文一直运行。

## 6.2 DeepSeek / OpenAI 如何分工

| 类型 | 起步安排 | 不能误解成什么 |
|---|---|---|
| 熟悉流程、普通查询、轻量变化解释 | DeepSeek 组织现有工具 | 不是强迫它承担所有困难任务 |
| 精确统计、核算、格式转换、规则执行 | 程序完成 | 不是让更大模型心算替代程序 |
| 新问题、复杂材料、多目标取舍、调查设计 | 适合的 OpenAI 模型可从任务开始主办 | 不是只在 DeepSeek 失败后才能用 |
| 图片／复杂页面理解 | 通过实测的视觉能力 | 不能假设所有模型或接口都兼容 |
| 高影响决策与重要分歧 | 必要时增加一次独立复核 | 两模型一致不等于事实正确 |
| 日常追踪 | 先变化检测／到期判断，再按需调用模型 | 不是每个客户每天一份模型报告 |

精确型号、上下文、推理档位、工具兼容和价格由真实账号能力确认。方案不把 ChatGPT 展示名写死成生产 API 型号；保留原 DeepSeek 客户端，OpenAI 使用独立适配，避免全局替换兼容变量破坏原链。

用户最新执行顺序：现阶段相关模型工作先沿DeepSeek，其他通道先做本地契约/模拟验证，待API额度与配置就绪并完成相应验证后再正式切换。上表的OpenAI分工保留为目标能力，不据available标记、验证模式或Git合并提前启用。能力不足如图片/工具不假装已支持；不新增真实API测试或费用授权。

### 自主路由的三个步骤

**先过滤能力与权限。**需要哪些输入和工具、数据允许进入哪些通道、时限和可用性如何。

**再选择达到质量要求的模型。**按照任务类型的真实评测选取，不单纯按价格、品牌或文本长度决定。

**过程中按具体困难调整。**证据矛盾、方法不适用、工具错误、重要反证等可以触发补证、换模型或复核；模型自报信心不是唯一依据。缺数据先补证，不换贵模型猜数字。

模型可以提出升级理由，受控路由器决定执行。通常一项任务一个主办模型，不固定多模型串联；正常工具循环不每步重新选路。

切换时交接目标、约束、已核事实、来源、已做动作、当前困难和必要下一步，不搬运私有推理，不重发原成功动作，不把全量订单和聊天历史重复传给下一模型。

## 6.3 按需数据计划

Hermes 先读数据目录：字段、来源、时间覆盖、新鲜度、过滤能力、口径和缺项，再提出结构化查询请求。身份和范围由服务端赋予，模型不能写一个 owner 字段获得权限。

查询顺序：

**群体摘要 → 候选筛选 → 必要客户详情 → 变化／到期补查 → 最小证据和结果。**

在完整授权范围内由程序聚合可以是必要的；模型逐行读取全体订单通常不必要。候选查询要声明总量、排序、分页和截断，不能任意取前100名就宣称找齐全部高价值客户。

源系统支持客户ID、批量IN、更新时间或游标时优先使用；不支持则沿原统一数据通道维护最小索引或分段增量，不能为每个目标新建全量采集器。确需大范围统计时可以分批流式完成，有明确用途和覆盖说明，不把“少取数”做成损失统计正确性的硬限。

周更或历史冻结报告与更新鲜的动态观察分别记录实际截止，不覆盖旧快照，也不冒称局部来源实时且完整。

## 6.4 只保留四类必要状态

| 状态 | 保留理由 |
|---|---|
| 最小客户事实／可更新特征 | 身份、历史首购、最近有效购买、必要金额／频次／退款和成本覆盖，避免把老客当新客 |
| 目标与关注状态 | 为什么关注、依据哪版证据、当前阶段、下次检查与退出条件 |
| 真实动作与观察记录 | 对谁做过什么、授权与回执、试验分组、观察锚点与结果 |
| 已确认业务方法 | 适用条件、步骤、反例、版本和失效条件，不存成当日价格永久规则 |

这四类是逻辑用途，不要求新增四个数据库。原始订单详情、重复名单、完整网页和模型中间表按用途短期保存。

仅保存查询 recipe 或 hash 不一定能重现历史；需要对应事实版本，或保存少量必要的冻结结果。无法回源时明确说明，不用摘要冒充原始证据。

## 6.5 第一场景：高价值客户动态追踪

价值评估结合可得的净实付、采购贡献、购买频次、持续性、退款和服务成本。区分历史高价值、近期高价值、新客高潜力与消费集中但持续性不明。没有成本就不声称知道净利润。

风险结合可比群体或个人购买节奏；不是所有人7天未买都算流失。稀疏历史保留不确定性，不编精确概率。授权范围内跨游戏活跃、退款、交付问题或正常间隔都可能改变判断。

动作始终包含不干预，其他候选包括服务跟进、商品解释、内容提醒、限定优惠和替代商品。不把高消费自动等同最大折扣，也不把“不复购”自动解释成价格问题。

追踪触发来自相关新事实、到达检查时间或目标约束改变。没有新订单也可在到期时判定仍未复购；已解决、已复购、目标失效则退出或降频。

新客复购沿可信 Day0 和成熟的7／14／30天窗口。观察期首单、历史首购和源系统新客标记分开；游客身份按已确认映射，不猜测合并。仅有付款用户资料时不推断全部未购访客动机，拉新还需对应流量和转化证据。

## 6.6 决策卡最少回答六个问题

对谁做什么；哪些证据支持；哪些仍是缺口；为什么不选其他方案；需要什么授权；何时复查、继续或停止。

阶段2验收至少包含一个真实群体、必要客户下钻、一轮变化／到期复查、实际模型选择回执、可复算结果和数据负载计量。测试覆盖退款更正、历史不足、身份歧义、截断与未成熟观察期。

第一批可用小组真实案例做对照，不追求一次覆盖所有用户分层。方法调试题与未参与调试的测试题分开；不能只让模型给自己评分。

# 七、阶段3：从判断进入已有业务执行链

**目的：完成一个真实、范围明确、可读回的经营动作，证明 Hermes 不只是建议器。**

## 7.1 优先复用，不从零建立写系统

候选来自用户已确认具备的商品、优惠、上新或活动能力。阶段0已核验的原执行器、operation_id、幂等、锁和回执继续作为唯一真源。

自动改价保持原执行者和当前有效规则。Hermes 可研究调整或调用已授权控制入口，但不增加第二个逐小时直接改价的 Agent，也不把新模型复核插入正常改价必须等待的路径。

当前定价合同由实际活动版本决定。本文件不重述和重置具体锚点、红线计算范围、优惠窗口或成本样本规则，以免未来施工把历史参数带回生产。

## 7.2 从方案到执行的最小链

**明确差异和作用对象 → 程序核验当前事实与规则 → 匹配现有或新批准范围 → 原执行器完成动作 → 读回真实状态 → 登记效果观察。**

已存在有效范围授权就引用它，不重复要一次相同审批。没有授权时只暂停相关副作用，继续完成调查、草案和其他允许工作。账号总权限不能代替该目标的业务授权。

建议按策略包批准：对象范围、允许动作、期限、额度／折扣约束、频次、去重、退出条件。无需让用户审批每次读数。

## 7.3 写前和写后各查什么

写前核对象仍合格、商品和优惠状态未发生实质变化、授权有效、叠加与冷却条件满足、没有相同动作已经完成。

写后按该业务现行验收口径查询原回执和实际状态。未知状态优先对账，不换 ID 盲重试。不能把新方案无关的额外验证强塞成旧自动化的阻断条件。

停止新动作不代表已发生的副作用自动撤销。页面可恢复旧配置；已使用优惠、已付款订单和已发出消息需按现实补偿，不宣称整体可原子回滚。

## 7.4 本阶段过关

至少一个得到明确授权的真实动作完成并读回；重复请求不重复执行；过期／变更授权不会继续写；局部失败不影响原全站业务；观察计划从实际执行时间起算。

尚未获得生产授权时可以交付草案、适配和预演，但不能标本阶段执行闭环完成。当前未接通消息工具时，不把“优惠已创建”声称为“客户已收到”。

# 八、阶段4：团队 Agent 与员工任务协作

**目的：Hermes 能把明确工作交给合适的人或岗位 Agent，并收到可验收成果，不是只成功发出一条指令。**

## 8.1 先选执行者，再选模型

| 工作 | 优先执行者 |
|---|---|
| 精确、重复、已有规则的动作 | 原 FS 程序 |
| 常规与复杂内部业务调查 | Hermes 内部 DeepSeek／OpenAI |
| 活动文案、FAQ、项目材料或已维护的岗位流程 | 人类负责人及岗位 Agent |
| 资源协调、重要主观取舍、业务关系判断 | 人类负责人 |
| 代码改动与现场部署 | 指定本机 Work／Codex 入口和原发布链 |

每项任务一个主办者。需要独立评审时另设目的明确的评审工作，不让所有模型轮流重写。

首发一个 Hermes 主控，加一至两个明确岗位节点即可。节点是能力角色，不要求人数与 Agent 数一一对应，也不要求常驻推理。

## 8.2 两种运行方式，结果契约相同

**自动方式：**实际工作区允许并已配置时，FS 触发已发布岗位 Agent，Agent 按受限身份取任务和资料，提交成果，FS 验收。

**人员接单方式：**员工在 FS 领取任务，在自己的授权 ChatGPT／工作环境推进，再回交结果。它是有效协作方式，但状态必须写“人员启动”，不冒充服务器自动唤醒。

不控制私人聊天，不共享个人 Cookie，不假设个人与团队记忆自动同步。

## 8.3 平台能力核验与官方边界

截至本次核查，官方文档提供已发布 Workspace Agent 的外部触发与 beta 运行状态查询；触发受理不等于工作完成，最终回答当前不能直接经该触发接口取得，因此需要单独的成果回写。[S1]

触发使用工作区的 Workspace Agent 访问令牌，须由管理配置允许；不能拿普通模型调用凭据或员工登录状态替代。[S2]

ChatGPT 可通过自定义 MCP 连接公司工具，包括获准的写动作；是否在本工作区开放、连接是否能用及访问范围必须实际验证。[S3]

本文件不把团队连接当阶段1—2的前置。施工到此时重新核对官方接口和实际账号，不仅凭本文件中的历史说明部署。

## 8.4 双向连接的最小工具

读取分配任务、按范围取得证据、报告进度／阻塞、提交成果／文件、查询验收状态。先开放非生产任务结果写入，再研究更广权限，不开放“任意调用 Admin”工具。

FS 启动 Agent 的身份，与 Agent 调用 FS 的身份是两条授权链。任务ID是定位符，不是访问密钥；模型不能填一个负责人ID获得跨项目数据。

触发只携带任务ID、版本、目标摘要和证据引用，任务资料按需取；避免每个节点各复制一份客户库。

## 8.5 每份任务包必须明确

目标与范围、交付物、验收标准、事实版本与截止、允许动作和禁止事项、依赖、负责人、回写位置、异常上报条件。

示例：“根据已确认商品与优惠方案，提交英文活动文案和FAQ；不改折扣、不承诺未确认时效、不发布页面；成果提交至对应 FS 任务。”

远端受理、运行结束、成果收到、业务验收通过分别记录。重复受理、迟到结果或被取消的旧任务不能覆盖新版本，也不能触发新的生产动作。

## 8.6 过关条件

用非生产材料完成“FS任务→真实接单／触发→受限读取→真实成果回写→验收”。随后验证无关任务越权失败、重复事件不重复工作、撤权和取消行为清楚。

没有成果回写就不能宣布接通。平台自动触发不可用时继续人工接单和基础业务，局部问题不阻断全项目。

# 九、阶段5：一个完整活动从目标到复查

**首个综合试点：围绕复购目标，复用已有活动模板做一轮限定范围活动。**

不默认修改正在运行的万圣节页，不把新设计复杂交互或新资源位接口当首发前置。具体数值目标、商品、优惠、人员和日期由真实基线与批准确定。

## 9.1 完整工作链

| 步骤 | 主办方 | 要交付的真实结果 |
|---|---|---|
| 判断是否值得做 | Hermes＋FS | 用户／商品证据、备选动作，允许结论是不做活动 |
| 形成方案 | Hermes＋原业务核算 | 目标群体、商品及规格、优惠和范围、衡量办法 |
| 内容与FAQ | 负责人＋岗位 Agent／员工 ChatGPT | 可用英文材料、来源与版本，不擅改商业条件 |
| 模板配置／必要工程 | FS工具或本机工程负责人 | 未公开预览，必要时PR及测试 |
| 联合验收与批准 | 程序＋Hermes＋必要人审 | 一份明确方案与差异，不逐个按钮审批 |
| 正式执行 | 原业务执行链 | 实际配置／优惠／发布回执及读回 |
| 复查 | FS事实＋Hermes | 订单、使用、复购及可得贡献，未成熟项明确 |

内容和模板工作可以在方案冻结后并行。商品、平台、区服、规格、优惠身份和作用范围不能各环节自行改动。

## 9.2 验收不止页面看起来完成

沿活动实际规则检查商品可售、金额和优惠、加入购物车、结算入口、实际应用范围，以及返回重购、删除购物车、重复操作和多优惠冲突等相关历史问题。

不为验收擅自真实付款或创建未经批准的促销。预览通过与生产发布分开；已发布与客户实际使用分开。

结果追踪按既有活动来源和实付口径。活动订单相关金额不必然等于活动增量；多活动关联订单不能简单重复相加。

## 9.3 过关条件

一项明确目标经过多角色协作，有完整成果、真实批准执行、状态读回和成熟／待成熟结果记录。若团队环节由人启动，活动闭环可通过，自动团队派发能力仍单独标待验。

# 十、阶段6：持续经营与跨游戏协调

## 10.1 先把已验证流程稳定重复，再扩游戏

将验证有效的高价值用户追踪、新客复购或活动流程做成持续目标。程序处理变化和到期，模型处理必要判断，越界或重要变化再提交负责人。

低风险读取、筛选、文档和草案自主完成；已批准策略范围内的动作可执行；越过新对象／新优惠／新渠道／新期限时才补批。不要把用户变成每个工具调用的审批员。

## 10.2 解决真实的全局冲突

优先处理同客户重复触达与优惠叠加、同商品多任务修改、同页面／资源位覆盖、同一供应能力被重复承诺。规则确定的由程序校验，需要取舍的由 Hermes 提议或负责人决定。

一个项目最优不一定等于全公司最优。目标优先级和经营约束由负责人明确，不按哪个 Agent 提交得快或措辞强烈决定资源分配。

供应商系统、资源位和前端配置尚未具备时保持对应缺项，不虚构自动派单或资源配置成果；只扩展已接通范围。

## 10.3 持续方法改进

收集真实失败、有效方法和执行结果，形成带条件、反例和时效的候选方法。用未参与调试的案例验证，再沿现有知识审核、发布和撤销机制进入共享知识。

目标是让 DeepSeek 或适合的程序下次更独立、更稳定地处理同类工作，不是永久求助更昂贵模型。个人上下文、项目事实、共享方法和核心生产规则分层管理。

## 10.4 长期验收

能够暂停一个目标而不停止全站；重复事件不重复经营动作；任务和文件增长可控；查询负载、费用、人介入、返工和成熟业务结果可比较。

没有对照或可识别条件不声称因果增长。没有成熟观察不报收益。不是“自动任务越多越好”，而是完成有效经营工作的代价和风险更可控。

# 十一、贯穿全程的数据、文件与磁盘治理

## 11.1 少保存重复，不是不要历史

数据治理覆盖查询过程、模型输入、临时文件、索引、日志和备份，不只看最终界面返回了多少行。

必须保留支撑历史首购、身份映射、退款更正、真实动作、试验分组与结果复查的必要事实。不能把“订单详情用后清”错误实现成“忘记所有历史”，从而把老客户再次归类为新客。

原用户分析周快照、实时观察、订单事实和附件是不同用途，不套同一个保留期限。原业务的法定或内部保留要求优先核对，本文件不替代它们。

## 11.2 首发建议的生命周期

以下参数只作为新功能的起步配置，阶段0结合空间和现有政策确认后实施；不追溯授权删除现有业务文件。

| 类别 | 起步建议 | 保留与清理原则 |
|---|---|---|
| 上传分片、转换件、计算中间文件 | 任务终结后24小时内清理 | 运行中或状态未知先确认归属；孤儿任务有可核验的过期处理，不能永久挂住 |
| 普通上传原件 | 30天 | 到期可延长或明确归档，文件卡显示期限 |
| 普通生成产物 | 90天 | 不因反复下载自动永久保留；版本同样计入容量 |
| 普通会话及派生摘要／索引 | 90天起步 | 项目事实和正式方法可显式转为另一保留类；删除会话不应暗留全文摘要 |
| 临时客户详情和重复派生结果 | 依任务需要设短期缓存 | 不默认每次保存整群名单；必要事实单独提取 |
| 正式项目材料、实际动作与必要证据 | 沿明确的业务保留规则 | 不能随普通附件清理一起删除；到期与删除责任明确 |

原件、页面图、解析文本、缩略图、全文或向量索引、模型提供方可管理文件、对象版本和相关备份都应纳入同一生命周期视图。

本地删除不等于提供方所有日志立即消失；供应商保留按真实条款和实际可管理接口说明。文件已过期不可回源时，界面和结论都要显示，不能用摘要冒充仍可阅读原件。

## 11.3 配额和保护

在现场有足够余量的前提下，新功能可从单文件50MB、单批最多10件且总量200MB、普通用户2GB、全站新增文件空间10GB开始测试。个人额度共同受总空间约束，解析扩展和中间件也计量；这些不是已经生效的限制。

接近阈值先处理已到期内容和告警，空间不足限制新增大文件或非必要批量产物，不停原定价、不删仍有效的正式成果。需要扩大时依据实际使用调整，而不是为节省空间让所有功能一律不可用。

上传和解析采用流式、分页、分批处理；禁止为了算 hash 一次性把整个大库读入内存。附件字节不塞进主库 BLOB；原始查询和模型输入不在日志里再完整复制一次。

对于用户上传的压缩包、宏、脚本和生成 HTML，按支持范围限制解析、外链访问与执行；计算在隔离工作区内，不能继承生产密钥和任意服务器目录。

## 11.4 缓存、索引和清理

按文件内容、解析器版本和权限域复用解析结果，后续只读相关章节或行列；不能把全部附件自动加入永久向量库。

需要共享引用时区分逻辑授权与物理对象；一人删除不能误删另一有效引用，也不能通过去重暴露其他人的文件是否存在。

删除先撤销访问，再清理可控字节与索引并记结果。失败有有限重试和可见状态，不仅在数据库里打“已删”标记。长期目标需用的证据快到期时，保存必要小证据或延长明确范围，不能为一个小结论保留整库副本。

## 11.5 备份治理

临时分析空间不纳入长期整库备份；正式事实和关键项目成果沿原恢复策略备份。所有备份占用纳入总容量，不把主库缩小当成整机空间已释放。

旧库压实、迁移、恢复点退役和备份永久删除沿现有专门授权推进，不因本方案提出省空间就盲删。SQLite 等实际文件空间是否回收要单独核验，不以删行数冒充文件已缩小。

旧备份中的已删除副本随实际轮转到期；恢复后重放删除／过期状态，防止文件复活。保留恢复所需的完整链，不能只看副本数做机械删除。

## 11.6 作业时间

新增例行研究、追踪、清理和学习任务沿北京时间00:00—07:00窗口。用户当前交互按需运行；原已授权采价、改价和已有实时动作不被新窗口停掉。

新的全天事件触发需在目标和调度授权中明确。上传容量检查即时执行，不能等夜间再避免写满。

# 十二、共同对象、权限与接口约定

以下定义用于让 A/B 和外部执行者对同一任务有一致理解，不要求创建新的独立中台、十几张状态表或一套新的审批系统。优先映射到原 conversation、run、目标、操作和产物记录。

## 12.1 五类核心对象

| 对象 | 最小内容 |
|---|---|
| 目标 | 身份／负责人、业务范围、目的与基线、约束、有效期、允许动作、复查和停止条件 |
| 任务 | 父目标、任务ID与版本、主办执行者、依赖、交付物、验收、状态和阻塞 |
| 证据 | 来源、字段／口径、时间与版本、覆盖／缺项／截断、授权范围、结果引用和保留用途 |
| 产物 | 文件ID、任务／项目归属、版本、格式／大小／哈希、访问权限、到期和派生资源 |
| 行动 | 对象、拟变更、规则／授权引用、原操作ID、执行者、实际回执、观察窗口和补偿状态 |

业务方法继续进入原知识机制，不因这张表重复建库。客户当前状态和临时结论不直接发布为共享业务规则。

## 12.2 数据工具的最小逻辑能力

数据目录与覆盖查询；完整范围的群体聚合；可过滤、分页的候选筛选；授权客户必要时间线；变化查询；到期观察；现有业务动作的准备、执行和读回。

返回数据同时说明来源、新鲜度、是否完整、分页位置、缺失字段及可测成本。接口形状合法不代表业务含义正确，币种、单位、净实付、观察窗和身份仍需复用正式口径核验。

授权身份从服务端上下文取得。模型传来的目标、过滤条件和对象ID是请求，不能替代权限。不给模型任意 SQL 写入或任意后台 URL 代理作为捷径。

## 12.3 权限范围

功能权限与业务数据范围分开。可以上传分析不代表能读所有游戏；可以使用更贵模型不代表可以触达客户；共享会话不扩大接收者原有数据权限。

员工互动连接与岗位 Agent 服务身份分别配置。公司资料只能进入获准处理的模型或组织，不能为消耗剩余额度自动跨通道发送敏感内容。

不把生产凭据写入附件、任务文字、GitHub 或浏览器前端。撤权后，新的工具调用、成果下载和副作用重新检查；原已发生动作保留真实对账。

## 12.4 状态和重试

至少分清调度、运行、交付、经营效果：已派发不是已执行，运行结束不是成果已回，成果已回不是验收通过，动作生效不是收益成熟。

同一事件重试复用身份；任务内容变化用新修订，不挪用原请求ID伪装同一次。操作状态未知先查询真实状态，不重发副作用。迟到结果可作为证据保存，但不能覆盖当前获批版本或继续执行已取消任务。

已有确定性任务的锁、幂等与CAS继续复用，不能再套一层相互冲突的“安全账本”。日志保留必要字段与错误，不倾倒全部客户资料。

暂时性网络、限流与服务故障在任务已有预算内有限退避，尊重来源Retry-After；认证、权限、参数、确定性缺失不反复重试。只重试失败的独立步骤，不重复已成功结果。写回不确定先读取原操作；限额与具体间隔采用现有实现或相关测试确定，不额外复制一套调度器。

## 12.5 业务口径不变量

Admin 主源、Order 补源；自营主站及授权卫星站纳入，独立分销按已有范围排除。来源按下单时记录及既有空白来源规则处理，不另造归因。

优先使用Admin实际支持目标日期范围的原生汇总。详情和日趋势按接口真实上限分段、分页、去重与聚合；不机械要求所有原生汇总都采用28天切片。数据口径归属与代码协作范围分开，分销数据不纳入某经营指标不等于其代码永久不可协作。

FC写价成功沿最新用户口径：本次Order后台修改明确提示业务成功，随后从Admin重新查询对应商品单位价格与目标一致即可记录成功；公开页/地区展示/PUBLIC_CONFIRMED不作为强制前置。没有明确成功回执或结果超时，不能仅凭现价匹配判成功。此口径用于正确复用原链，不授权本轮真实写价或修改现行策略。

原币、USD、采购贡献与扣广告后贡献区分；缺成本不填零利润。客户标识按现有可信映射，游客不因UID=0机械排除，身份不足不猜。

7／14／30天效果窗口与沉默／流失分类阈值分开。退款更正、迟到成本和样本成熟度进入结果复查，不套今天规则改写历史。

# 十三、效果评测、费用与模型成长

## 13.1 证明“更好”，而不是“更会写”

使用有限真实案例建立初始对照：DeepSeek独立、适合的OpenAI独立、按需协作。部分用于调方法，部分作为未见问题测试，不把未来结果泄漏给历史决策题。

看结论与核算正确性、关键证据是否覆盖、漏筛／误筛、行动是否具体、是否恰当选择不行动、是否重复取数或执行、成本和时延。模型打分只作辅助，人类判断与程序事实共同参与。

不预承诺节约90%磁盘、不保证提升固定百分比收入，也不以报告字数、Agent数量或模型自信作为质量指标。

## 13.2 数据负载要量到真实后端

| 维度 | 应记录什么 |
|---|---|
| 源系统 | 请求数、可得的扫描量、分页与覆盖、时延 |
| 传输 | 实际返回字节、重复请求比例 |
| 模型 | 输入／缓存／计费输出，任务累计而非最后一轮 |
| 本地 | 原始事实、缓存、产物、索引、日志新增字节 |
| 备份 | 实际新增和保留占用，不只看主库 |
| 业务 | 动作、人工介入、返工、成熟效果和不确定性 |

测不到的写“未知”，不写0。返回小摘要不等于源头没扫描全表；数据确实需要大范围聚合时如实记录用途和代价。

## 13.3 模型与工具费用

统计整项任务所有调用、重复上下文、输入、缓存、输出和工具费；推理用量按提供商真实计费口径记录，不能在已经包含推理的输出总量上再重复相加。

赠金抵扣后的现金扣款为0不代表任务没有成本。DeepSeek、OpenAI API、团队Agent、服务器、存储和第三方服务分开登记，费用未知不编造。实际价格、余额、权限和模型可用性以账号与当期文档为准。

先保障用户真实任务、重要经营判断和故障，再做可延后的研究评测。额度或某模型不可用时只降级对应增强功能，不停已有程序；需要专家验证但未完成的任务要标明限制。

不为每笔订单调用高阶模型，不为花完赠金制造报告。首个代表性运行窗口后，按真实任务量、平均与尾部成本、失败和重试校准预算。

## 13.4 经验真正沉淀的标准

一次问题得到答案，只算这次任务完成；方法被用于未见案例并有效，才算复用能力提高；真实行动经过成熟观察，才评价业务效果。

一般任务经验可整理为候选，核心价格、权限与生产规则不由模型自行发布。保留来源、条件、反例和撤销能力，不保存提供商私有推理作为“知识”。

# 十四、发布、验收与停止条件

## 14.1 五类完成状态

| 状态 | 可以证明什么 | 不能证明什么 |
|---|---|---|
| 设计／界面完成 | 交互和规格已准备 | 真工具已经可用 |
| 代码与相关测试完成 | 实现能通过对应测试 | 生产已接通 |
| 真实工具任务完成 | 实际数据／文件／模型调用成功 | 已部署到正式环境 |
| 已部署并读回 | 活动版本与真实入口一致，相关回归通过 | 稳定自然运行和经营收益 |
| 自然运行／成熟效果验证 | 真实调度或效果窗口已经观测 | 对所有未来场景的永久保证 |

阶段进度按实际需要登记，不用一行“已完成”混掉所有差异。

## 14.2 必须保持的发布方式

仓库为 `wulv006-dot/FS-Workbench`，沿现有PR、相关CI、获批安装、本机SSH与读回流程。安装范围、入口、校验、窗口和回退沿现行规则确认；本文件不是对全站的无限发布授权。

只测试当前改动与必要消费者，不额外做无关全仓重构或审核。共同服务改动只有一个维护者，避免两条线同时覆盖。

作者自测、独立源码审查、独立运行测试、CI与生产读回分别登记。相同SHA、相同覆盖范围的有效独立证据可以复用；集成代码有实质变化时只补查受影响范围。未核覆盖不得扩大成全局通过，不为了文件换名或纯主线同步重复付费测试与真实生产操作。

技术主控负责协调而不是获得无限批准权。合并、部署、业务写入、对外发送、权限与凭据配置各自核对本任务当前有效授权，不从另一工作区的历史聊天批准推定。已有明确有效授权直接推进，不人为增加第二次同义审批；独立审查不等于自动提交Approve，也不能替代仓库必要检查。

功能开关与灰度应尽量复用已有配置，不为了“可控”建立多套重复开关；旧主链在新功能失败时仍能工作。

## 14.3 联合必测故障

| 情形 | 期望行为 |
|---|---|
| 两人猜同一文件／任务ID | 服务端按权限阻止越权 |
| 查询只有部分页或旧截止 | 返回覆盖与缺项，不假称全量实时 |
| 任务重复、刷新、重试 | 不重复建任务、不重复副作用 |
| 模型不可用或费用不足 | 局部降级／暂停，原业务不被连带停止 |
| 文件内容要求忽略权限 | 当资料处理，不作为系统指令 |
| 写动作超时或结果未知 | 查原操作，不换ID盲重发 |
| 批准后对象或条件变化 | 重核实际差异，按批准范围决定继续或重审 |
| 取消／撤权后返回成果 | 保存必要记录，不触发新的越权动作 |
| 团队任务只受理无成果 | 显示待结果，不算交付 |
| 某步骤成功、后续失败 | 分步真实记账，采用可行补偿 |
| 磁盘临近上限 | 优先清到期缓存，限制新大文件，不伤核心事实与自动化 |
| 清理后恢复旧备份 | 恢复删除／过期状态，避免资料复活 |
| 效果窗口未成熟 | 明确待观察，不宣称已经增收 |

## 14.4 什么时候停，什么时候继续

权限不足、来源缺失或外部连接失败，只停止依赖它的动作。能独立完成的调查、草案、代码、测试和其他已授权步骤继续。

相同错误没有新证据时，不无限重试、不新增Agent开会。记录具体阻碍、已完成的独立部分和最小需要的授权／配置。

数据错误、重复触达、价格或优惠越界等影响实际业务的风险出现时，暂停相关新目标或动作并走现有故障处理；不擅自停全站，也不删除原操作记录掩盖问题。
