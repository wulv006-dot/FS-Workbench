## 2. 视觉与信息架构定版

### 2.1 总体布局

- PC 优先。统一常驻左侧导航，宽 236px；顶部只留面包屑、页面级动作、主题与账号，不再放第二套全站导航。
- 1366×768、1440×900、1920×1080 为验收视口。浏览器 125%/200% 缩放不遮挡主动作；小窗口可折叠导航，不另做移动端产品。
- 内容宽度是**扣除侧栏后的可用宽度上限**：默认 1480px，分析/作业 1420px，阅读 1180px，登录/短表单 760px。实际 `width:100%;min-width:0`，不是强制固定宽。
- 首页保持今日经营 + 工作区 + 常用入口。经营管理台、游戏监控台仍同时出现在首页快捷区与数据分析目录。
- 一级导航：工作台、数据分析、Hermes 智体、球类工作区、RPG 工作区、机器人管理、协作工具。账号管理按已有权限显示。
- 数据分析：数据看板、运营报告、经营管理台、游戏监控台。运营报告打开 Hermes 报告页，不重新建立旧周报生产链路。
- 球类按 FC、MLB、NBA2K、Madden 分类；RPG 共用控制台保留一个主卡，再按实际深链接选择游戏，不能复制三张相同卡。
- “FC27 图片图库”纠正为“FC27 收藏馆调价”；“FC 赔率工具”按真实内容标为“FC26 库存与交付（历史工具）”，不伪装为 FC27 新工具。历史工具不做大改。

### 2.2 令牌与排版

主色浅色 `#1f6f73`、暗色 `#4db8b0`；主体背景分别 `#e9edf2`、`#0a1424`。卡片圆角 16px，表单 9px，紧凑控件 6px，模态 18px；保留少量 12/22/pill 场景，但不机械修改图表几何数值。

正文 14.5px/1.55，次要正文不低于 12px；表格 13–14px。数字使用 tabular-nums；金额保留原币种和精度，不为了统一视觉而四舍五入业务写入值。

参考包需修正对比度：`#74819a` 在白底约 3.93:1、`#9aa6b8` 约 2.46:1，不用于普通信息文字。浅色次要文字改 `#596980`（白底约 5.59:1）；三级信息也不得仅靠淡灰不可读。主按钮现行 CSS 已正确引用 `--fs-brand-on`，保留其暗色深字设计，不把它误判为白字缺陷。需实际修正的是 `.fs-btn--ok/--danger/--amber` 写死白字：例如白字配浅色成功绿约 3.33:1、配暗色成功绿约 2.00:1，不满足普通小字。新增各语义 `on-color` 令牌并验浅暗背景；警告文字另用深琥珀。

普通文字达到 4.5:1，大字达到 3:1；状态必须有文字/图标，不能只靠红绿。图表多序列可用蓝/紫/琥珀等辅助色，统一品牌不等于所有曲线涂成同色。

动效 120–200ms，开启反馈上限 320ms，仅真实成功切换触发；加载不闪六个开关。遵守 prefers-reduced-motion。默认不加额外状态光点和持续霓虹。

### 2.3 主题接线

继续接受现有 `theme=light|dark|system` 和 `fs-navigation-theme` 偏好；无历史偏好时默认浅色，有明确偏好的用户保持原选择。应用壳解析一次，向 html 和每个 Shadow host 下发同一有效主题。迁移期可同步 `data-theme` 与 `data-fs-theme`，但只维护一个状态源。

文档级组件 CSS 不会自动进入 Shadow DOM。分析模块必须在自己的 Shadow root 加载同版本组件样式，令牌从 host 继承；旧 `:host` 品牌变量整段拆除或映射。iframe 若存在需同源受控主题通信；不跨域强行注入。登录页使用轻量令牌/表单子集，不加载需要登录后才能取到的完整导航。

已核参考 `fs-tokens.css` 的显式暗色有 71 个令牌覆写，而系统暗色段只有 63 个，漏掉 `--fs-ok-hover`、`--fs-warn-hover`、`--fs-danger-hover`、`--fs-info-hover`、`--fs-grid-mask`、`--fs-sh-0`、`--fs-sh-inset`、`--fs-text-invert`。因此不能宣称两种暗色已同源完整。定版采用主题适配器统一输出显式主题；如保留无 JS 的系统 CSS 回退，须由同一令牌表生成，不手抄第二份。局部 light 容器也要有完整重置规则，不能只支持局部 dark。

## 4. 唯一真源、固定部署路径和拉取方式

### 4.1 三种“源”必须分清

1. 线上运行源：Nginx 实际命中的文件、服务实际启动源码/镜像。它决定不能丢掉的现状。
2. 维护源：以后只在这里编辑并测试的 Git 目录。它通过明确构建生成发布物。
3. 发布快照：releases/ 与服务器不可变版本，作为可复现证据与回滚资产；不再手工维护，但不能删掉。

每模块必须有一行 `module-source-lock.json`：moduleId、route、Git commit、editableSource、buildCommand、publisher、runtimeTarget、servedAssetUrls、sha256、serviceUnit、observedAt、evidenceLevel、rollbackReceipt。缺 runtimeTarget 或 hash 的行不进入本批部署。

### 4.2 共享 UI 新维护布局（本方案定版，尚未创建生产路径）

| 用途 | 固定维护路径 | 生产布局 |
|---|---|---|
| 设计令牌 | `ui-system/tokens/fs-tokens.css` | `/var/lib/fs-navigation-formal-static/<release-id>/ui/fs-tokens.css` |
| 通用组件 | `ui-system/components/fs-ui.css` | 同版本 `ui/fs-ui.css` |
| 主题/壳适配 | `ui-system/adapters/` | 同版本 `ui/`，仅在使用模块引用 |

`<release-id>` 是发布前一次生成并冻结的不可变标识，沿用现有 publisher 的合法格式。不是让施工者任选部署根目录。URL 固定为 `/dashboard/workspace-assets/<release-id>/ui/...`；扩展现有精确资产清单与路由，不新增宽泛目录 alias。这属于待实现的受控发布增量，需要测试对应的白名单、门禁、备份和回退；不直接将新文件塞进旧冻结合同。

固定模块业务 URL 不变。页面可锁定不同 UI 版本以分批发布；一个版本内的源码只生成一次。离线下载的老板 HTML 报告允许内嵌样式，其 CSS 必须由同一真源自动生成，保留版本标记，不依赖访问内网。

模块前端的唯一维护目录仅在对应批次采纳时建立：从已确认活动字节复制一次到 `ui-system/modules/<moduleId>/`，记录 adoption manifest，再更改该模块构建输入。不是现在搬动全仓。此前 releases 下的冻结文件不编辑；后台和 Python 内联页暂留原已核维护文件，只将适用样式作为共用资产引入，避免为抽离模板增加运行风险。

### 4.4 真源拉取操作顺序

1. 只读确认当前 Git main、线上发布 journal、活动发布锁/未确认发布。不启动或结束他人任务，不直接清锁。当前已核文件清单在 live-source-files.json，先对本批精确路径重算 SHA；不重新泛扫全机。

## 6. 开关与待决项最终裁决

UI 待决项由本方案定版；不借此制定新的业务恢复规则。

| 问题 | 定版 |
|---|---|
| 暂停后恢复 | 展示现有后端恢复策略；人工 OFF 永不自动开启。明确安全暂停提供“查看原因/检查恢复”动作，不能仅因竞品价格回升由前端自动开关 |
| 暂停时点击开关 | 开关只表达自动化意愿 enabled；暂停原因另做状态。关掉意愿即停自动，不把 switch 当展开详情按钮 |
| 业务停用解除 | 只有原后端授权角色和原解除入口可操作，留原审计。UI 不增管理员、不扩大权限 |
| 首次开启 | 明确说明会修改线上价格、对象与范围，确认后走已有业务请求；开关 UI 不另做隐藏写价 |
| 缺竞品源 | 行内提示“未配置”，跳现有配置入口；不默认替用户选来源或利润阈值 |
| 撤销窗口 | 普通筛选/本地表单可给 5 秒撤销；服务器写入和改价不提供假撤销。已提交动作只能按实际取消/补偿接口处理 |
| 保存反馈 | 点击立即锁重复提交；300ms 后显示写入中；10s 提示耗时，按原请求 ID 查询。超时 = 结果待确认，不能立刻回滚开关或新 ID 重试 |
| 无权限视图 | 只显示后端已授权可读字段；保留真实状态并解释不可操作原因，不能把不可读数据当完整状态暴露 |

开关实际状态模型：用户意愿 enabled + 运行状态 running/paused/error/off/unknown + 写请求 pending/confirmed/failed/unknown。不能用一个 checkbox 同时表示服务健康、业务授权和采集状态。ARIA switch 仍是布尔开关；暂停用附属文字解释，不创建不合法的 mixed 状态。

权限锁必须同时覆盖鼠标、标签点击、Space/Enter 与程序触发；disabled、事件处理及服务端校验共同生效。只加 pointer-events 或 aria-disabled 不足以防止请求。

### 6.1 对开关阶段规范的进一步纠偏

- 原文的“成本 ÷ 0.95”“每 30 分钟”“球员卡按 10-07 指令停用”均不是本次可写死的生产规则。按当前后端配置和最新用户指令显示；不能把历史停用样例写回当前球员同步状态。
- 不接受“关闭永远零风险”的假设。关闭会影响时效和在途任务；说明停止的是下一轮还是可取消的当前任务，由既有后端状态决定。
- 生产开关不使用“先显示已生效，超时就恢复原态”的乐观语义。显示目标意图及“待确认”，只有确认回执/读回才能显示已开启或已关闭；明确拒绝时才还原到已知状态。
- 行内确认不采用 3 秒自动消失，避免读屏及慢操作来不及；由用户确认/取消或离开页面结束。确认期间如果配置 revision 变化则失效并重读。
- “撤销关闭”实质是重新开启，可能重新启动改价。不能做无确认反向写入。仅在后端确有可取消事务且原动作未生效时提供真正取消；否则明确走新的开启流程。
- 原生 disabled 不等于所有读屏无法读取说明。保留常显原因和独立可聚焦的帮助/详情入口；如某控件为了可发现性选择 aria-disabled，必须在事件入口阻止请求，并保留服务端拒绝。不能宣称 change 后 revert 是唯一权威防线。
- 锁定原因由 `lockReason` 区分，`.is-off` 只表达关闭皮肤，不能隐含“禁止用户打开”。权限、业务安全锁、主动关闭分别有字段。
- Phase 1 与 Phase 2 文本含 v1.1/v1.3 与光点默认显示/可选等不一致。本单选择默认无呼吸光点，以文字“已暂停”与琥珀标识表达；不依赖闪烁速度区分风险。
- 演示 JS 的禁用回退写成 `input.checked = !input.checked`，只是假设当前事件必然翻转过。生产适配必须恢复已确认的服务端值，不能遇程序派发 change 就盲翻。
- 演示页的柱线组合图把利润率 `0.22` 与百万级营收共用同一个 Y 比例尺，折线会贴近零线。不得照搬为经营图表；金额轴和百分比轴分开，轴标签、单位和缺值定义明确。演示样本数据不能进入生产报告。
