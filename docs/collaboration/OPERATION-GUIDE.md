# FS GitHub协作：两位用户操作手册

版本：2026-10-06准备稿；仓库：[FS-Workbench](https://github.com/wulv006-dot/FS-Workbench)（private）。项目是MMOEXP游戏运营Agent，原工程为 `E:\WorkBuddy\大超服务器`。

本轮只交付手册和首次入库准备方案，未commit、push、部署、改权限或启动登录。用户已条件批准首批达到标准的干净源码、测试、文档入私库：先明确流程、AI约束、准确白名单并由根协调审核。这不等于允许把原工程、历史Git或311候选整包原样推上去。

后续今晚自主推进授权已收到：普通实现、可逆优化与条件齐全的首批入库由根协调推进，无需逐步再问。本分工仍不并发push。下文“等待批准”仅适用于尚未覆盖的模块生产放行、跨模块业务确认或重大事项；既有具体授权可直接引用。新持久凭据/OAuth/SSHkey、生产权限扩展、定价策略、不可恢复删除不能从广授权推导。

## 一、你们只需要做这六步

1. **告诉自己的AI做哪个模块、要改什么。** 开头复制下方“开始同步”模板；吴律处理FC/NBA/MLB等球类，陈超处理D4/Aion。
2. **看AI给的范围卡。** 只核对“目标模块、会改变的功能、影响其它模块吗、需要谁确认”。范围不明先停止；不需要自己敲Git命令。
3. **让AI在自己的独立分支做。** 分支可以理解成自己的工作副本；别人没提交的内容必须保留。改完让AI给一页中文结果：改了什么、通过哪些测试、哪些未验、回退怎么做。
4. **查看合并申请（PR）。** GitHub里可以点仓库的 `Pull requests`，打开AI提供的那一条，看 `Conversation` 中文说明、`Files changed` 文件列表和 `Checks` 检查结果。PR是“把我的改动加入共同版本”的申请。
5. **逐项确认，然后让AI合并。** 只说“批准这个PR的这个SHA合并到代码库，未批准上线”。共享或跨模块修改必须取得每个受影响负责人确认，不能只看一个绿色勾。提交变化后，旧确认失效，重新确认。作者的AI自称审查通过不代表另一个人确认了。
6. **上线另做一次明确批准。** 合并后网站不会自动更新。AI必须给出指定模块、确切commit SHA、精确文件/产物、测试与未验项、现场基线及回滚方案；你再决定是否批准该模块上线。第一次源码入库也不会自动改网站。

首次入库按 [FIRST-UPLOAD-PLAN.md](FIRST-UPLOAD-PLAN.md)；机器可核对的311来源清单及权限边界在 [SOURCE-MAP.json](SOURCE-MAP.json)。这些是准备资料，工程唯一协作事实源仍是主 `HANDOFF.md`，由根协调追加；本轮未改它。

## 二、什么可点，遇事问谁

| 位置/提示 | 可以做 | 必须停止的情况/处理人 |
| --- | --- | --- |
| Code、分支下拉、History、PR的Conversation/Files changed/Checks | 查看；把PR链接或报错交给自己的AI | 下载ZIP仅供查看，不拿ZIP覆盖工程或服务器 |
| Compare & pull request / Create pull request | AI核对分支、基线、秘密和范围后可创建；首次空库由根协调先建立干净基线 | 分支不明、出现其它模块、敏感文件或冲突就停 |
| Review / Approve | 让AI解释具体改动；本人只确认属于自己的业务范围 | 不能代替另一owner批准；同一PR后续有新提交要重看 |
| Merge / Confirm merge | 默认交AI执行；只有你已经批准该确切SHA、review和测试满足后才允许 | 不因按钮绿色直接点；不能跳过未验与owner项 |
| Update branch、Resolve conflicts、Revert、Delete branch | 交AI按模板处理；读回确认完成后再考虑删除已合并任务分支 | 不在网页随手选“全部用我的/全部用他的”；不要删除main |
| Settings / Rules / Collaborators / Billing / Actions | 本轮仅查看能力；任何变更另定任务 | 不改公开、不扩权限、不购套餐、不新增凭据、不启动未知workflow |
| 登录提示 | 普通查看可使用各自已有GitHub网页登录 | Git推送登录若需要新的授权或凭据，按入库计划说明后先停，不向AI粘贴密码/验证码/token |

FC/NBA/MLB问吴律；D4/PoE2/Aion2问陈超。共享登录、首页、导航由吴律主导发布，陈超可参与特殊情况和升级设计；不是排他权限。其它模块问两位及根协调确认责任，标“待指派”，不自行猜负责人。经营供数/准确区间被球类页面使用，不因此归球类owner独占。保留d4follow中已列的PoE2分支，不按目录名遗漏，真实运行仍需验收。

跨模块必要改动：AI先列“为什么必须改、具体文件、受影响模块/owner、接口兼容、测试和回退”。取得逐项确认后更新范围卡，才修改新列文件。分工不会给任何AI默认改其它模块的权利。

## 三、状态必须这样标

| 状态 | 含义 | 你该怎么理解 |
| --- | --- | --- |
| 准备中 / 待入库审核 | 本地材料，未上传 | 不能当共同最新版，更不能上线 |
| 源码已入库 / 未部署 | 远端已读回确切SHA，作为开发审阅基线 | 可以协作，网站尚未改变 |
| 测试通过（列范围）/ 仍有未验 | 只有列出的检查通过 | Windows跳过、Linux/真实角色/运行闭包缺口仍在 |
| 待owner确认 / 待合并 | 具体SHA尚未得到全部确认 | 不合并 |
| 已合并 / 未部署 | 已进入main，记录最终merge/squash SHA | 不是上线许可 |
| 待指定模块上线批准 | 产物和现场基线已准备 | 只批准列明模块及SHA，不批准“全站最新版” |
| 已部署 / 读回通过 | 现场版本、SHA、健康及业务合同已验证 | 自然周期另记；人工补跑不叫自然成功 |
| 阻断 / unknown / 漂移 | 结果或基线不可信 | 停止写入；核对旧操作，不换ID重试，不用旧包覆盖 |

同一commit可以“源码入库通过”且“生产发布阻断”。冻结revision3的 `releaseReady=false`、`uploadApproved=false` 是历史候选状态；新的条件入库批准必须在独立入库记录中注明，不修改冻结记录伪造成已验收。

## 四、双方AI共同硬约束（每次任务必读）

- 读取适用 `AGENTS.md`、`.gitignore`、最新 `HANDOFF.md` 和未决项、source-map、模块合同、最新验收。明确当前用户授权高于历史“未获push批准”，但不扩大到部署、凭据、权限或全目录上传。
- 核对远端仓库、private、分支、baseline SHA和本地状态。先记录别人的未提交文件与哈希；不reset、clean、stash他人改动，不整体复制，不把同事改动混进自己的提交。状态读回仍一致才继续。
- 原工程Git保持无remote、本机历史不推；独立干净仓库/工作树协作。不复制原 `.git`、raw、运行状态或冻结候选后原地修改。只有明确范围内的规范源可改；副本、历史baseline和部署目标不是默认真源。
- 一任务一分支，名如 `wulv/fc-ops-read-20261006`、`chenchao/d4-ui-20261006`；本轮未创建。branch范围卡列准确允许路径和只读依赖。同一模块也不允许互相覆盖未提交代码。
- 白名单控制新增和提交；`.gitignore`只是防误入，不会清除已跟踪秘密。禁止 `git add .`、`git add -A` 或整目录Web上传作为选文件流程。逐项stage，检查实际index、commit树和差异；只记秘密位置/类别，不输出秘密值。
- 禁止force push（包括force-with-lease）、reset远端main、旧包覆盖、重写公共历史、直接从原工程push。需要处理冲突就人工可审阅地合并；无法判断语义交对应owner。
- 不以CI绿色、页面200、静态解析、源文件存在或归档unit声明冒充实际运行、自然周期、角色或业务验收。缺现有只读角色就标未验；不新建账号/降级管理员补测。
- 源码协作不触生产。默认不启用Actions部署、cron/timer、价格自动写、权限、真实订单操作或新长期访问。只用已核实工具；不安装软件/执行未知候选代码来“完善手册”。
- NBA升级后置不拖其它模块：可独立审阅合并其它模块，但不把NBA未验修改打入其发布包。若共享认证/接口实际受影响，仍要跨模块审批与回归。NBA候选R3-01 UI稳定ID/结果核对、R3-02目录持久化及Linux验收未闭合，不能标可发布。
- FC普通同事读取全部FC经营数据（销售额、成本、利润、商品排行）已获业务批准；四静态别名、限定FC准确区间/投影、真实会话与负向角色矩阵尚未部署/验收。不开放内部全站range或其它业务；写价/上架/权限仍仅既有合法管理员。
- 生产部署与回滚必须另批指定模块和commit/产物；保留数据、队列、锁、回执、价格策略与审计。不回滚整个数据库撤销上游副作用；unknown先核对，不能生成新ID再写。

## 五、可复制给双方AI的任务模板

所有尖括号由AI填真实值；无法核实的写“未验/待确认”，不能伪造SHA、路径、同意或结果。以下模板是未来任务入口，本轮不执行其中写操作。

### A. 开始同步（每次先发）

```text
我代表<吴律/陈超>，目标是<模块与业务结果>。先只读核对，不触生产。
读适用AGENTS、gitignore、最新HANDOFF/未决项/source-map/本模块合同与验收。
核对实际项目和独立Git目录、private远端、main最新SHA、我当前分支/HEAD/状态。
只用既有认证，禁止打印秘密/新凭据/新OAuth或SSHkey/改权限/购套餐。
原E工程保持无remote/不推历史；别人未提交改动列位置和哈希并保留。
若已有Git无法鉴权，停止相关写动作并说明最小一次登录步骤，不自动开始授权。
输出范围卡、基线SHA、同步差异、风险、未验和需要谁确认。
在干净独立目录可fetch后从最新已核实main开我的任务分支；不要在dirty目录pull或覆盖。
只读/可逆准备可继续，涉及新范围/业务/生产批准的部分等待确认。
```

### B. branch范围卡（AI先填写，再动手）

```text
任务/提出人：<>
moduleId / 业务owner / 发布主导人：<>
独立工作目录 / 分支 / 远端：<>
baseline main SHA / 开始HEAD / 已有未提交快照：<>
批准目标与不变量：<>
允许改的精确路径：<>
允许只读依赖 / 禁止触碰路径：<>
跨模块变更：<无；或逐文件理由、受影响owner及本人确认记录>
auth/route/data-schema/price/schedule/shared/部署：<逐项是/否>
source→artifact→runtime映射依据及状态：<>
必要测试 / 当前未验 / 敏感物检查：<>
本任务允许<开发/提交分支/创建PR等>；不包含<未获批准的动作>。
发现新影响或基线漂移时只报告并更新范围卡，不能自动扩范围或重试写。
```

### C. 只改本模块并保留他人工作

```text
按已确认范围卡只修改<moduleId及精确路径>，在自己的独立分支完成。
先核对source-map真源和逐文件SHA；只读其它模块，不改bundle/历史baseline/runtime/冻结C3。
保留所有他人未提交文件，不stash/reset/clean、不整库格式化、不混入他们的差异。
必要跨模块问题先给具体理由/文件/兼容测试/owner表，等待该范围确认。
完成后给diff文件清单与哈希、行为变化、测试实跑输出摘要、未验与停止条件。
新增秘密排除项先在独立仓规则提出并修正，再按精确路径stage；不stage整个目录。
原工程的manifest收录源若未来获准修改须履行refresh_local副本同步；它不代表部署。
```

### D. 提交PR并做合并review

```text
本任务已允许<提交任务分支/创建PR>，仅针对范围卡内文件，未批准上线。
重新fetch，记录当前origin/main和PR head SHA；若main/文件基线变了，先审查兼容差异。
核对stage/commit树精确白名单和敏感物，真实运行必要隔离测试，逐项列pass/fail/skip/未验。
review包括source-map真源、变更路径、合同、权限/负向、共享消费者、数据与回退，不只看CI。
每个受影响owner各有一行：模块、姓名、确切head SHA、确认/未确认、证据；未确认不合并。
可请求另一位负责人安排其AI复核，但不可把作者AI自验当独立review或代替人类确认。
推分支前重查远端head；只fast-forward，不forcepush。冲突不点全部选一方。
根/owner批准确切SHA后才合并；提交新增后重新review与确认。
合并后读回远端main最终SHA/树/关键文件，与批准内容比对，记录已合并未部署。
若要向对方发送消息/PR评论，先确认我已明确授权该发送；不要自行发外部消息。
```

### E. owner逐项确认（本人使用）

```text
我<姓名>仅确认<我负责的模块/共享变更>：PR<链接>，head SHA<完整SHA>。
我看过<行为说明/差异/测试/未验项>，同意<仅入库合并；或明确列出的范围>。
其它受影响模块负责人仍需逐项确认。新的commit会使本次确认失效。
这不是生产上线、数据迁移、价格策略、自动运行、权限或新凭据批准。
```

### F. 指定commit模块上线（先准备，另获批准）

```text
只为<moduleId>准备上线审阅包，源commit<完整SHA>，精确文件/产物及依赖版本<清单>。
给source-map、产物SHA、必要运行闭包、既有认证角色、测试通过/未验、数据/锁/回执保护。
经已有授权只读核对现场版本与expectedLiveSHA；不读取/显示真实秘密，不触价格/部署。
列受影响其它模块、owner确认、发布锁/受控入口、读回指标、失败停止与单模块回滚方案。
若任一必要安全/运行/角色门槛未验，标阻断，不向人类推荐点上线。
等待我另发“批准<moduleId>按<commit/产物SHA>和清单上线”，不得由合并推导授权。
```

### G. 读回与回滚

```text
对已获明确批准的<模块/commit/产物>，在发布锁内重新读真实基线；漂移即停。
只用既有受控入口换本模块代码，保留数据/锁/receipt/配置/审计，检查其它模块仍正常。
读回源→产物→线上SHA、版本账本、既有角色/业务合同；自然作业按真实周期另验。
结果unknown/部分成功/并发冲突时暂停写，只读核对原ID与上游状态，不换ID重试。
需要回滚则先给确切目标版本/当前基线/兼容性/影响/备份摘要，按已有具体授权执行；
没有回滚授权就等待。Git代码撤回另开revert PR，不reset历史/forcepush；
现场回滚不能用旧ZIP/旧全站包/整库数据库覆盖。经营页仍走网关明确有意回滚合同。
输出实际结果与剩余未验；未经读回不得称成功。
```

## 六、规则和实际保护要分开

本轮只读确认私库为private、吴律连接有admin/push、大超write，远端分支列表为空。没有核实本账号套餐、branch protection/rulesets/CI/CODEOWNERS强制配置；本轮也没有启用它们。write是仓库级能力，不是“只准改自己的目录”。规则依赖AI范围守卫、review和双方执行，不能宣称GitHub已经强制锁死跨模块修改。

官方说明：私库保护分支和branch/tag rulesets支持GitHub Pro及相应Team/Enterprise方案；本账号是否有套餐和有效配置仍待核实，不购套餐。CODEOWNERS指定审阅者，需要配合要求owner审阅的有效规则；多个owner同一行通常任一人批准即可，不能自动代表双方都确认。以上不提供模块级代码阅读隔离。[保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)。

官方另将push rulesets列为Team私库/内部库能力，不应把它与Pro的branch rulesets混为一谈。当前无证据证明本库已配置任何这类强制保护。[Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)。根协调后续如需配置保护，应单列任务核实套餐、支持设置、适用分支、执行状态和bypass；不能先按“已强制”放行。即使有规则，管理员绕过/SSH root直接写和不经受控入口的生产行为也不由Git审阅全面约束。

## 七、异常一律先停写

看见 `authentication failed` / `403` / `protected branch`：停，不换token/放宽权限/禁用规则。`non-fast-forward` / `conflict`：先fetch、对照双方差异，不能forcepush。SHA不一致或出现其它模块：停并请对应owner确认。扫描发现秘密：不输出值、不上传、不测其有效性；若已泄露，交owner另行处理，不用删一行掩盖历史。生产读回失败或unknown：保留证据与旧ID，暂停写和重试；不能靠旧包盖回。任何未验都写明阻断的是“入库、合并还是该模块上线”，不把准备稿当完成事实。
